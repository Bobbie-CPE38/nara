# Demo runbook — ก่อนสร้างเหตุหรือเดินนาฬิกา

## ตรวจโหมดและผลข้างเคียงก่อนเริ่ม

**เครื่อง AWS ที่โหลดชุดใหญ่มีพนักงานจำลอง 500 คนอยู่ใน candidate pool จริงของระบบ ไม่ได้แยกออกจาก outreach.** การเพิ่มข้อมูลเองไม่สร้าง Offer/LLM แต่การกด Demo events, แจ้งลา, check-in ที่กระตุ้นงาน หรือเดินนาฬิกา/Job ภายหลังสามารถคัดเลือกพนักงานในทั้ง 20 หอ และเรียก LLM ตามค่าตั้ง/นโยบายที่เปิดอยู่. ผู้ที่มี LINE binding จริงใน pool เดิมหรือผูกใหม่อาจได้รับ Offer/Handover/Outcome จริง และ LLM อาจมีค่าใช้จ่าย. พนักงานใหม่เริ่มต้นไม่มี LINE binding จึงไม่ใช่การส่ง LINE ให้คนใหม่ครบ 500 คนทันที; นโยบายและสิทธิ์เดิมยังใช้ตัดสินผู้สมัคร.

ผู้ดูแลยืนยัน 2026-10-23 (Bangkok) ให้ **คง candidate pool และยอมรับผลข้างเคียงนี้**. ไม่ใช่การอนุญาตให้ส่งข้อความทดสอบโดยไม่ประสานผู้รับ หรือการยืนยันว่า workflow จริงผ่าน.

1. ตรวจ LINE/LLM mode บน Dashboard และตกลงผู้รับ LINE/ช่วงทดสอบกับทีมก่อนสร้างเหตุ. ใช้ session บัญชีของตัวเอง; Demo Basic credential ให้เฉพาะผู้ดูแลที่ Reset/เปลี่ยนนาฬิกาได้.
2. ถ้าจะทดสอบโดยไม่ส่ง LINE/ไม่เรียก LLM ให้ผู้ดูแลตั้ง `LINE_MODE=simulation`, `LLM_ENABLED=false` ผ่านแหล่ง env ของเครื่องและ restart ตาม [คู่มือ deploy](deploy-aws.md) ก่อนกดปุ่มใด ๆ. การไม่เปิดแอป LINE หรือการหยุด Quick Tunnel ไม่ปิดการส่งจาก AWS.
3. หากใช้ real mode ให้ตรวจคิว/ผู้รับตาม [runbook LINE](round6/pr-W-handoff.md) ก่อนเปิดและหลังทดสอบ. อย่าถือว่าการ freeze clock หยุดการส่งทั้งหมด และอย่าเปลี่ยนเป็น real หากยังมี intent จำลองค้างอยู่โดยไม่ตรวจ.
4. ค่อยสร้างเหตุ/แจ้งลา/เดินนาฬิกา แล้วตรวจเคสและผลข้างเคียง. อย่ากดซ้ำเพื่อแก้การรอส่งโดยไม่ตรวจสถานะ.
5. Reset ล้างสถานการณ์และยกเลิก session/code; อาจต้อง LINK ใหม่ตามกติกาเดิม. สำรองข้อมูลและตกลงช่วงหยุดก่อน Reset. บนเครื่องที่โหลด profile แล้ว Reset จะสร้างชุดใหญ่ใหม่ด้วย ห้ามใช้ seed ล้างฐานเพื่อแก้ข้อผิดพลาด.

## Golden Case เปลี่ยนรายชื่อสำรองหลัง import

การทดสอบแยก ณเวลา Golden fixture พบ pool 14 → 514 และผู้สมัครที่ถูกจัดอันดับ 3 → 123; สามอันดับแรก 201/202/203 และ first wave 201/202 คงเดิม และ flow ตอบรับ/อนุมัติ/Handover/เช็กอินผ่าน. แต่ 120 รายใหม่เป็นตัวสำรอง CROSS_WARD ถ้ารายเดิมปฏิเสธ/หมดเวลา flow ต่อไปอาจเลือกคนใหม่และขออนุมัติข้ามหอ. อย่าใช้สคริปต์เดิมโดยสมมติว่ารายชื่อหลังอันดับ 3 คงเดิมหรือไม่เกิด outreach เพิ่ม; ดู [หลักฐาน/ขอบเขตการทดสอบ](large-demo-data.md#golden-case-หลัง-import-automated-ไม่ใช่-aws-live).

## การตรวจชุดใหญ่

ใช้ supervisor 950 ดู Dashboard และ Gap ของหอ 10001–10020; staff ทั่วไปยังอยู่ภายใต้ scope เดิม. วิธีโหลด/backup และหลักฐาน operator อยู่ใน [คู่มือชุดใหญ่](large-demo-data.md). ประวัติ RESOLVED/UNRESOLVED/FAILED เป็น synthetic ใช้ดูข้อมูล ไม่ใช่ผล live Solver/approval/LINE และไม่ปิด AU4 acceptance.

## ผูก LINE ผ่านหน้าจัดการพนักงาน

ล็อกอินเว็บด้วยบัญชี **SUPERVISOR** ที่เปลี่ยนรหัสผ่านเริ่มต้นแล้ว (เช่น 950) → **จัดการพนักงาน** (`/admin/staff`) → ค้นหาด้วยรหัสหรือชื่อ → ตรวจชื่อ/หอ → **สร้างโค้ดผูก LINE** → **คัดลอกข้อความ**. ส่ง `LINK <รหัส>` ให้เจ้าตัวเป็นการส่วนตัว เพื่อส่งจาก LINE ของตัวเองไปหา NARA. ไม่ต้องเข้า EC2 และไม่ต้องใช้ Demo Basic credential ในหน้านี้. บัญชี Head Nurse/Staff และ X-Demo-User ไม่มีสิทธิ์ออกโค้ด แม้ AUTH_MODE=demo; ต้องใช้ session ของ Supervisor จริง.

โค้ดใช้กลไกเดิม: ใช้ได้ครั้งเดียว อายุ 10 นาทีตาม Backend clock (รวมการ freeze/advance ใน Demo). หน้าจอแสดงเวลาหมดอายุ; ถ้าซ่อน/เปลี่ยนหน้าแล้วจะไม่ดึง raw code เดิมกลับมา. ส่งให้เฉพาะบุคคลที่เลือก; หน้าเว็บไม่เก็บโค้ดใน URL/localStorage. การออกโค้ดใหม่ไม่ยกเลิกโค้ดเก่าที่ยังไม่หมดอายุ ตามพฤติกรรม CLI เดิม. พนักงานที่ไม่ Active/ไม่มี USER actor ออกโค้ดไม่ได้ และคนที่มี LINE binding อยู่แล้ว (รวม inactive contact) ต้องปลดก่อน; หน้านี้ไม่มีการแก้ข้อมูลพนักงาน.

เมื่อผูกสำเร็จ พนักงานส่ง **`MYID`** ในแชตส่วนตัวกับ NARA เพื่อดูรหัสพนักงานของบัญชีที่ผูกอยู่ เช่น 201. ใช้ได้เฉพาะ active staff + active contact + USER actor ตามการตรวจเดิม; ไม่ตอบรหัสในกลุ่ม/ห้อง และไม่รองรับการระบุรหัสคนอื่น. หากยังไม่ผูก ระบบแนะนำให้ขอโค้ดจากผู้ดูแล. ถ้าต้องสมัครเว็บ พิมพ์ `REGISTER` เพื่อรับรหัสสมัครเว็บอายุ 10 นาที (real UTC) ตาม flow เดิม; MYID ไม่สร้างบัญชีหรือรหัสสมัคร.

API เพิ่ม: `GET /admin/staff?q=&offset=0&limit=25` (สูงสุด 100 ต่อหน้า), `POST /admin/staff/{staff_id}/line-code` → `{code, expires_at}`. ทุก response ใต้ `/admin` เป็น `Cache-Control: no-store`; ทุก write ต้องมี allowed Origin ทั้ง demo/session. ออกโค้ดสูงสุด 20 ครั้งต่อนาทีต่อ Supervisor ใน process เดียว (รีสตาร์ตล้าง limiter). ไม่มี migration และไม่มีการ deploy/live LINE test อัตโนมัติจาก PR.


### ยกเลิกการผูก LINE พร้อมยืนยันรหัส

ในหน้าจัดการพนักงาน กด **ยกเลิกการผูก LINE** ที่พนักงานซึ่งมี binding → ตรวจชื่อ/รหัส → พิมพ์ Staff ID ให้ตรงทุกหลัก → กด **ยืนยันยกเลิกการผูก**. ปุ่มยืนยันยังใช้ไม่ได้ถ้าเว้นว่างหรือกรอกผิด; Backend ตรวจซ้ำกับ staff_id ใน URL ด้วย (`confirm_staff_id` ต้องเป็น string ตรงกัน). กดยกเลิกแบบฟอร์มจะไม่ส่งคำสั่งและล้างค่าที่กรอก. หน้าโหลดสถานะใหม่หลังสำเร็จ จึงสร้างโค้ด LINK ใหม่ให้พนักงาน Active ได้.

สิทธิ์ Supervisor/session/Origin/no-store เหมือนการออกโค้ด รวมการปลดพนักงาน Inactive ที่ยังมี binding. `POST /admin/staff/{staff_id}/line-unlink` รับ `{ "confirm_staff_id": "201" }` ตอบ `{ "unlinked_contacts": 1 }`; ID ยืนยันไม่ตรงตอบ 400 และ body ที่ขาด/ชนิดผิดตอบ 422 โดยไม่ปลดใคร. เรียกซ้ำที่ปลดแล้วตอบ 0. ใช้ `line_account_service.unlink` เดิม: ล้าง LINE binding, revoke โค้ด LINK และ REGISTER ที่ยังไม่ได้ใช้ และ Audit `LINE_ACCOUNT_UNLINKED` บันทึก actor ของ Supervisor ที่กดจริง (CLI เดิมยังใช้ SYSTEM). ไม่ลบบัญชีเว็บ รหัสผ่าน หรือประวัติเวร. LINE เดิมใช้ MYID/REGISTER/check-in/ตอบ Offer ในฐานะพนักงานนี้ต่อไม่ได้จนกว่าจะผูกใหม่.
