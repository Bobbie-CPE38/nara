# ภาพรวมงานหลัง Skeleton

แต่ละแถวคือหนึ่งรอบ ทั้งสามคนทำขนานกันในรอบเดียวกัน

ตารางนี้ปรับตาม Contract รอบ 1, รอบ 2 และรอบ 3 แล้ว งานที่ถูกดึงมาทำก่อนเอาออกจากรอบเดิม งานที่เหลือยังอยู่รอบเดิมตามแผนแรก เลขรอบคงไว้ รอบ 4 จึงมีช่องว่าง (R2-Q36)

| รอบ | คน 1 | คน 2 | คน 3 | ของที่ต้องตกลงร่วมกันก่อนเริ่มรอบ |
| :-: | :-- | :-- | :-- | :-- |
| **1** | Merge Gap (Window, Threshold, Event สี่ชนิด, Job), Coverage (`effective_minimum`), สถานะเคสคำนวณจาก Gap | Hard Rules ของจริง, Solver ใช้ Gap และ Soft Constraint, Working Time Snapshot, Safety รายคน | Wave, Reject, หลาย Offer ต่อคน, อนุมัติและจัดเวรรายคน, Timeout ของ Offer | ตกลงแล้ว อยู่ใน `round1-contract-draft.md` |
| **2** | เส้นออกจาก `MANUAL_HANDOFF` (Head Nurse จัดคนเอง หรือปิดเคสโดยไม่มีคนแทน), การอนุมัติจำกัดหอ | OR-Tools: Hard Rules คัดข้างนอกเหมือนเดิม OR-Tools ทำ Soft ผลเท่ารอบ 1 | Approval Timeout และการกลับไปต่อท้ายคิวหนึ่งครั้ง | ตกลงแล้ว อยู่ใน `docs/round2/round2-contract-draft.md` |
| **3** | งานค้างของ Roster และการลา (R3-Q1), เปิด PR สภาพแวดล้อมทดสอบบน AWS | คะแนนและคำอธิบายอันดับ พร้อมประโยคจาก LLM (Bedrock) | LINE จริง + Webhook + ตรวจ Signature, ผูกบัญชี LINE | ตกลงแล้ว อยู่ใน `docs/round3/round3-contract-draft.md` หน้าเว็บพยาบาลตกลงแล้ว ผู้ทำตกลงตอนแตก branch |
| **4** | (งานเดิมย้ายไปรอบ 1) | Cross-Ward, ผู้อนุมัติเป็น Supervisor | Auto-Approval | ใครอนุมัติกรณีข้ามหอ, กติกาเทียบ `incoming_count` ของ Auto-Approval |
| **5** | ห่อ Orchestrator ด้วย LangGraph | `NO_SHOW` | Handover | Orchestrator เปลี่ยนโครง ต้องไม่ทำ Handler ของคนอื่นพัง |
| **6** | LLM สรุปสถานการณ์ |  | LLM ตีความคำตอบอิสระ | ทีมต้องเลือกก่อนว่าจะทำทางนี้ไหม |

| :-- | :-: | :-- |

## จุดที่งานของสามคนพันกัน

- **รอบ 1** พันกันมากสุด: Wave ของคน 3 เลือกคนจาก Plan ของคน 2 และทั้งคู่ใช้ Gap ของคน 1 ส่วนสถานะเคสของคน 1 ถูกเรียกจากการตอบ Offer และการอนุมัติของคน 3 ลำดับ PR อยู่ข้อ 10 ของร่าง
- **รอบ 2:** OR-Tools ต้องให้ผลเท่ากับ Solver รอบ 1 เมื่อพิสูจน์ได้ว่าดีสุด Test ที่สมมติรายชื่อผู้สมัครตายตัวจึงไม่ควรแดง PR A ตรึงผลเดิมไว้เทียบแล้ว จุดที่พันกันจริงของรอบนี้คือตัวอ่านกลางใน `case_facts_service` ซึ่งทั้ง Approval Timeout และเส้นออกจาก `MANUAL_HANDOFF` แก้ และสาย Migration สามตัว ลำดับ PR อยู่ข้อ 6 ของร่างรอบ 2
- **รอบ 5:** LangGraph แตะไฟล์กลาง (`orchestrator.py`) ที่ทุก Handler พึ่ง ควรทำตอนที่คนอื่นไม่ได้แก้ Handler อยู่

## วิธีทำ Spec ของแต่ละรอบ

ทีมใช้แบบ A: ตกลง Contract ทีละรอบ

| แบบ | ทำยังไง | ข้อดี | ข้อเสีย |
| :-- | :-- | :-- | :-- |
| **A. ตกลง Contract ทีละรอบ (ใช้แบบนี้)** | ก่อนเริ่มแต่ละรอบ ตกลงเฉพาะของกลางของรอบนั้น แล้วเขียนลง `workflow.md` ใน PR เดียวให้ทุกคนรีวิว รายละเอียดข้างในแต่ละคนออกแบบเอง | เหมือนขั้นที่ 0 กับ PR scaffold ของขั้นที่ 4 ที่ทีมทำแล้วได้ผล ทำขนานได้ทันที | ต้องมีวินัยตกลงก่อนเขียนโค้ดทุกรอบ |
| **B. Spec ใหญ่ทั้ง 6 รอบทีเดียว** | ออกแบบทุกอย่างให้จบก่อนเริ่ม | เห็นภาพรวม เจอข้อขัดแย้งข้ามรอบเร็ว | ใช้เวลานาน รอบท้าย ๆ จะเดาผิดเพราะยังไม่รู้ผลของรอบต้น |
| **C. แยก Spec คนละไฟล์ ไม่มีของกลาง** | แต่ละคนเขียน Spec ของงานตัวเอง | เร็วสุด | เสี่ยงซ้ำรอยขั้นที่ 4 ที่มี Query เดียวกันสองที่ และ PR สองตัวเขียวแยกกันแต่รวมแล้วพัง |

งานที่ซับซ้อนเฉพาะคน เช่น OR-Tools ของคน 2 หรือ LINE Webhook ของคน 3 เขียน Spec แยกเป็นไฟล์ของตัวเองได้ ซึ่ง `repo-structure.md` เตรียมชื่อไว้แล้ว (`optimization.md`, `safety-validation.md`, `approval.md`) ส่วน `workflow.md` เก็บเฉพาะของที่ข้ามคน รอบ 2 ไม่ใช้ไฟล์แยก Spec ของทั้งรอบรวมการออกแบบข้างในของ OR-Tools อยู่ในร่างรอบ 2 ไฟล์เดียว (R2-Q38)

เหตุผลที่ไม่ทำ Spec ใหญ่: รอบ 1 รอบเดียวมีงานจากรอบ 2, 3 และ 4 ถูกดึงเข้ามาระหว่างตกลง Contract ถ้าเขียนล่วงหน้าทั้ง 6 รอบจะต้องรื้อ

5. คน 1 เปิด PR 0 ของรอบ 2: ย้าย Contract เข้า `workflow.md` พร้อมเส้น T8 กับ T9 ใน `transitions.py` และค่าใหม่ใน `enums.py` (เสร็จแล้ว PR #52)
6. แตก branch งานตามลำดับ PR ในข้อ 6 ของร่างรอบ 2 (เสร็จแล้ว PR ทุกตัวเข้า `staging` ครบ #51 ถึง #57 รายชื่ออยู่ที่ `docs/workflow.md` ส่วน "สถานะของรอบ 2")
7. จัดงานของรอบ 3 ใหม่ (เสร็จแล้ว PR #60) รอบ 3 มีคำอธิบายอันดับ, LINE จริง, หน้าเว็บพยาบาล, งานค้างของคน 1 และสภาพแวดล้อมทดสอบบน AWS
8. คน 1 เปิด PR 0 ของรอบ 3: ย้าย Contract เข้า `workflow.md` และค่าใหม่ใน `enums.py`
9. แตก branch งานตามลำดับ PR ในข้อ 6 ของร่างรอบ 3 รายชื่ออยู่ที่ `docs/workflow.md` ส่วน "สถานะของรอบ 3"
