# ภาพรวมงานหลัง Skeleton

> แต่ละแถวคือหนึ่งรอบ ทั้งสามคนทำขนานกันในรอบเดียวกัน

| รอบ | คน 1 (คุณ) | คน 2 | คน 3 | ของที่ต้องตกลงร่วมกันก่อนเริ่มรอบ |
| :-: | :-- | :-- | :-- | :-- |
| **1** | Coverage ครบ: Role + Skill + Minimum | Hard Rules ของจริง ใช้ร่วมทั้ง Solver และ Safety | Reject แล้วไปคนถัดไป, Head Nurse ไม่อนุมัติ | Transition ใหม่ของเส้นปฏิเสธ, Audit `OFFER_REJECTED` / `SAFETY_FAILED` / `APPROVAL_REJECTED`, รหัส Hard Rule |
| **2** | เช็กว่าใครว่างด้วยกติกาเดียวทั้งระบบ | OR-Tools: Hard ก่อน แล้ว Soft | Celery + Redis: Candidate Timeout | กติกา availability ตัวกลาง, Transition ของ Timeout, ลำดับ Lock ของงานเบื้องหลัง |

| **4** | รวม Event หลายตัว + Lock ต่อ Shift | Cross-Ward, ผู้อนุมัติเป็น Supervisor | Approval Timeout, Auto-Approval | กติการวม Event, นิยาม `ratio` / `incoming_count`, ใครอนุมัติกรณีข้ามหอ |
| **5** | ห่อ Orchestrator ด้วย LangGraph | `NO_SHOW` | Handover | Orchestrator เปลี่ยนโครง ต้องไม่ทำ Handler ของคนอื่นพัง |
| **6** | LLM สรุปสถานการณ์ |  | LLM ตีความคำตอบอิสระ | ทีมต้องเลือกก่อนว่าจะทำทางนี้ไหม |

## จุดที่งานของสามคนพันกัน

- **รอบ 1** พันกันมากสุด: Reject ของคน 3 ต้องมีผู้สมัครคนถัดไป ซึ่งมาจาก Solver ของคน 2 และทั้งคู่ต้องใช้ Coverage ของคุณตัดสินว่ายังขาดคนไหม
- **รอบ 2:** กติกา availability ของคุณถูกเรียกจาก Solver, Safety และ Execute อยู่แล้ว แก้ทีเดียวกระทบทุกคน
- **รอบ 5:** LangGraph แตะไฟล์กลาง (`orchestrator.py`) ที่ทุก Handler พึ่ง ควรทำตอนที่คนอื่นไม่ได้แก้ Handler อยู่

## ต้องออกแบบ spec ไหม

ต้องครับ แต่ไม่ใช่เขียนใหม่ทั้งก้อน เพราะ `workflow.md` เป็น spec กลางอยู่แล้ว สิ่งที่ขาดคือส่วนของกรณีพิเศษ ซึ่ง Skeleton เขียนไว้แค่ว่า "เพิ่มเมื่อ Implement"

| แบบ | ทำยังไง | ข้อดี | ข้อเสีย |
| :-- | :-- | :-- | :-- |
| **A. ตกลง contract ทีละรอบ (แนะนำ)** | ก่อนเริ่มแต่ละรอบ นั่งตกลงครึ่งวันเฉพาะของกลางของรอบนั้น แล้วเขียนลง `workflow.md` ใน PR เดียวให้ทุกคนรีวิว รายละเอียดข้างในแต่ละคนออกแบบเอง | เหมือนขั้นที่ 0 กับ PR scaffold ของขั้นที่ 4 ที่ทีมทำแล้วได้ผล ทำขนานได้ทันที spec | ต้องมีวินัยตกลงก่อนเขียนโค้ดทุกรอบ |
| **B. spec ใหญ่ทั้ง 6 รอบทีเดียว** | ออกแบบทุกอย่างให้จบก่อนเริ่ม | เห็นภาพรวม เจอข้อขัดแย้งข้ามรอบเร็ว | ใช้เวลานาน รอบท้ายๆ จะเดาผิดเพราะยังไม่รู้ผลของรอบต้น และรอบ 6 ทีมยังไม่ได้ตัดสินด้วยซ้ำ |
| **C. แยก spec คนละไฟล์ ไม่มีของกลาง** | แต่ละคนเขียน spec ของงานตัวเอง | เร็วสุด | เสี่ยงซ้ำรอยขั้นที่ 4 ที่มี query เดียวกันสองที่ และ PR สองตัวเขียวแยกกันแต่รวมแล้วพัง |

**แนะนำแบบ A** โดยเพิ่มจากที่เคยทำหนึ่งอย่าง: งานที่ซับซ้อนเฉพาะคน เช่น OR-Tools ของคน 2 หรือ LINE Webhook ของคน 3 ให้เขียน spec แยกเป็นไฟล์ของตัวเอง ซึ่ง `repo-structure.md` เตรียมชื่อไว้แล้ว (`optimization.md`, `safety-validation.md`, `approval.md`) ส่วน `workflow.md` เก็บเฉพาะของที่ข้ามคน

**เหตุผลที่ไม่แนะนำ spec ใหญ่:** ตลอดขั้นที่ 3 ถึง 6 การออกแบบเปลี่ยนกลางทางหลคิด Headcount, `resume()`, snapshot ของ Gapถ้าเขียนล่วงหน้าทั้งหมดจะต้องรื้อ
