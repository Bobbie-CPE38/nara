# ภาพรวมงานหลัง Skeleton

แต่ละแถวคือหนึ่งรอบ ทั้งสามคนทำขนานกันในรอบเดียวกัน

ตารางนี้ปรับตาม Contract รอบ 1 แล้ว งานที่ถูกดึงมาทำในรอบ 1 เอาออกจากรอบเดิม งานที่เหลือยังอยู่รอบเดิมตามแผนแรก รอบ 2 ถึง 4 จึงมีช่องว่าง ทีมต้องจัดงานของรอบ 2 ขึ้นไปใหม่ก่อนเริ่มรอบ 2

| รอบ | คน 1 | คน 2 | คน 3 | ของที่ต้องตกลงร่วมกันก่อนเริ่มรอบ |
| :-: | :-- | :-- | :-- | :-- |
| **1** | Merge Gap (Window, Threshold, Event สี่ชนิด, Job), Coverage (`effective_minimum`), สถานะเคสคำนวณจาก Gap | Hard Rules ของจริง, Solver ใช้ Gap และ Soft Constraint, Working Time Snapshot, Safety รายคน | Wave, Reject, หลาย Offer ต่อคน, อนุมัติและจัดเวรรายคน, Timeout ของ Offer | ตกลงแล้ว อยู่ใน `round1-contract-draft.md` |
| **2** | (งานเดิมย้ายไปรอบ 1) | OR-Tools: Hard ก่อน แล้ว Soft | (งานเดิมย้ายไปรอบ 1) | Solver แบบ OR-Tools ต้องให้ Plan และ `rank` รูปเดิม |
| **3** | การจัดการเคสหลัง `MANUAL_HANDOFF`, Escalation | คะแนนและคำอธิบายอันดับ | LINE จริง + Webhook + ตรวจ Signature | เส้นออกจาก `MANUAL_HANDOFF`, รูปของคำอธิบายอันดับ |
| **4** | (งานเดิมย้ายไปรอบ 1) | Cross-Ward, ผู้อนุมัติเป็น Supervisor | Approval Timeout, Auto-Approval | ใครอนุมัติกรณีข้ามหอ, Transition ของ Approval Timeout |
| **5** | ห่อ Orchestrator ด้วย LangGraph | `NO_SHOW` | Handover | Orchestrator เปลี่ยนโครง ต้องไม่ทำ Handler ของคนอื่นพัง |
| **6** | LLM สรุปสถานการณ์ |  | LLM ตีความคำตอบอิสระ | ทีมต้องเลือกก่อนว่าจะทำทางนี้ไหม |

งานที่ถูกดึงมารอบ 1

| งาน | รอบเดิม | เหตุผล |
| :-- | :-: | :-- |
| รวม Event หลายตัว + Lock ต่อ Shift (Merge Gap) | 4 | เคสรับหลายคนต้องรู้ Gap รวมของเวรตั้งแต่เปิดเคส |
| Candidate Timeout | 2 | Wave ที่ไม่มีใครตอบจะค้างเคสไว้ ใช้ Job ตัวเดียวกับ Merge Gap ไม่ใช้ Celery + Redis |
| หยุดเคสที่ `MANUAL_HANDOFF` | 3 | ไม่เหลือผู้สมัครไม่ใช่ระบบขัดข้อง จึงไม่ควรเป็น `FAILED` รอบ 1 แค่หยุดที่สถานะนี้ |
| Working Time Snapshot | 3 | การจัดอันดับด้วย Soft Constraint ต้องใช้ชั่วโมง, OT และเวรติดกัน |
| Soft Constraint (ใช้ Weight) | 2 | ใช้จัดอันดับตั้งแต่รอบ 1 เหลือแค่การเปลี่ยนไปใช้ OR-Tools |
| กติกาตรวจความพร้อมตัวเดียวทั้งระบบ | 2 | ตัวตรวจ Hard Rules ของรอบ 1 เป็นตัวเดียวที่ Solver, Wave และ Safety เรียก และ `assert_available()` ถูกลบ |

## จุดที่งานของสามคนพันกัน

- **รอบ 1** พันกันมากสุด: Wave ของคน 3 เลือกคนจาก Plan ของคน 2 และทั้งคู่ใช้ Gap ของคน 1 ส่วนสถานะเคสของคน 1 ถูกเรียกจากการตอบ Offer และการอนุมัติของคน 3 ลำดับ PR อยู่ข้อ 10 ของร่าง
- **รอบ 2:** OR-Tools เปลี่ยนว่าใครอยู่ใน Plan และอันดับ Test ของคน 3 ที่สมมติรายชื่อผู้สมัครตายตัวจะแดง
- **รอบ 5:** LangGraph แตะไฟล์กลาง (`orchestrator.py`) ที่ทุก Handler พึ่ง ควรทำตอนที่คนอื่นไม่ได้แก้ Handler อยู่

## วิธีทำ Spec ของแต่ละรอบ

ทีมใช้แบบ A: ตกลง Contract ทีละรอบ

| แบบ | ทำยังไง | ข้อดี | ข้อเสีย |
| :-- | :-- | :-- | :-- |
| **A. ตกลง Contract ทีละรอบ (ใช้แบบนี้)** | ก่อนเริ่มแต่ละรอบ ตกลงเฉพาะของกลางของรอบนั้น แล้วเขียนลง `workflow.md` ใน PR เดียวให้ทุกคนรีวิว รายละเอียดข้างในแต่ละคนออกแบบเอง | เหมือนขั้นที่ 0 กับ PR scaffold ของขั้นที่ 4 ที่ทีมทำแล้วได้ผล ทำขนานได้ทันที | ต้องมีวินัยตกลงก่อนเขียนโค้ดทุกรอบ |
| **B. Spec ใหญ่ทั้ง 6 รอบทีเดียว** | ออกแบบทุกอย่างให้จบก่อนเริ่ม | เห็นภาพรวม เจอข้อขัดแย้งข้ามรอบเร็ว | ใช้เวลานาน รอบท้าย ๆ จะเดาผิดเพราะยังไม่รู้ผลของรอบต้น |
| **C. แยก Spec คนละไฟล์ ไม่มีของกลาง** | แต่ละคนเขียน Spec ของงานตัวเอง | เร็วสุด | เสี่ยงซ้ำรอยขั้นที่ 4 ที่มี Query เดียวกันสองที่ และ PR สองตัวเขียวแยกกันแต่รวมแล้วพัง |

งานที่ซับซ้อนเฉพาะคน เช่น OR-Tools ของคน 2 หรือ LINE Webhook ของคน 3 เขียน Spec แยกเป็นไฟล์ของตัวเอง ซึ่ง `repo-structure.md` เตรียมชื่อไว้แล้ว (`optimization.md`, `safety-validation.md`, `approval.md`) ส่วน `workflow.md` เก็บเฉพาะของที่ข้ามคน

เหตุผลที่ไม่ทำ Spec ใหญ่: รอบ 1 รอบเดียวมีงานจากรอบ 2, 3 และ 4 ถูกดึงเข้ามาระหว่างตกลง Contract ถ้าเขียนล่วงหน้าทั้ง 6 รอบจะต้องรื้อ

## ขั้นถัดไป

1. ทีมรีวิว PR เอกสารของ branch `docs/round1-contract` (เสร็จแล้ว PR #32)
2. คน 1 เปิด PR 0: ย้าย Contract เข้า `workflow.md` พร้อม `transitions.py` และ `enums.py` (เสร็จแล้ว PR #33)
3. แตก branch งานตามลำดับ PR ในข้อ 10 ของร่าง (เสร็จแล้ว PR ทุกตัวเข้า `staging` ครบ รายชื่ออยู่ที่ `docs/workflow.md` ส่วน "สถานะของรอบ 1")
4. จัดงานของรอบ 2 ขึ้นไปใหม่ เพราะงานหลายตัวถูกดึงมารอบ 1 แล้ว **ยังไม่ได้ทำ และเป็นขั้นถัดไปของทีม** ตารางบนสุดของไฟล์นี้ยังเป็นแผนเดิม: รอบ 2 มีงานของคน 2 คนเดียว (OR-Tools) ช่องของคน 1 และคน 3 ว่าง
