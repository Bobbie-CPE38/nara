## สิ่งที่ตกลงแล้ว

### Merge Gap (คน 1)

- Event ของเวรเดียวกันถูกเก็บรอไว้ใน Window ก่อน ยังไม่เปิดเคส ตอนรับ Event ระบบเก็บแค่ตัว Event (`RECEIVED`)
- พอ Window ปิด ระบบทำทีละ Event: บันทึกการลาหรือแก้ข้อมูลของ Event นั้น แล้วตรวจ Threshold (Ratio, Role Gap, Skill Gap) หลังวนครบทุก Event จึงเขียน `required_staff` จากจำนวนผู้ป่วยค่าสุดท้าย คิด Gap แล้วสร้างเคส ถ้า Gap สุดท้ายเป็น 0 ทุกตัว ไม่สร้างเคส
- หนึ่ง Window เปิดได้หนึ่งเคส Event ที่เข้ามาตอนเวรมีเคสเดินอยู่ต้องรอเคสนั้นจบก่อน ไม่ถูกเอาไปรวมกับเคสเดิม
- รับ Event ครบสี่ชนิด: `STAFF_UNAVAILABLE`, `ASSIGNMENT_CANCELLED`, `PATIENT_SURGE`, `REQUIREMENT_CHANGED`
- ความยาว Window ตั้งต่อเวรที่ `SHIFT.merge_window_seconds` Golden Case ใช้ 0 จึงได้ผลเหมือนวันนี้
- มี Job เป็น Service แยกใน `docker-compose.yml` เรียก Backend ทุก 30 วินาทีให้ปิด Window ที่ถึงเวลา

### เคสรับหลายคน

- เป้าหมายของเคสคือทำให้ Gap หมด ทั้งจำนวนคน, Role และ Skill ไม่ใช่ได้คนครบจำนวน และใช้หลายคนปิดได้
- สถานะเคสคำนวณจาก Gap ที่เหลือและ Offer ที่ค้าง ไม่เดินตามผู้สมัครคนเดียว
- Safety ตรวจรายคนทันทีที่ตอบรับ อนุมัติรายคน อนุมัติแล้วจัดเวรทันที ไม่ตรวจซ้ำ
- ไม่เหลือผู้สมัครและไม่มีคนรออนุมัติที่เติม Gap ได้ เคสไป `MANUAL_HANDOFF` ไม่ใช่ `FAILED` ยกเว้นยังมี Offer ที่ผู้สมัครกดรับไม่ได้ชั่วคราวเพราะไปรับเคสอื่น เคสรอจน Offer นั้นหมดเวลาก่อน

### Wave และ Offer (คน 3)

- ส่ง Offer เป็น Wave หลายคนพร้อมกัน Target ต่อ Gap แต่ละแบบ = `ceil(gap * 11 / 10)`
- คนหนึ่งคนนับให้ทุก Target ที่เขาตรง Golden Case จึงส่ง Wave แรก 2 คน คือ 201 กับ 202
- ผู้สมัครตอบ `REJECT` ได้ และถือ Offer จากหลายเคสพร้อมกันได้ไม่เกิน 3 (`OUTREACH_POLICY`)
- Offer หมดเวลาใน 300 วินาที การอนุมัติไม่มี Timeout

### Hard Rules และ Solver (คน 2)

- Hard Rules 11 รหัส เป็น Pure Function ใน `domain/constraints/` ใช้ผลเดียวกันทั้ง Solver, การเลือกคนของ Wave และ Safety
- เพดานสองตัวเป็น Hard Constraint: ชั่วโมงรวม 52 ต่อสัปดาห์ และเวรต่อเนื่อง 7 เวร ตรวจหลังรวมเวรที่เสนอ ส่วน OT รายสัปดาห์เกินได้ ใช้เป็น Soft Constraint อย่างเดียว
- Solver อ่าน Gap ของเคส เลือกกลุ่มด้วยสูตร `plan_penalty` ที่ใช้ Weight จาก `SOFT_CONSTRAINT_POLICY`
- Plan เก็บทุกคนที่ผ่าน Hard Rules กลุ่มที่ Solver เลือกคือ Wave แรก คนที่เหลือรอ Wave ถัดไป
- ตาราง `CANDIDATE_ITEM_TARGET` เก็บว่าแต่ละคนถูกเลือกมาเติม Target ไหน
- ใช้ `STAFF_WORKING_TIME_SNAPSHOT` ตั้งแต่รอบ 1

## จุดที่ต้องรู้ก่อนเริ่มเขียนโค้ด

1. **PR 0 ยังไม่ลบสองเส้นของ `SAFETY_VALIDATION`** โค้ดวันนี้ยังเดินผ่านสองเส้นนี้ ถ้าลบก่อน Golden Path จะพัง PR 0 เพิ่ม T1 ถึง T7 อย่างเดียว สองเส้นเดิมลบใน PR 3
2. **PR M ลบ `STAFFING_CASES.event_id`** Test ของทุกคนที่สร้างเคสตรง ๆ จะแดงหลังรวม และทุกคนต้อง `make reset` หลัง merge
3. **PR 2b เปลี่ยน Golden Path** `OFFER_SENT` มีสองแถว และ 202 มี Offer Test ที่ตรวจลำดับ Audit ทั้งเส้นต้องแก้ใน PR เดียวกัน
4. **ลำดับ Lock เปลี่ยน** การตอบ Offer, การอนุมัติ และ Job ของ Offer หมดเวลา ล็อกตามลำดับเดียวกัน: Offer ที่ยังไม่จบของเคสทุกแถว แล้วเคส แล้ว `STAFF` ของผู้สมัครทั้ง Plan การอนุมัติล็อก Offer ของผู้สมัครคนนั้นในเคสอื่นด้วย (ข้อ 4.3)
5. **เคสที่หยุดแล้วไม่รับคำตอบ** ตอนเคสเข้า `MANUAL_HANDOFF` Offer ที่ยัง `SENT` ถูกยกเลิก ทั้ง `respond` และ `decision` ตอบ `409` กับเคสที่หยุดแล้ว และ `recompute()` ไม่ทำอะไรกับเคสแบบนั้น
6. **เคสอื่นที่ได้รับผลกระทบต้องถูกสั่งให้คำนวณสถานะใหม่** เมื่อผู้สมัครตอบรับ หลุด หรือได้เวรในเคสหนึ่ง Offer ของเขาในเคสอื่นเปลี่ยนตาม ผู้เรียกต้องเรียก `recompute()` ให้เคสอื่นหลัง Commit ไม่งั้นเคสนั้นค้าง (ข้อ 2.3)
7. **PR 2b, 3 และ 4 เข้า Branch รวมก่อน** แล้ว merge เข้า `staging` ครั้งเดียว เพราะสามตัวนี้ต้องอยู่ครบระบบจึงทำงานถูก (ข้อ 10)

## ข้อจำกัดของร่าง

- รายการ Test ที่จะแดงมาจากการอ่านโค้ด ยังไม่ได้รันจริง
- ลำดับ Lock เป็นการวิเคราะห์ ยังไม่มี Test สอง Connection พิสูจน์
- ตาราง Hard Rules ยังไม่ได้เทียบกับ Model `HardConstraintPolicy` ทีละคอลัมน์
