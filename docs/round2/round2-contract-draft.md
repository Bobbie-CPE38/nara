ตาราง `docs/round1/next-move.md` กำหนดรอบ 2 ไว้แบบนี้ และ PR ปิดรอบไม่ได้เปลี่ยนแผน

`next-move.md` ข้อ "ขั้นถัดไป" ข้อ 4 เขียนไว้ตรง ๆ ว่าการจัดงานรอบ 2 ขึ้นไปใหม่ **ยังไม่ได้ทำ และเป็นขั้นถัดไปของทีม**

รอบ 2 จึงมีเรื่องที่ต้องทำสองขั้น

1. **ทีมต้องจัดงานของคน 1 และคน 3 ก่อน** ร่างนี้เสนอทางเลือกไว้ในข้อ 3.2 แต่ไม่ได้เลือกแทนทีม
2. **ตกลง Contract ของ OR-Tools** ซึ่งเป็นงานเดียวที่กำหนดแล้ว ร่างนี้เขียนส่วนที่เป็นของกลางไว้ในข้อ 4 ส่วนการออกแบบข้างใน Solver เป็นของคน 2 ข้อตกลงเดิมให้อยู่ในไฟล์แยก `docs/optimization.md` แต่คน 1 ตอบ R2-Q38 ว่ารอบนี้ใช้ Spec รวมในไฟล์นี้ ไม่แยกไฟล์

ข้อ 1 และข้อ 2 ตรวจจากโค้ดจริงแล้วทั้งหมด ไม่มีข้อไหนต้องรอ PR อีก ส่วนข้อ 3 ถึง 7 เป็นข้อเสนอและคำถาม

**คำตอบของคน 1 โดยย่อ (2026-10-13):** รอบ 2 มีสามงาน คือ OR-Tools (คน 2), เส้นออกจาก `MANUAL_HANDOFF` (คน 1) และ Approval Timeout (คน 3) OR-Tools ทำแค่ Soft ผลต้องเท่าเดิม มีเพดานเวลา 3 วินาที ไม่ใช้ Branch รวม และ Migration ของคน 3 เข้าก่อนของคน 2 Head Nurse จัดคนของหอเดียวกันเข้าเวรเองได้ และข้ามได้เฉพาะกฎความล้า คำขออนุมัติหมดเวลาที่ 900 วินาที แล้วผู้สมัครกลับไปต่อท้ายคิวได้หนึ่งครั้ง ไม่มีกำหนดเสร็จของรอบ

**สิ่งที่รีวิวของ PR #50 พบ (2026-10-13):** คำตอบสามเรื่องยังลงมือทำไม่ได้กับโค้ดปัจจุบัน ต้องตกลงรายละเอียดเพิ่มก่อน คือ เวรที่ Head Nurse จัดเองยังไม่ถูกนับว่าปิด Gap ของเคส (ข้อ 3.2 และ R2-Q40), การติดต่อคนเดิมรอบที่สองชนกับโค้ดที่สมมติว่าหนึ่งคนมีหนึ่งรอบต่อเคส (ข้อ 3.2 และ R2-Q41) และ `solve()` ยังไม่มีช่องรับเพดานเวลากับช่องคืนสถานะ (ข้อ 4.1 และ R2-Q42)

**คำตอบของคน 1 ต่อรีวิว (R2-Q40 ถึง R2-Q55) โดยย่อ:** เวรที่จัดเองผูกกับเคสด้วยตารางใหม่ `manual_assignment` การติดต่อรอบที่สองแยกด้วย Offer โดยผล Safety และคำขออนุมัติชี้ไป Offer ของรอบนั้น `solve()` เพิ่ม Argument หนึ่งตัวและช่องสถานะหนึ่งช่อง **`UNKNOWN` พาเคสไป `MANUAL_HANDOFF` ไม่ใช่ `FAILED` (เปลี่ยนจากคำตอบ R2-Q4 และ R2-Q5 เดิม)** เพดาน 3 วินาทีเป็นงบรวม Head Nurse จัดคนที่มีการตอบรับค้างในเคสอื่นได้หลังยืนยันคำเตือน แล้วระบบยกเลิก Offer ที่ขัดกัน คน 1 ทำ PR ที่จำกัดการอนุมัติตามหอ และ PR H ทำตามคำตอบ R2-Q14 ไปเลยโดยไม่รอผู้รู้

## 4. Contract ของ OR-Tools

### 4.1 สิ่งที่ต้องเหมือนเดิม

* Argument ห้าตัวเดิมของ `solve()` และสามค่าเดิมของ `SolverResult` (ข้อ 1) ความหมายไม่เปลี่ยน
* **[จากรีวิว] ส่วนที่ต้องเพิ่มใน Interface (R2-Q42)** ร่างเดิมเขียนว่า Signature ต้องเหมือนเดิมทั้งหมด ซึ่งขัดกับข้อ 4.4 เพราะ `solve()` ตอนนี้ไม่มีช่องรับเพดานเวลา และ `SolverResult` ไม่มีช่องคืนสถานะ `create_plan()` จึงเดาสถานะจากว่ามีผู้สมัครหรือไม่ [คน 1] R2-Q42 ก: เพิ่มได้สองอย่างนี้เท่านั้น
  * ข้อมูลเข้า: เพดานเวลาเป็น Argument แบบ keyword ตัวใหม่ `create_plan()` อ่านค่าจาก Policy แล้วส่งเข้ามา `solver.py` ยังไม่อ่าน DB
  * ผลลัพธ์: `SolverResult` มีช่องสถานะเพิ่มหนึ่งช่อง เป็นค่าของ `SolverStatus`
  * ที่ผู้เรียกต้องแก้ใน PR B: `create_plan()` ส่งเพดานเวลา, เขียน `CANDIDATE_PLANS.solver_status` จากช่องสถานะแทนการเดา, เมื่อไม่มีผู้สมัครผ่าน Hard Rules เลยยังได้ `INFEASIBLE` โดยไม่ต้องเรียก OR-Tools เหมือนเดิม และ `optimize.py` ต้องจัดการสถานะที่ไม่มีคำตอบตามข้อ 4.4
* `rank` เรียง 1 ถึง n: คนใน Wave แรกก่อน เรียงด้วย `ranking_key` แล้วตามด้วยคนที่เหลือ เรียงด้วย `ranking_key`
* `first_wave` บอก Target ที่แต่ละคนเติม ได้จาก `fill_targets()` ตัวเดิม ไม่ใช่จาก OR-Tools
* Target ที่ผู้สมัครมีไม่พอถูกลดลงเท่าจำนวนคนที่ตรง (ร่างรอบ 1 ข้อ 8.3)
* ผลต้องซ้ำเดิมเมื่อข้อมูลเข้าเหมือนกัน**และสถานะเป็น `OPTIMAL`** คำตอบแบบ `FEASIBLE` (หมดเวลาก่อนพิสูจน์) อาจไม่ซ้ำเดิม เพราะขึ้นกับว่าเครื่องค้นไปได้ไกลแค่ไหนก่อนหมดเวลา ตรงกับข้อ 4.4 แถว "การรันซ้ำ"
* `solver.py` ไม่อ่าน DB ไม่เขียน และไม่อ่าน Clock ของระบบ (`clock.now()`) การจับเวลาเพื่อเพดานเวลาเป็นเรื่องข้างในของ OR-Tools ไม่นับเป็นการอ่าน Clock ของระบบ

### 4.2 สิ่งที่เปลี่ยน

* การค้นกลุ่มที่ `plan_penalty` ต่ำสุด เปลี่ยนจากการค้นแบบตัดกิ่งที่เขียนเอง (`_cheapest_covering_group`) เป็นโมเดลของ OR-Tools
* `SOLVER_VERSION` เปลี่ยนจาก `"weighted-v1"` เป็นค่าใหม่ เพื่อให้รู้ว่า Plan แถวไหนมาจาก Solver ตัวไหน
* เพิ่ม Dependency `ortools` ซึ่งตอนนี้ไม่มีใน `backend/pyproject.toml` ลองให้ `pip` คำนวณใน container ของ Backend แล้ว (Python 3.11.17, ไม่ได้ติดตั้งจริง) ได้ `ortools 9.15.6755` และดึงของตามมาอีกเจ็ดตัว: `numpy`, `pandas`, `protobuf`, `absl-py`, `immutabledict`, `python-dateutil`, `six` ผลที่ตามมา
  * [จากรีวิว แก้ข้อความเดิมที่ผิด] คำสั่งเริ่มของ container ของ Backend คือ `pip install --no-cache-dir -e ".[dev]"` คำสั่งนี้รันทุกครั้งที่ container เริ่ม แต่ดาวน์โหลดไม่เท่ากันทุกครั้ง container เดิมที่หยุดแล้วเริ่มใหม่ยังมีแพ็กเกจที่ติดตั้งไว้ `pip` จึงแค่ตรวจว่ามีครบ ส่วน container ที่ถูก**สร้างใหม่** (เช่น `docker compose down` แล้ว `up` หรือ image เปลี่ยน) ไม่มีแพ็กเกจเหลือ ต้องดาวน์โหลดและติดตั้งชุดนี้ใหม่ทั้งหมด และเพราะมี `--no-cache-dir` จึงไม่มี cache ช่วย
  * CI ใช้ `pip install -e ".[dev]"` พร้อม cache ของ pip cache ลดการดาวน์โหลด แต่ขั้นติดตั้งยังต้องทำทุกครั้ง CI จึงช้าลงทุกรอบ ไม่ใช่แค่ครั้งแรก
  * container ของ Job รันแค่ `app.jobs.ticker` ไม่ได้ติดตั้งแพ็กเกจ จึงไม่กระทบ ตราบที่ `ticker` ไม่ import Solver
  * [คน 1] รับได้ ไม่เปลี่ยนวิธีติดตั้งในรอบนี้ วัดเวลาเริ่ม container จริงใน PR ของ OR-Tools ถ้าช้าเกินไปค่อยกลับมาตัดสิน (R2-Q11)

### 4.3 "Hard ก่อน แล้ว Soft" หมายถึงแบบไหน (ต้องตกลง)

ตอนนี้ Hard Rules ถูกตรวจรายคนใน `hard_rule_service` **ก่อน**เรียก `solve()` คนที่ไม่ผ่านไม่ถูกส่งเข้า Solver

| ทาง | ทำยังไง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **ก. คัดด้วย Hard Rules ข้างนอกเหมือนเดิม OR-Tools ทำแค่ Soft (แนะนำ)** | การคัดรายคนด้วย Hard Rules ใน `create_plan()` ไม่เปลี่ยน OR-Tools รับเฉพาะคนที่ผ่านแล้ว เงื่อนไขในโมเดลมีแค่ "ครอบคลุม Target ครบ" [จากรีวิวรอบสอง แก้ข้อความเดิม] ร่างเดิมเขียนว่า `create_plan()` ไม่เปลี่ยนเลย ซึ่งขัดกับข้อ 4.1 ที่ `create_plan()` ต้องส่งเพดานเวลาและอ่านสถานะ | Hard Rules ยังมีที่เดียว Safety, Wave และ Solver ใช้ตัวตรวจตัวเดียวกันเหมือนรอบ 1 ส่วนของ Hard Rules ไม่ถูกแตะ สิ่งที่เปลี่ยนคือ `solver.py` กับผู้เรียกสองจุดในข้อ 4.1 | OR-Tools ไม่เห็นเงื่อนไขระดับกลุ่ม เช่น สองคนในกลุ่มรวมกันแล้วผิดกฎบางข้อ |
| ข. ย้าย Hard Rules เข้าโมเดล | เขียน Hard Rules เป็น Constraint ของ OR-Tools | รองรับเงื่อนไขระดับกลุ่มและ Cross-Ward ในรอบ 4 ได้ตรง | กติกา Hard มีสองที่ (โมเดลกับ `domain/constraints/`) Safety ยังใช้ตัวเดิม สองที่ไม่ตรงกันได้ และรหัสเหตุผลที่ข้ามรายคน ซึ่งหน้า `cases/[id]` แสดงอยู่แล้ว ต้องหาทางสร้างใหม่ |
| ค. สองชั้น | รายคนคัดข้างนอก เงื่อนไขระดับกลุ่มเข้าโมเดล | ได้ทั้งสองอย่าง | รอบ 2 ยังไม่มีเงื่อนไขระดับกลุ่มสักข้อ จึงเป็นงานเผื่อ |

เหตุผลที่แนะนำทาง ก: Hard Rules ของรอบ 1 ทุกข้อตรวจรายคนกับเวรที่เสนอ ไม่มีข้อไหนขึ้นกับว่าใครอยู่ในกลุ่มเดียวกัน และรอบ 1 เพิ่งรวมตัวตรวจให้เหลือตัวเดียว

**[คน 1] เลือกทาง ก** กฎระดับกลุ่มไม่อยู่ในรอบ 2 ถ้ารอบ 4 ทำ Cross-Ward จึงเพิ่มเฉพาะกฎระดับกลุ่มเข้าโมเดล (รูปของทาง ค) โดยตัวตรวจรายคนและโมเดลของรอบ 2 ใช้ต่อได้ งานนั้นต้องทำไม่ว่ารอบ 2 เลือกทางไหน เพราะกฎระดับกลุ่มต้องใช้ข้อมูลของหออื่นที่รอบ 2 ยังไม่มี

| หมดเวลา | มีคำตอบแล้วแต่ยังพิสูจน์ไม่ได้: ใช้คำตอบนั้นและเขียน `FEASIBLE` บันทึกใน Audit `SOLVER_EXECUTED` อย่างเดียว ไม่มีเครื่องหมายในหน้าเว็บ (R2-Q32) ไม่มีคำตอบเลย: เขียน Plan ที่มีสถานะ `UNKNOWN` และเคสเป็น `MANUAL_HANDOFF` (R2-Q43 ก เปลี่ยนคำตอบ R2-Q5 เดิมที่ให้ `FAILED`) ไม่ถอยไปใช้การค้นแบบเดิม |

**[จากรีวิว] สถานะที่ไม่มีคำตอบ: `UNKNOWN` กับ `MODEL_INVALID` ต่างกัน (R2-Q43)**

* `MODEL_INVALID` คือโมเดลที่โค้ดสร้างขึ้นผิดรูป เป็นบั๊กของระบบ
* `UNKNOWN` คือหมดเวลาก่อนเจอคำตอบแรก และก่อนพิสูจน์ได้ว่าไม่มีคำตอบ เป็นผลที่เกิดได้ตามปกติเมื่อโจทย์ใหญ่เทียบกับเพดานเวลา **ไม่ใช่ระบบทำงานผิด** ไฟล์คำถามชุดแรกเขียนรวมสองค่านี้ว่าเป็นระบบทำงานผิด ซึ่งไม่ถูก แก้ที่ R2-Q4 แล้ว
* **[คน 1] R2-Q43 ก: แยกสองค่า** `UNKNOWN` ไป `MANUAL_HANDOFF` พร้อมเหตุผลใหม่ และ `MODEL_INVALID` ไป `FAILED` ข้อนี้เปลี่ยนคำตอบ R2-Q4 ส่วนที่ 2 และ R2-Q5 คำถามย่อยของคน 1 ซึ่งเดิมให้ `FAILED` ทั้งสองค่า คน 3 เป็นผู้เสนอ และคน 2 เขียนในรีวิวว่าเอนไปทางเดียวกัน
  * `optimize.py` ไม่โยน Exception เมื่อได้ `UNKNOWN` เขียน Plan และ Audit `SOLVER_EXECUTED` ตามปกติ แล้วเขียน Audit `MANUAL_HANDOFF` ด้วยเหตุผลใหม่ใน `ManualHandoffReason` ชื่อที่เสนอคือ `SOLVER_TIMEOUT`
  * `MODEL_INVALID` โยน Exception ที่ชื่อบอกสาเหตุ เคสเป็น `FAILED` ผ่าน D11
  * Head Nurse รับช่วงเคสที่ Solver หมดเวลาได้ด้วยเส้นออกจาก `MANUAL_HANDOFF` ในข้อ 3.2 เคสแบบนี้ไม่มี `CANDIDATE_ITEMS` เลย การเลือกคนจากทั้งหอ (R2-Q13) จึงจำเป็น
* เหตุผลที่ทำให้เลือกทางนี้ สองข้อ ตรวจจากโค้ดแล้ว
  * **ถ้าเคสเป็น `FAILED` จะไม่มีแถว Plan ที่มีสถานะ `UNKNOWN` หรือ `MODEL_INVALID` เหลือในฐานข้อมูล** เคสเป็น `FAILED` ได้ทางเดียวคือ Handler โยน Exception แล้ว `orchestrator._run_round()` ย้อน Savepoint ของรอบนั้นทั้งรอบ แถว `CANDIDATE_PLANS` กับ Audit `SOLVER_EXECUTED` ที่เขียนในรอบนั้นจึงหายไปด้วย สิ่งที่เหลือคือ Audit `WORKFLOW_FAILED` ซึ่งเก็บแค่ชื่อชนิดของ Exception (`error_type`) ไม่เก็บข้อความ ถ้า `UNKNOWN` ไป `FAILED` จึงไม่มีอะไรบอกว่าเกิดจากหมดเวลา
  * **เคส `FAILED` ไม่มีใครรับช่วงได้** ตามคำตอบ R2-Q22 เคส `FAILED` แสดงในรายการแต่กดจัดการไม่ได้ เวรที่ Solver หมดเวลาจึงยังขาดคนโดยไม่มีเส้นทางในระบบให้ Head Nurse จัดคน ในทางที่เลือก Handler ไม่โยน Exception แถว Plan ที่มีสถานะ `UNKNOWN` ถูกเก็บ และ Head Nurse รับช่วงได้ทันที (`ManualHandoffReason` ตอนนี้มี `NO_CANDIDATE_LEFT` กับ `NO_FEASIBLE_PLAN`)

**[จากรีวิว] เพดานเวลาครอบคลุมอะไร (R2-Q44)**

* [คน 1] R2-Q44 ก: 3 วินาทีเป็นงบรวมของการเรียก `solve()` หนึ่งครั้ง ถ้าโมเดล Solve หลายรอบ (เช่น รอบหาคะแนนต่ำสุด แล้วรอบตัดสินคะแนนเท่ากัน) ทุกรอบใช้งบก้อนเดียวกัน รอบหลังได้เวลาเท่าที่เหลือ ไม่ใช่รอบละ 3 วินาที
* เพดานนี้จำกัดเวลาค้นของ OR-Tools อย่างเดียว **ไม่ได้จำกัดเวลาที่ถือ Lock** ซึ่งรวมการโหลดข้อมูล การตรวจ Hard Rules การสร้างโมเดล และการเขียน Plan ด้วย ประโยคในไฟล์คำถามชุดแรกที่ว่าเพดานเวลา "จำกัดเวลาที่ถือ Lock ได้แน่นอน" จึงเกินจริง แก้แล้ว PR B ต้องวัดเวลารวมของ `create_plan()` ไม่ใช่เวลาค้นอย่างเดียว

ข้อนี้คือคำตอบของคน 2 ต่อเรื่อง "ตัวตัดสินเมื่อคะแนนเท่ากัน และการคูณสเกล" ข้อความที่ขึ้นต้นด้วย **[คน 2]** เป็นของคน 2 คนเดียว คน 1 และคน 3 ยังไม่ได้ยืนยัน ข้อความที่ขึ้นต้นด้วย **[ตรวจแล้ว]** คือสิ่งที่คน 1 ตรวจกับโค้ดหรือรันพิสูจน์

**1. สูตรคะแนน**

* [คน 2] คะแนนของผู้สมัครแต่ละคนคำนวณด้วย `candidate_penalty()` ตัวเดิม ใช้ `Fraction` ตลอด ไม่แปลงผ่าน `float`
* [คน 2] ให้ `x_i` เป็น 1 เมื่อเลือกผู้สมัครคนที่ i และเป็น 0 เมื่อไม่เลือก คะแนนของกลุ่มคือผลรวมคะแนนของคนที่เลือก ตามสูตร `plan_penalty` เดิม
* [คน 2] ข้อบังคับการเติม Target ของจำนวนคน Role และ Skill และการลด Target เมื่อผู้สมัครมีไม่พอ ใช้กติกาของรอบ 1

**2. แปลงคะแนนเป็นจำนวนเต็มโดยไม่ปัดเศษ**

* [คน 2] ให้คะแนนของแต่ละคนเป็นเศษส่วนที่ลดรูปแล้ว `p_i = a_i / b_i` สเกลคือ `L = LCM(b_1, ..., b_n)` และคะแนนจำนวนเต็มคือ `C_i = a_i × (L / b_i)` ไม่ใช้สเกลตายตัวแบบ 100 หรือ 1,000 เพราะแทนเศษส่วนบางค่าไม่ได้ตรง
* [คน 2] หลังแปลงแล้ว หาร `C_i` ทุกตัวด้วย GCD ร่วมเพื่อลดขนาดตัวเลข ถ้าคะแนนทุกคนเป็นศูนย์ ใช้ตัวหาร 1
* [คน 2] ตรวจขอบเขตจำนวนเต็มที่ CP-SAT รองรับ และตรวจความถูกต้องของโมเดลก่อนรัน ถ้าตัวเลขใหญ่เกินหลังลดรูปแล้ว ให้โยนข้อผิดพลาดเฉพาะ เช่น `SolverScalingOverflowError` เข้าเส้นทางระบบผิดพลาด (เคสเป็น `FAILED` ผ่าน D11) ห้ามแก้ด้วยการปัดเศษ ลดความแม่นยำ หรือเปลี่ยน Weight โดยไม่บอก
* [ตรวจแล้ว] ตัวอย่างของคน 2 รันด้วยโค้ดแล้วตรง: คะแนน `5/4` กับ `13/10` ได้ `L = 20` และคะแนนจำนวนเต็ม 25 กับ 26 ซึ่ง GCD ร่วมเป็น 1 ส่วนกรณีคะแนนเป็นศูนย์ทุกคน GCD ได้ 0 จึงต้องใช้ตัวหาร 1 ตามที่เขียน

**3. เลือกกลุ่มสามขั้น ตามลำดับเดียวกับรอบ 1**

* [ตรวจแล้ว] `_cheapest_covering_group` ของรอบ 1 เทียบคำตอบด้วย `(plan_penalty, จำนวนคน, tuple(sorted(staff_ids)))` ค่าน้อยกว่าชนะ การเรียงผู้สมัครด้วยคะแนนก่อนค้นเป็นแค่ลำดับเดินการค้น ไม่ใช่ตัวตัดสิน
* [คน 2] **ขั้นที่ 1 คะแนนต่ำสุด:** Minimize `Σ C_i × x_i` เมื่อพิสูจน์ค่าต่ำสุดได้แล้ว เพิ่มข้อบังคับตรึงคะแนนเท่ากับค่านั้น ค่าที่ใช้ตรึงคำนวณจาก `C_i` กับค่า `x_i` ด้วยจำนวนเต็ม ไม่ดึงจากค่า Objective แบบ floating point ของ Solver
* [คน 2] **ขั้นที่ 2 จำนวนคนน้อยสุด:** ภายใต้คะแนนที่ตรึงไว้ Minimize `Σ x_i` เมื่อพิสูจน์ได้แล้ว เพิ่มข้อบังคับ `Σ x_i = จำนวนคนต่ำสุดที่พิสูจน์ได้` ถ้ายังพิสูจน์ไม่ได้ ให้หยุดและคืนแผนที่ใช้ได้เป็น `FEASIBLE` ไม่ตรึงจำนวนคนจากคำตอบที่ยังไม่พิสูจน์
* [คน 2] **ขั้นที่ 3 ชุด `staff_id` ที่น้อยสุดตามลำดับ:** หลังตรึงคะแนนและจำนวนคนแล้ว
  1. เรียงผู้สมัครตาม `staff_id` จากน้อยไปมาก
  2. สำหรับผู้สมัครคนปัจจุบัน ตั้ง Objective เป็น Maximize `x_i` โดยคงข้อบังคับทั้งหมด รวมค่าที่ตรึงจากคนก่อนหน้า
  3. เมื่อพิสูจน์ได้ ตรึง `x_i` เท่ากับค่าที่ได้ แล้วทำคนถัดไป
  4. ทำจนค่าการเลือกของทุกคนถูกกำหนด หรือค่าที่เหลืออนุมานได้จากจำนวนคนที่ตรึงไว้
* [คน 2] ห้ามใช้ผลรวม `staff_id` เป็น Objective และห้ามใช้แค่การเรียงรายชื่อหลังเลือกกลุ่ม เพราะไม่รับประกันสมาชิกกลุ่มเดียวกับรอบ 1 ตัวอย่าง: `[201, 204]` ชนะ `[202, 203]` เพราะตำแหน่งแรก 201 น้อยกว่า 202 ทั้งที่ผลรวมของสองชุดเท่ากัน
* [ตรวจแล้ว] ขั้นที่ 3 ให้ผลเท่ากับการเทียบ `tuple(sorted(staff_ids))` ของรอบ 1 จริง ลองด้วยโค้ดกับโจทย์สุ่ม 2,440 ชุด (กลุ่มขนาดเท่ากัน เลือกคน ID ต่ำสุดที่ยังเลือกได้ก่อน) ได้ชุดเดียวกับค่าต่ำสุดของ tuple ทุกชุด การลองนี้ทดสอบหลักการ ไม่ได้ทดสอบโมเดล OR-Tools ซึ่งยังไม่มี

**5. สถานะที่รายงาน**

| สถานะ | [คน 2] ความหมาย |
|---|---|
| `OPTIMAL` | พิสูจน์ครบทั้งคะแนน จำนวนคน และชุด `staff_id` |
| `FEASIBLE` | มีแผนที่ผ่านข้อบังคับ แต่หมดเวลาก่อนพิสูจน์ครบทุกขั้น แม้ขั้นคะแนนจะพิสูจน์แล้ว |

| `INFEASIBLE` | พิสูจน์ว่าไม่มีแผนตามข้อบังคับ ตามคำตอบท้ายข้อนี้ ค่านี้ออกจาก `solve()` เฉพาะเมื่อไม่มีผู้สมัครเลย ถ้า OR-Tools รายงานค่านี้ทั้งที่มีผู้สมัคร `solve()` คืน `MODEL_INVALID` |

* [คน 2] ต้องเก็บแผนที่ใช้ได้ล่าสุดไว้แยกจากตัว Solver ก่อนเริ่มรอบถัดไป

* [คน 2] รอบหลังคืน `MODEL_INVALID` หรือเกิดข้อผิดพลาดของระบบ: รายงานข้อผิดพลาด ห้ามกลบด้วยคำตอบของรอบก่อน
* [คน 2] รอบหลังพิสูจน์ `INFEASIBLE` ทั้งที่มีแผนเดิมซึ่งควรผ่านข้อบังคับที่เพิ่งตรึง: ถือเป็นความผิดปกติของการสร้างโมเดล ไม่ใช่ "ไม่มีผู้สมัคร" สถานะที่คืนคือ `MODEL_INVALID` ตามคำตอบท้ายข้อนี้

## 8. สิ่งที่ยังไม่ได้ตรวจ

ข้อที่ร่างฉบับแรกเขียนว่ายังไม่ได้ตรวจ และตอนนี้ตรวจแล้ว: `ortools` ติดตั้งและรันได้กับ Python ของ container (ข้อ 4.2 และ 4.6), เวลาของ CP-SAT เทียบกับการค้นแบบเดิม (ข้อ 4.6), จำนวนไฟล์ที่อ้าง `solver_status` (ข้อ 5), ผลจริงของ PR O, 5, 6 (ข้อ 2)

ที่ยังเหลือ และเหตุผลที่ยังตรวจไม่ได้

* เวลาที่ container ของ Backend และ CI ใช้เพิ่มเมื่อมี `ortools`: การวัดในข้อ 4.6 ติดตั้งลงโฟลเดอร์ชั่วคราวและลบออกแล้ว ไม่ได้จับเวลาการเริ่ม container ต้องแก้ `pyproject.toml` จริงจึงจะวัดได้ ซึ่งเป็นงานของ PR B
* ตัวตัดสินด้วย `staff_id` เมื่อคะแนนเท่ากัน และการคูณสเกลตัวเลข: มีการออกแบบแล้วในข้อ 4.7 และหลักการของขั้นที่ 3 ลองด้วยโค้ดแล้ว แต่โมเดลที่ใช้วัดเวลาในข้อ 4.6 ไม่มีสองเรื่องนี้ จึงยังไม่รู้เวลาของโมเดลจริง ต้องเขียนโมเดลจริงก่อน
* กรณีหมดเวลา 3 วินาที: ยังไม่เคยเกิดในการวัด จึงยังไม่เห็นว่า CP-SAT คืนคำตอบแบบไหนตอนหมดเวลา
* ข้อเสนอจากรีวิว (R2-Q40 ถึง R2-Q42) ตรวจแล้วแค่ว่าโค้ดปัจจุบันเป็นอย่างที่ผู้รีวิวบอก ยังไม่ได้ลองเขียนจริง จึงยังไม่รู้ว่ามีตัวอ่านจุดอื่นนอกจากสี่จุดในข้อ 3.2 ที่ต้องแก้หรือไม่ คนทำ PR T ต้องค้นทุกที่ที่จับคู่ด้วย `candidate_item_id`
* ผลที่อ่านจากโค้ดว่าเกิดเมื่อมีรอบที่สองหรือเวรที่จัดเอง (ข้อ 3.2) ยังไม่ได้รันพิสูจน์ เพราะยังไม่มีโค้ดของสองเส้นทางนั้น
* ใน 54 ไฟล์ Test ที่มีเลข 201 ถึง 203 ยังไม่ได้แยกว่าไฟล์ไหนขึ้นกับลำดับของ Solver จริง การแยกต้องมี Solver ตัวใหม่ที่ให้ลำดับต่างออกไปมารันเทียบ
* คำตอบทุกข้อในไฟล์นี้เป็นของคน 1 คนเดียว ยังไม่ได้ถามคน 2 และคน 3
