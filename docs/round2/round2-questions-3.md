## กลุ่มที่ 2: การจัดคนเองชนกับเคสอื่น

### R2-Q46 Head Nurse จัดคนที่ตอบรับ Offer ของเคสอื่นค้างอยู่ ทำยังไง

**ที่มา:** ตัวตรวจ Hard Rules ดูเวรใน Roster คนที่ตอบรับ Offer แล้วแต่ยังรออนุมัติยังไม่มีแถว Roster ตัวตรวจจึงไม่เห็น และเส้นทางอนุมัติของรอบ 1 ตั้งใจไม่ตรวจ Hard Rules ของผู้สมัครซ้ำตอนสร้างเวร (Q38) ลำดับที่ทำให้พังคือ

1. คน A ตอบรับ Offer ของเวร Y และผ่าน Safety แล้ว
2. ระหว่างที่ Y รออนุมัติ Head Nurse จัด A เข้าเวร X เอง
3. X กับ Y ซ้อนเวลากัน หรือรวมกันแล้วผิดกฎพักหรือกฎชั่วโมง
4. Head Nurse อนุมัติ Y ด้วยผล Safety เดิม

ผลคือ A ได้ทั้งสองเวร เกิดได้ในหอเดียว ไม่ต้องมี Cross-Ward

รอบ 1 มีของที่แก้ปัญหาแบบเดียวกันอยู่แล้วในเส้นทางอนุมัติ คือ `approval_service._cancel_conflicting_offers()` หลังสร้างเวร ระบบตรวจ Offer ของคนเดียวกันในเคสอื่นที่ยัง `SENT` หรือ `ACCEPTED` ถ้าเวรที่เสนอผิดกฎซ้อนเวลา พัก ชั่วโมง หรือเวรติดกันเมื่อเทียบกับ Roster ใหม่ ระบบยกเลิก Offer นั้น แล้วเคสเจ้าของ Offer ถูกคำนวณสถานะใหม่

**ก. ไม่ให้จัด ถ้าคนนั้นมีการตอบรับค้างที่ขัดกับเวรนี้**
- ข้อดี: ง่ายสุด ไม่แตะเคสอื่น คนที่ตอบรับไปแล้วไม่ถูกดึงออก
- ข้อเสีย: Head Nurse ถูกระบบขวางด้วยการตอบรับที่ยังไม่แน่ว่าจะได้อนุมัติ และเคสที่ถึง `MANUAL_HANDOFF` มีคนให้เลือกน้อยอยู่แล้ว

**ข. ให้จัดได้ แล้วยกเลิก Offer ของเคสอื่นที่ขัดกับเวรใหม่ และคำนวณสถานะของเคสเหล่านั้นใหม่ (แนะนำ)**
- ข้อดี: กติกาเดียวกับที่การอนุมัติของรอบ 1 ทำอยู่ การตัดสินของคนชนะ Offer ที่ยังค้าง และใช้ฟังก์ชันที่มีอยู่ได้
- ข้อเสีย: เคสอื่นเสียผู้สมัครที่ตอบรับแล้ว และเส้นทางจัดคนเองต้องล็อกและแตะ Offer ของเคสอื่น จึงต้องรักษาลำดับ Lock ตาม `workflow.md` ข้อ 6.11

**ค. ให้จัดได้ และแสดงคำเตือนให้ Head Nurse ยืนยันก่อน แล้วทำแบบทาง ข**
- ข้อดี: Head Nurse รู้ว่ากำลังดึงคนออกจากเคสอื่น
- ข้อเสีย: หน้าจอและ API ต้องมีขั้นยืนยันเพิ่ม และข้อมูลที่แสดงอาจเก่าไปแล้วตอนกดยืนยัน

**ของที่จะใส่ในร่างไม่ว่าเลือกทางไหน เพราะเป็นข้อกำหนดที่คน 3 ขอ ไม่ใช่ทางเลือก**
- เส้นทางจัดคนเองต้องล็อกแถว `STAFF` ของคนที่ถูกเลือก แม้เขาไม่อยู่ใน Plan และตรวจซ้ำหลังได้ Lock
- เกณฑ์เสร็จของ PR H มี Test สอง Connection สองข้อ: การจัดคนเองแข่งกับการอนุมัติอัตโนมัติของคนเดียวกัน และการจัดคนเองแข่งกับการเปิดเคสใหม่ของเวรเดียวกัน (R2-Q19)

## กลุ่มที่ 3: การติดต่อรอบที่สอง

ข้อเท็จจริงที่จะแก้ในร่างโดยไม่ต้องถาม: ร่างเขียนว่า Offer ใบที่สอง "ไม่ชนเพดาน" ซึ่งผิด การยกเลิก Offer ใบแรกคืนช่องให้ก็จริง แต่เคสอื่นเอาช่องนั้นไปก่อนได้ Offer ใบที่สองจึงต้องผ่านการตรวจเพดานแบบเดียวกับใบแรก ขณะถือ Lock และใช้ข้อมูลปัจจุบัน

### R2-Q47 ถึงคิวรอบที่สองแล้ว แต่คนนั้นติดเพดาน Offer หรือไม่ผ่าน Hard Rules ตอนนั้น นับว่าใช้สิทธิ์ไปแล้วไหม

**ก. ยังไม่ใช้สิทธิ์ สิทธิ์หมดเมื่อ Offer ใบที่สองถูกส่งจริงเท่านั้น (แนะนำ)**
- ข้อดี: ตรงกับวิธีนับที่ R2-Q41 ทาง ก เสนอ คือนับจากจำนวนแถว Offer ไม่มี Offer ก็ไม่มีอะไรให้นับ และคนไม่เสียสิทธิ์เพราะเหตุชั่วคราว
- ข้อเสีย: คนนั้นถูกพิจารณาซ้ำทุกครั้งที่เคสเลือก Wave จนกว่าเคสจะจบ

**ข. ใช้สิทธิ์ไปแล้ว ถึงคิวครั้งเดียว ไม่ผ่านคือหลุด**
- ข้อดี: คิวรอบที่สองเดินจบแน่นอนในรอบเดียว
- ข้อเสีย: ต้องมีที่เก็บว่า "เคยถึงคิวแล้ว" เพราะไม่มีแถว Offer ให้นับ และคนเสียสิทธิ์ทั้งที่ไม่เคยได้ Offer ใบที่สอง

### R2-Q48 "ติดต่อคนที่ยังไม่เคยถูกติดต่อครบแล้ว" นับคนที่ถูกข้ามด้วยไหม

**ที่มา:** `wave_service.select_wave()` ข้ามคนที่ไม่ผ่าน Hard Rules ตอนนั้น หรือติดเพดาน Offer (`OFFER_LIMIT_REACHED`) คนกลุ่มนี้ไม่เคยได้ Offer จึงยังนับว่า "ไม่เคยถูกติดต่อ" ในรอบ 1 คนที่ถูกข้ามไม่ทำให้เคสหยุดรอ ถ้าไม่เหลือใครให้ส่ง เคสไป `MANUAL_HANDOFF` พร้อมรายชื่อคนที่ถูกข้าม

**ก. ไม่นับ คิวรอบที่สองเริ่มเมื่อการเลือก Wave ครั้งนั้นไม่เหลือคนที่ไม่เคยถูกติดต่อและส่ง Offer ได้ (แนะนำ)**
- ข้อดี: ตรงกับรอบ 1 ที่คนถูกข้ามไม่ทำให้เคสรอ เคสไม่ค้างเพราะคนที่อาจไม่ว่างอีกเลย
- ข้อเสีย: คนที่เคยตอบรับแล้วอาจได้ Offer ใบที่สองก่อนคนที่ยังไม่เคยได้โอกาสเพราะติดเพดานชั่วคราว ถ้าคนที่ถูกข้ามกลับมาว่างใน Wave ถัดไป เขายังถูกเลือกก่อนคนรอบที่สองตามเดิม

**ข. นับ คิวรอบที่สองเริ่มเมื่อทุกคนใน Plan เคยได้ Offer แล้วจริง ๆ**
- ข้อดี: ลำดับความยุติธรรมชัด
- ข้อเสีย: เคสไม่มีอะไรให้รอ จึงต้องไป `MANUAL_HANDOFF` ทั้งที่ยังมีคนพร้อมรับรอบที่สอง ซึ่งขัดกับเหตุผลที่เลือก R2-Q29 ข

## กลุ่มที่ 4: Test และเกณฑ์เสร็จ

### R2-Q49 Test ของกรณีหมดเวลาของ Solver ทำแบบไหน

**ที่มา:** ร่างเสนอให้บังคับกรณีหมดเวลาด้วยการส่งเพดานเวลาที่สั้นมาก คน 3 ชี้ว่าเลือกผลไม่ได้ เพดานเดียวกันให้ `OPTIMAL`, `FEASIBLE` หรือ `UNKNOWN` ก็ได้ ขึ้นกับความเร็วของเครื่อง Test บน CI จะผ่านบ้างไม่ผ่านบ้าง

**ก. แยกสองชั้น (แนะนำ)**
- ทำยังไง: ชั้นแรกทดสอบว่าระบบจัดการสถานะแต่ละค่าถูก โดยแทน Solver ด้วยตัวปลอมที่คืนสถานะที่กำหนด ผลแน่นอนทุกครั้ง ชั้นที่สองรัน OR-Tools จริง ตรวจว่าคำตอบที่ได้ครอบคลุม Target ครบ โดยไม่ตรวจว่าได้สถานะไหนที่เพดานเวลาเท่าไหร่
- ข้อดี: Test ไม่ขึ้นกับความเร็วเครื่อง ทุกสถานะถูกทดสอบแน่นอน
- ข้อเสีย: ต้องมีจุดให้สลับ Solver ใน Test ซึ่งเป็นงานออกแบบเพิ่มของคน 2

**ข. คงแบบเดิม ใช้เพดานเวลาที่สั้นมาก**
- ข้อดี: ไม่ต้องมีตัวปลอม
- ข้อเสีย: Test ไม่นิ่ง และคน 3 ขอให้เปลี่ยนแล้ว

### R2-Q50 ขอบเขตเวลาของ Approval Timeout เขียนเป็นสูตรตรง ๆ ไหม

### R2-Q51 เพิ่ม Test ของโจทย์ใหญ่ที่ไม่ต้องใช้การค้นแบบเดิมเป็นเกณฑ์เสร็จของ PR B ไหม

**ข. ไม่เพิ่ม รับความเสี่ยงตามที่เขียนไว้**
