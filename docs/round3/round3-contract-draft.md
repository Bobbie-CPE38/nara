## 2. ขอบเขตรอบ 3

### 2.1 งานของคน 1 (R3-Q1)

ช่องของคน 1 ว่าง ทางเลือกอยู่ที่ R3-Q1 ข้อเสนอคือทำงานค้างใน `docs/workflow.md` ข้อ 12 ที่ไม่ชนกับงานของคน 2 และคน 3:

* ตั้ง Roster เป็น `COMPLETED` เมื่อเวรจบ
* `GET /roster?staff_id=` ตารางเวรของพนักงานหนึ่งคน
* แก้ `end_at` ของ `STAFF_UNAVAILABILITY` (กลับเร็ว, หยุดนานกว่าที่บันทึก) พร้อม Audit `UNAVAILABILITY_UPDATED` ซึ่งค่ามีใน Enum แล้ว
* ธง "อยู่เวรแต่ไม่พร้อม" ใน `GET /roster`

เหตุผล: ทั้งสี่เรื่องอยู่ในงาน Roster และ Event ที่คน 1 ดูแลมาตั้งแต่รอบ 1 ไม่แตะ Solver และ Outreach ที่คน 2 และคน 3 แก้ในรอบนี้

**ตอบแล้ว: R3-Q1 ก** และงาน Deploy บน AWS ทำร่วมกันทั้งสามคน (R3-Q19 ค)

### 2.1.1 สภาพแวดล้อมทดสอบบน AWS (R3-Q12)

* ตอบแล้ว: มีสภาพแวดล้อมทดสอบบน AWS สำหรับทดสอบ LINE จริงร่วมกัน ระหว่างพัฒนาคน 3 ใช้ Tunnel ได้ CI ใช้ Secret ทดสอบ ไม่พึ่ง LINE จริง
* ผู้รับผิดชอบ: ทำร่วมกันทั้งสามคน (R3-Q19 ค) รูปแบบ: เครื่อง EC2 หนึ่งเครื่อง รัน `docker compose` ชุดเดิม พร้อม HTTPS สำหรับ Webhook (R3-Q20 ก) ความลับ: Systems Manager Parameter Store แบบ SecureString (R3-Q21 ก) Backend บน AWS ใช้ IAM Role ไม่ใช้ Access Key ใน env (R3-Q15)
* แบ่งงานใน PR D (ตกลงแล้ว) ทำร่วมกัน แต่มีคนเปิด PR หนึ่งคนเพื่อให้มีคนเริ่มและคนรวบรวม
  * **คน 1 เปิด PR D และดูแลตัวเครื่อง:** EC2, `docker compose` บนเครื่อง, HTTPS, การอ่านความลับจาก Parameter Store ตอนเริ่มเครื่อง, วิธี Deploy และเอกสารวิธีใช้
  * **คน 2 ส่วน Bedrock:** IAM Role ที่ให้ Backend เรียกเฉพาะโมเดลที่ใช้, AWS Budget สำหรับแจ้งเตือน, ตรวจว่าเครดิต AWS ครอบคลุม Bedrock
  * **คน 3 ส่วน LINE:** URL ของ Webhook บนเครื่องนี้, ใส่ Channel secret และ Channel access token ลง Parameter Store, ลองรับ Webhook จริงหนึ่งรอบ
  * **รีวิว:** คน 2 และคน 3 รีวิว PR D ส่วนของตัวเองต้องผ่านการลองจริงของเจ้าของส่วนนั้นก่อน merge

## 3. Contract ของคำอธิบายอันดับ (คน 2)

ของกลางที่ต้องตกลง เพราะหน้าที่แสดงไม่ใช่ของคน 2 คนเดียว

* **ที่มาของตัวเลข (R3-Q2 ก, ตอบแล้ว):**อ่านจาก `input_snapshot` ของ Plan กับ Policy ที่ Plan ชี้ คำนวณคะแนนรายพจน์ตอนอ่าน ไม่มี Migration ตัวเลขจึงเป็นภาพ ณ ตอนวางแผนเสมอ แม้ชั่วโมงทำงานของคนจะเปลี่ยนทีหลัง
* **รูปใน API (R3-Q3 ก, ตอบแล้ว):**เพิ่มช่องในแต่ละ `candidates[]` ของ `GET /cases/{id}` เช่น `score = {total, terms: [{name, value, weight, points}], first_wave, reason_codes}` แทนการเพิ่ม Route ใหม่
* **ข้อความอธิบาย (R3-Q4 ค, R3-Q14 ถึง R3-Q16 ตอบแล้ว):** ประโยคสร้างด้วย LLM โดย Job ครั้งเดียวต่อ Plan และชุดข้อมูลที่ใช้อธิบาย แล้วเก็บลงตาราง หน้าแสดงตัวเลขทันทีและแสดงประโยคเมื่อพร้อม การเปิดหน้าซ้ำและการ Polling ไม่เรียก LLM ใหม่ ผู้ให้บริการคือ Amazon Bedrock แบบ On-demand ผ่านตัวกลางเดียว (`bedrock` และ `fake`) โมเดลยังไม่ล็อก ต้องทดสอบ 20 ถึง 30 เคสก่อนยืนยัน LLM ใช้ไม่ได้ให้แสดงตัวเลขรายพจน์และเหตุผลจากรหัสตายตัว และขึ้นว่า "คำอธิบายยังไม่พร้อม" ห้ามสลับไป `fake` เงียบ ๆ ส่งให้ LLM แค่ตัวเลข เป้าหมาย อันดับ และรหัส ไม่ส่งชื่อพนักงาน LLM ห้ามคำนวณคะแนนใหม่ เปลี่ยนอันดับ หรือตัดสินอะไร ข้อมูลที่ส่งต้องแยก `plan_penalty` (ใช้เลือกกลุ่ม) ออกจาก `ranking_key` (ใช้เรียงใน Plan) การสร้างประโยคไม่ถือ Lock ของ Workflow และไม่ทำให้เคส `FAILED` บันทึกการเรียกทุกครั้ง (token, เวลา, สถานะ, attempt, ค่าใช้จ่ายประมาณ) ค่าตั้งเริ่มต้น `LLM_ENABLED=false`, `LLM_PROVIDER=fake`, เพดาน 1,024 token ต่อคำตอบ, Timeout 15 วินาที, Retry ไม่เกินหนึ่งครั้ง งบทดลอง US$10 ต้องตรวจก่อนว่าเครดิต AWS ครอบคลุม Bedrock รายละเอียดเต็มอยู่ใน R3-Q15
* **หน้าไหนแสดง (R3-Q5 ก, ตอบแล้ว):** หน้า `cases/[id]` อย่างเดียว
* **กติกาที่ต้องยึด:** ใช้ `candidate_penalty()` ตัวเดียว ผลรวมของคะแนนรายพจน์ต้องเท่ากับ `penalty` ที่ Plan เก็บไว้พอดี ถ้าไม่เท่าให้ถือว่าเป็นบั๊ก ไม่ปัดให้ตรง

## 4. Contract ของ LINE จริง (คน 3)

ต่อกับระบบนอกครั้งแรก จึงมีข้อตกลงกลางมากกว่างานอื่น

* **โหมด (R3-Q6 ก, ตอบแล้ว):**มีสองโหมดสลับด้วย env: โหมดจำลอง (ค่าเริ่มต้น, ใช้หน้า `demo/line-sim` ตามเดิม) และโหมด LINE จริง CI และ Test ทั้งหมดรันในโหมดจำลอง
* **ความลับ:** Channel secret และ Channel access token มาจาก env เท่านั้น ห้ามอยู่ใน repo ไฟล์ตัวอย่าง env ใส่แค่ชื่อตัวแปรโดยไม่มีค่า ไม่มีค่าแล้วระบบต้องอยู่โหมดจำลอง ไม่ล่ม
* **การรับคำตอบ (R3-Q7 ก, ตอบแล้ว):** Webhook ตรวจ `X-Line-Signature` (HMAC-SHA256 ของ body ด้วย Channel secret) ก่อนทำอะไร ไม่ผ่านตอบ `401` ไม่เขียน DB แล้วแปลงคำตอบเป็นการเรียก `outreach_service.record_response()` ตัวเดียวกับหน้าจำลอง
* **คำตอบซ้ำ (R3-Q8 ก, ตอบแล้ว):** เก็บรหัส Event ที่ประมวลแล้วในตารางใหม่ ซ้ำแล้วตอบ 200 โดยไม่ทำอะไร ต้องมี Migration
* **ผูกคนกับบัญชี LINE (R3-Q9 ข แบบลดขอบเขต, ตอบแล้ว):** ไม่มีหน้าเว็บ ผู้ดูแลออกรหัสและปลดการผูกผ่านคำสั่ง พนักงานส่ง `LINK <รหัส>` ในแชต รหัสสุ่ม อายุ 10 นาที ใช้ครั้งเดียว เก็บเป็น hash ทั้งระบบอ่าน `CONTACTS.line_uid` ผ่านตัวอ่านตัวเดียว บัญชี LINE ผูกได้กับพนักงานคนเดียว (Unique Constraint) และห้ามเขียนทับบัญชีที่ผูกแล้วอัตโนมัติ รหัสเก็บในตารางใหม่ คน 3 ทำ และมี Audit ของการผูกและการปลด (R3-Q22 ก) ชื่อ Audit Action คือ `LINE_ACCOUNT_LINKED` และ `LINE_ACCOUNT_UNLINKED` (ตกลงแล้ว)
* **ส่ง Offer (R3-Q10, R3-Q17, R3-Q18 ตอบแล้ว):** หลัง Transaction ของ Wave Commit แล้ว ส่งข้อความผ่าน Push API ทันที ส่งไม่สำเร็จให้ Job ส่งซ้ำในรอบถัดไป รวม 3 ครั้ง นับจำนวนครั้งในแถว Offer (Migration) ถ้ายังไม่สำเร็จ ตั้ง Offer เป็น `FAILED` นับเหมือน `TIMEOUT` (ถือว่าติดต่อแล้ว ไม่นับในเพดาน Offer) เขียน Audit ใหม่ `OFFER_DELIVERY_FAILED` แล้วคำนวณสถานะเคสใหม่ เคสต้องไม่เป็น `FAILED` เพราะการส่งข้อความ
* **ตอบหลังเส้นตาย (R3-Q11 ก, ตอบแล้ว):** ใช้กติกาเดิม `clock.now() >= expires_at` ตอบไม่ได้ ระบบตอบกลับใน LINE ว่าหมดเวลา
* **การทดสอบกับ LINE จริง (R3-Q12 ข, ตอบแล้ว):** สภาพแวดล้อมทดสอบบน AWS สำหรับทดสอบร่วมกัน คน 3 ใช้ Tunnel ระหว่างพัฒนา CI ใช้ Secret ทดสอบ (ข้อ 2.1.1)

## 5. จุดที่เสี่ยงพังเงียบ

* **สองทางตอบ Offer:** ถ้า Webhook เขียนการตอบเองแทนการเรียก `record_response()` กติกาเส้นตาย, การพัก Offer และลำดับ Lock จะมีสองที่ และจะเพี้ยนกันโดยไม่มี Error
* **Webhook ซ้ำ:** การตอบรับซ้ำอาจได้ `409` จากกติกาเดิมซึ่งปลอดภัย แต่การปฏิเสธซ้ำหรือคำตอบที่มาถึงสลับลำดับต้องมี Test
* **ความลับหลุด:** Test ที่บันทึก Request จริงหรือ log ที่พิมพ์ Header อาจพาโทเค็นเข้า repo
* **คะแนนไม่ตรงกับที่ Solver ใช้:** ถ้าคำอธิบายคำนวณจากค่าปัจจุบันของคนแทนค่าใน Snapshot ตัวเลขจะไม่ตรงกับอันดับ
* **Clock ของ Demo กับเวลาจริงของ LINE:** ระบบใช้ Clock ที่เลื่อนได้ ส่วน LINE ใช้เวลาจริง ข้อความที่แสดงเส้นตายในแชตต้องใช้เวลาของระบบ และการเลื่อน Clock ใน Demo จะทำให้ข้อความในแชตดูไม่ตรงกับนาฬิกาบนโทรศัพท์

## 8. สิ่งที่ยังไม่ได้ตรวจ

* รายละเอียดของ LINE Messaging API (รูปของ Webhook event, ข้อจำกัดของ Push, ราคา) เขียนจากความรู้ทั่วไป ยังไม่ได้เปิดเอกสารของ LINE ตรวจ คน 3 ต้องตรวจก่อนตอบ R3-Q7, R3-Q8 และ R3-Q10
* ทีมมีบัญชี LINE Official Account หรือ Channel สำหรับทดสอบแล้วหรือยัง ยังไม่รู้
* ค่าใช้จ่ายของ LLM ต่อ Plan ยังไม่รู้ ต้องวัดจากการทดสอบ Bedrock จริง 20 ถึง 30 เคส และยังไม่ได้ตรวจว่าเครดิต AWS ครอบคลุม Bedrock
* ค่าใช้จ่ายของสภาพแวดล้อมทดสอบบน AWS ยังไม่ได้ประเมิน
* `input_snapshot` เก็บ `penalty` เป็นตัวเลขที่แปลงจาก `Fraction` แล้ว ยังไม่ได้ลองว่าผลรวมรายพจน์ที่คำนวณใหม่เท่ากับค่านั้นพอดีหรือมีเศษจากการแปลง
