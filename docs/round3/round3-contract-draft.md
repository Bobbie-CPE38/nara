## 2. ขอบเขตรอบ 3

### 2.1 งานของคน 1 (R3-Q1)

ช่องของคน 1 ว่าง ทางเลือกอยู่ที่ R3-Q1 ข้อเสนอคือทำงานค้างใน `docs/workflow.md` ข้อ 12 ที่ไม่ชนกับงานของคน 2 และคน 3:

* ตั้ง Roster เป็น `COMPLETED` เมื่อเวรจบ
* `GET /roster?staff_id=` ตารางเวรของพนักงานหนึ่งคน
* แก้ `end_at` ของ `STAFF_UNAVAILABILITY` (กลับเร็ว, หยุดนานกว่าที่บันทึก) พร้อม Audit `UNAVAILABILITY_UPDATED` ซึ่งค่ามีใน Enum แล้ว
* ธง "อยู่เวรแต่ไม่พร้อม" ใน `GET /roster`

เหตุผล: ทั้งสี่เรื่องอยู่ในงาน Roster และ Event ที่คน 1 ดูแลมาตั้งแต่รอบ 1 ไม่แตะ Solver และ Outreach ที่คน 2 และคน 3 แก้ในรอบนี้

**ตอบแล้ว: R3-Q1 ก** และงาน Deploy บน AWS ทำร่วมกันทั้งสามคน (R3-Q19 ค)

### 2.1.1 สภาพแวดล้อมทดสอบบน AWS (R3-Q12)

* ตอบแล้ว: มีสภาพแวดล้อมทดสอบบน AWS สำหรับทดสอบ LINE จริงร่วมกัน ระหว่างพัฒนาคน 3 ใช้ Tunnel ได้ CI ใช้ Secret ทดสอบ ไม่พึ่ง LINE จริง
* ผู้รับผิดชอบ: ทำร่วมกันทั้งสามคน (R3-Q19 ค) รูปแบบ: เครื่อง EC2 หนึ่งเครื่อง รัน `docker compose` ชุดเดิม พร้อม HTTPS สำหรับ Webhook (R3-Q20 ก) ความลับ: Systems Manager Parameter Store แบบ SecureString (R3-Q21 ก) Backend บน AWS ใช้ IAM Role ไม่ใช้ Access Key ใน env (R3-Q15)
* แบ่งงานใน PR D (ตกลงแล้ว) ทำร่วมกัน แต่มีคนเปิด PR หนึ่งคนเพื่อให้มีคนเริ่มและคนรวบรวม
  * **คน 1 เปิด PR D และดูแลตัวเครื่อง:** EC2, `docker compose` บนเครื่อง, HTTPS, การอ่านความลับจาก Parameter Store ตอนเริ่มเครื่องแล้วโหลดเข้า env ของ container (แอปอ่านจาก env อย่างเดียว ข้อ 4), วิธี Deploy และเอกสารวิธีใช้
  * **คน 2 ส่วน Bedrock:** IAM Role ที่ให้ Backend เรียกเฉพาะโมเดลที่ใช้, AWS Budget สำหรับแจ้งเตือน, ตรวจว่าเครดิต AWS ครอบคลุม Bedrock
  * **คน 3 ส่วน LINE:** URL ของ Webhook บนเครื่องนี้, ใส่ Channel secret และ Channel access token ลง Parameter Store, เปิด "Webhook redelivery" ใน LINE Developers Console (ค่าเริ่มต้นปิด ข้อ 4), ลองรับ Webhook จริงหนึ่งรอบ
  * **รีวิว:** คน 2 และคน 3 รีวิว PR D ส่วนของตัวเองต้องผ่านการลองจริงของเจ้าของส่วนนั้นก่อน merge

## 3. Contract ของคำอธิบายอันดับ (คน 2)

ของกลางที่ต้องตกลง เพราะหน้าที่แสดงไม่ใช่ของคน 2 คนเดียว

* **ที่มาของตัวเลข (R3-Q2 ก, ตอบแล้ว และแก้ตามรีวิว PR #60):** คำนวณคะแนนรายพจน์ตอนอ่านจาก `input_snapshot` ของ Plan อย่างเดียว ห้ามอ่านค่าน้ำหนักจาก Policy ตอนอ่าน เพราะ Policy ถูกแก้ทับได้ (ข้อ 1) ดังนั้นตอนวางแผน `optimization_service.create_plan()` ต้องเก็บเพิ่มลง Snapshot สองอย่าง
  * `weights`: ค่าน้ำหนักทั้งหกตัวและ `source_order` ที่ใช้วางแผนจริง
  * `penalty_exact`: `penalty` ของแต่ละคนแบบค่าตรง เป็นข้อความ `"เศษ/ส่วน"` จาก `Fraction` ส่วน `penalty` เดิมเก็บไว้ตามเดิมเพื่อไม่ให้ผู้อ่านเดิมพัง
  * Snapshot เป็น `JSONB` การเพิ่ม key จึงไม่ต้องมี Migration ตัวเลขเป็นภาพ ณ ตอนวางแผนเสมอ แม้ชั่วโมงทำงานของคนหรือ Policy จะเปลี่ยนทีหลัง
  * Plan ที่สร้างก่อน PR E ไม่มีสอง key นี้ ให้คืน `score = null` และหน้าแสดงอันดับตามเดิมโดยไม่มีคะแนน ห้ามเดาค่าน้ำหนักจาก Policy ปัจจุบัน
* **รูปใน API (R3-Q3 ก, ตอบแล้ว):** เพิ่มช่องในแต่ละ `candidates[]` ของ `GET /cases/{id}` แทนการเพิ่ม Route ใหม่ รูปคือ `score = {total, terms: [{name, value, weight, points}], first_wave}` หรือ `null` ตามข้อบน
  * `name` ใช้ชื่อเดียวกับค่าน้ำหนักใน `penalties.py`: `candidate_count`, `consecutive_shift`, `workload_imbalance`, `projected_overtime`, `candidate_source` ไม่มี `roster_change` เพราะเป็น 0 ในรอบนี้และไม่ใช่ของรายคน
  * `first_wave` อ่านจาก Snapshot ซึ่งเก็บอยู่แล้ว
  * ตัดช่อง `reason_codes` ที่เคยยกตัวอย่างไว้ออก เพราะไม่มีที่มาใน Snapshot เหตุผลแบบตายตัวสร้างจาก `terms` และ `first_wave` แทน (ข้อถัดไป)
* **ข้อความอธิบาย (R3-Q4 ค, R3-Q14 ถึง R3-Q16 ตอบแล้ว):** ประโยคสร้างด้วย LLM โดย Job ครั้งเดียวต่อ Plan และชุดข้อมูลที่ใช้อธิบาย แล้วเก็บลงตาราง หน้าแสดงตัวเลขทันทีและแสดงประโยคเมื่อพร้อม การเปิดหน้าซ้ำและการ Polling ไม่เรียก LLM ใหม่ ผู้ให้บริการคือ Amazon Bedrock แบบ On-demand ผ่านตัวกลางเดียว (`bedrock` และ `fake`) โมเดลยังไม่ล็อก ต้องทดสอบ 20 ถึง 30 เคสก่อนยืนยัน LLM ใช้ไม่ได้ให้แสดงตัวเลขรายพจน์และเหตุผลแบบตายตัว และขึ้นว่า "คำอธิบายยังไม่พร้อม" ห้ามสลับไป `fake` เงียบ ๆ เหตุผลแบบตายตัวคือข้อความที่หน้าเว็บเขียนไว้คงที่หนึ่งข้อความต่อ `name` ของพจน์ และอีกหนึ่งข้อความตาม `first_wave` (อยู่ในกลุ่มแรก หรือเป็นตัวสำรอง) เรียงพจน์จาก `points` มากไปน้อย ไม่มีข้อมูลใหม่ที่ต้องเก็บ ส่งให้ LLM แค่ตัวเลข เป้าหมาย อันดับ และชื่อพจน์ ไม่ส่งชื่อพนักงาน LLM ห้ามคำนวณคะแนนใหม่ เปลี่ยนอันดับ หรือตัดสินอะไร ข้อมูลที่ส่งต้องแยก `plan_penalty` (ใช้เลือกกลุ่ม) ออกจาก `ranking_key` (ใช้เรียงใน Plan) การสร้างประโยคไม่ถือ Lock ของ Workflow และไม่ทำให้เคส `FAILED` บันทึกการเรียกทุกครั้ง (token, เวลา, สถานะ, attempt, ค่าใช้จ่ายประมาณ) ค่าตั้งเริ่มต้น `LLM_ENABLED=false`, `LLM_PROVIDER=fake`, เพดาน 1,024 token ต่อคำตอบ, Timeout 15 วินาที, Retry ไม่เกินหนึ่งครั้ง งบทดลอง US$10 ต้องตรวจก่อนว่าเครดิต AWS ครอบคลุม Bedrock รายละเอียดเต็มอยู่ใน R3-Q15
* **หน้าไหนแสดง (R3-Q5 ก, ตอบแล้ว):** หน้า `cases/[id]` อย่างเดียว
* **กติกาที่ต้องยึด:** ใช้สูตรของ `candidate_penalty()` ตัวเดียว คำนวณรายพจน์ด้วย `Fraction` จาก `weights` และค่าใน Snapshot แล้วเทียบผลรวมกับ `Fraction(penalty_exact)` แบบเท่ากันพอดี ถ้าไม่เท่าให้ถือว่าเป็นบั๊ก ไม่ปัดให้ตรง การเทียบนี้ทำใน Backend เท่านั้น ห้ามเทียบกับ `penalty` ที่เป็น `float` ตัวเลขที่ส่งออกใน API เป็นค่าสำหรับแสดงผล ส่วน `total` ใช้ค่าเดียวกับ `penalty_exact`

## 4. Contract ของ LINE จริง (คน 3)

ต่อกับระบบนอกครั้งแรก จึงมีข้อตกลงกลางมากกว่างานอื่น

* **โหมด (R3-Q6 ก, ตอบแล้ว):**มีสองโหมดสลับด้วย env: โหมดจำลอง (ค่าเริ่มต้น, ใช้หน้า `demo/line-sim` ตามเดิม) และโหมด LINE จริง CI และ Test ทั้งหมดรันในโหมดจำลอง
* **ความลับ:** แอปอ่าน Channel secret และ Channel access token จาก env เท่านั้น ห้ามอยู่ใน repo ไฟล์ตัวอย่าง env ใส่แค่ชื่อตัวแปรโดยไม่มีค่า ไม่มีค่าแล้วระบบต้องอยู่โหมดจำลอง ไม่ล่ม บนเครื่องทดสอบ AWS ค่าจริงเก็บใน Parameter Store (R3-Q21) และ PR D โหลดเข้า env ตอนเริ่มเครื่อง แอปจึงไม่ต้องรู้จัก Parameter Store
* **การรับคำตอบ (R3-Q7 ก, ตอบแล้ว):** Webhook ตรวจ `x-line-signature` ก่อนทำอะไร **[ตรวจกับเอกสาร LINE]** ลายเซ็นคือ HMAC-SHA256 ของ body ดิบตามที่ได้รับ (ก่อน parse JSON) โดยใช้ Channel secret เป็นกุญแจ แล้วเข้ารหัสแบบ Base64 เทียบแบบ constant-time (`hmac.compare_digest`) ไม่มี Header หรือไม่ตรงให้ตอบ `401` และไม่เขียน DB จากนั้นแปลงคำตอบเป็นการเรียก `outreach_service.record_response()` ตัวเดียวกับหน้าจำลอง
* **คำตอบนี้ของใคร และตอบ Offer ไหน (แก้ตามรีวิว PR #60):** ลายเซ็นยืนยันแค่ว่า LINE เป็นผู้ส่ง ไม่ได้ยืนยันว่าผู้ตอบเป็นเจ้าของ Offer
  * **ตัวพนักงาน:** หาจาก `source.userId` ของ Event ที่ผ่านการตรวจลายเซ็นแล้วเท่านั้น โดยผ่านตัวอ่าน `line_uid` ตัวเดียว และต้องเป็นการผูกที่ยังใช้งาน (`CONTACTS.is_active`) ไม่พบการผูกให้ตอบในแชตว่ายังไม่ได้ผูกบัญชี และไม่เรียก `record_response()`
  * **ตัว Offer:** ข้อความ Offer มีปุ่มแบบ Postback สองปุ่ม (รับ, ปฏิเสธ) ซึ่ง `postback.data` มีแค่ `outreach_id` กับคำตอบ ห้ามมี `staff_id` และถ้ามีก็ห้ามเชื่อ
  * **ความเป็นเจ้าของ:** `record_response(staff_id=..., outreach_id=...)` ตรวจอยู่แล้วว่า Offer เป็นของพนักงานคนนั้น **[ตรวจแล้ว]** (query join `CandidateItem.staff_id`) Webhook ห้ามข้ามการตรวจนี้
  * **ปุ่มเก่า:** ถ้ากดปุ่มของ Offer ที่ถูกแทนที่แล้ว หมดเวลาแล้ว หรือเคสหยุดแล้ว `record_response()` ปฏิเสธด้วย `OpenOfferConflictError` อยู่แล้ว **[ตรวจแล้ว]** (ตัวกันจาก commit `e7e87bb` ตรวจว่า Offer ยังเป็น `SENT` ยังไม่หมดเวลา และเคสยังไม่หยุด) Webhook ตอบในแชตว่า Offer นี้ใช้ไม่ได้แล้ว และไม่เขียนอะไรอีก
  * **ตอบกลับในแชต:** ใช้ Reply API ด้วย `replyToken` ของ Event นั้น **[ตรวจกับเอกสาร LINE]** Reply token ใช้ได้ครั้งเดียว และต้องใช้ภายในประมาณหนึ่งนาที (LINE บอกว่าเวลานี้อาจเปลี่ยน) ถ้าใช้ไม่ได้ ให้บันทึก log และไม่ส่งซ้ำ เพราะผลของการตอบอยู่ใน DB แล้ว
* **คำตอบซ้ำ (R3-Q8 ก, ตอบแล้ว และแก้ตามรีวิว PR #60):** เก็บ `webhookEventId` ที่ประมวลแล้วในตารางใหม่ที่มี Unique Constraint (ต้องมี Migration) **[ตรวจกับเอกสาร LINE]** Event ที่ LINE ส่งซ้ำใช้ `webhookEventId` เดิม และมี `deliveryContext.isRedelivery = true` LINE ไม่รับประกันลำดับของ Event และ Event เดียวกันอาจมาถึงมากกว่าหนึ่งครั้ง กติกาของ Transaction คือ
  * Insert แถวกันซ้ำใน Session เดียวกับการตอบ ก่อนเรียก `record_response()` แล้ว flush แถวนี้จึงถูก Commit พร้อมผลของการตอบใน Commit เดียวกัน **[ตรวจแล้ว]** `record_response()` Commit ผ่าน `orchestrator.recompute()` จึงห้าม Commit แถวกันซ้ำแยกไว้ก่อน
  * ถ้า Insert ชน Unique Constraint (ได้ Event ซ้ำ หรือสอง Request มาพร้อมกันแล้วอีกตัว Commit ไปก่อน) ให้ rollback แล้วตอบ `200` โดยไม่ทำอะไร
  * ถ้าเกิด Error ที่ไม่คาดไว้หรือ `OutreachLockRetryError` ให้ rollback ทั้งก้อน แถวกันซ้ำจึงไม่ถูกเก็บ แล้วตอบ `5xx` ให้ LINE ส่ง Event นั้นใหม่ได้
  * ถ้าเป็นการปฏิเสธทางธุรกิจที่คาดไว้แล้ว เช่น `OpenOfferConflictError` (หมดเวลา, ไม่เป็น `SENT`, เคสหยุด) หรือยังไม่ได้ผูกบัญชี ให้ rollback ผลของการตอบ แล้ว Insert แถวกันซ้ำและ Commit แยก จากนั้นตอบในแชตและตอบ `200` ห้ามตอบ `4xx` หรือ `5xx` เพราะ LINE จะส่งซ้ำโดยไม่มีประโยชน์
  * **[ตรวจกับเอกสาร LINE]** LINE ส่ง Event ซ้ำเฉพาะเมื่อเปิด "Webhook redelivery" ใน LINE Developers Console ซึ่งค่าเริ่มต้นปิดอยู่ คน 3 ต้องเปิดตอนทำส่วน LINE ของ PR D ถ้าไม่เปิด Event ที่ตอบ `5xx` จะหายไป และ LINE ไม่รับประกันว่าจะส่งซ้ำแม้เปิดไว้
* **ผูกคนกับบัญชี LINE (R3-Q9 ข แบบลดขอบเขต, ตอบแล้ว):** ไม่มีหน้าเว็บ ผู้ดูแลออกรหัสและปลดการผูกผ่านคำสั่ง พนักงานส่ง `LINK <รหัส>` ในแชต รหัสสุ่ม อายุ 10 นาที ใช้ครั้งเดียว เก็บเป็น hash ทั้งระบบอ่าน `CONTACTS.line_uid` ผ่านตัวอ่านตัวเดียว บัญชี LINE ผูกได้กับพนักงานคนเดียว (Unique Constraint) และห้ามเขียนทับบัญชีที่ผูกแล้วอัตโนมัติ รหัสเก็บในตารางใหม่ คน 3 ทำ และมี Audit ของการผูกและการปลด (R3-Q22 ก) ชื่อ Audit Action คือ `LINE_ACCOUNT_LINKED` และ `LINE_ACCOUNT_UNLINKED` (ตกลงแล้ว) **การใช้รหัสต้องทำใน Transaction เดียว (แก้ตามรีวิว PR #60):** ตั้งรหัสเป็นใช้แล้วแบบมีเงื่อนไข (ยังไม่ถูกใช้และยังไม่หมดอายุ ตัวเดียวกับที่ล็อกแถว) เขียนการผูก และเขียน Audit แล้ว Commit พร้อมกัน ถ้าส่วนใดพัง ทั้งหมด rollback และรหัสยังใช้ได้ สอง Request ที่ใช้รหัสเดียวกันพร้อมกันต้องสำเร็จได้แค่ตัวเดียว `userId` ของผู้ผูกมาจาก Event ที่ผ่านการตรวจลายเซ็นเท่านั้น
* **ส่ง Offer (R3-Q10, R3-Q17, R3-Q18 ตอบแล้ว และแก้ตามรีวิว PR #60):** ส่งผ่าน Push API ส่งไม่สำเร็จให้ Job ส่งซ้ำ รวม 3 ครั้ง ถ้ายังไม่สำเร็จ ตั้ง Offer เป็น `FAILED` นับเหมือน `TIMEOUT` (ถือว่าติดต่อแล้ว ไม่นับในเพดาน Offer) เขียน Audit ใหม่ `OFFER_DELIVERY_FAILED` แล้วคำนวณสถานะเคสใหม่ เคสต้องไม่เป็น `FAILED` เพราะการส่งข้อความ รายละเอียดที่ทุกคนต้องยึดมีดังนี้
  * **บันทึกงานส่งไว้กับแถว Offer:** แถว Offer ที่ Wave เขียนต้องมีสถานะการส่ง (รอส่ง, LINE รับแล้ว, ส่งไม่สำเร็จ, ยกเลิกการส่ง), จำนวนครั้งที่ส่ง และ Retry key โดยเขียนใน Transaction เดียวกับ Wave (Migration) หลัง Commit แล้วจึงส่งครั้งแรกทันที ถ้าเครื่องล่มหลัง Commit แต่ก่อนส่ง Job จะเห็นแถวที่ยังรอส่งแล้วส่งให้ ไม่มี Offer ที่ไม่ได้ส่งค้างเงียบ
  * **Retry key ตัวเดียวตลอด:** สร้าง UUID หนึ่งค่าต่อ Offer เก็บในแถวก่อนส่งครั้งแรก และส่งใน Header `X-Line-Retry-Key` ทุกครั้ง พร้อมเนื้อหาและผู้รับเหมือนเดิมทุกครั้ง **[ตรวจกับเอกสาร LINE]** Retry key ใช้ได้ 24 ชั่วโมงนับจากครั้งแรก ต้องใส่ตั้งแต่ครั้งแรก ไม่อย่างนั้นส่งซ้ำแบบกันซ้ำไม่ได้
  * **ผลของแต่ละครั้ง:** **[ตรวจกับเอกสาร LINE]** `2xx` แปลว่า LINE รับแล้ว ห้ามส่งซ้ำ `409` ที่มาจาก Retry key แปลว่าครั้งก่อนถูกรับไปแล้ว ให้ถือว่ารับแล้วเหมือน `2xx` ไม่ใช่ส่งไม่สำเร็จ Timeout และ `5xx` ให้ส่งซ้ำ (Timeout อาจเกิดหลัง LINE รับไปแล้ว Retry key จะกันข้อความซ้ำ) `4xx` อื่นแปลว่า Request ผิด ส่งซ้ำแล้วได้ผลเดิม จึงตั้ง Offer เป็น `FAILED` ได้เลยโดยไม่ต้องรอให้ครบ 3 ครั้ง การส่งซ้ำทุกครั้งนับใน Rate limit ของ LINE
  * **ตรวจก่อนส่งซ้ำและก่อนเขียน `FAILED`:** ล็อกแถว แล้วตรวจว่า Offer ยังเป็น `SENT` ยังไม่หมดเวลา และเคสยังไม่หยุด ถ้าไม่ผ่านให้ตั้งสถานะการส่งเป็นยกเลิกการส่ง ห้ามส่งข้อความ Offer ที่ล้าสมัย และห้ามเขียนทับ Offer ที่ถูกรับ ยกเลิก หมดเวลา หรือเคสหยุดแล้วด้วย `FAILED`
  * **LINE รับแล้วไม่ได้แปลว่าคนได้อ่าน:** **[ตรวจกับเอกสาร LINE]** Retry key กันข้อความซ้ำแต่ไม่รับประกันว่าข้อความถึงคน เช่น คนบล็อกบัญชีไว้ LINE ก็ยังตอบรับได้ Offer แบบนั้นจะหมดเวลาตามกติกาเดิม
* **ตอบหลังเส้นตาย (R3-Q11 ก, ตอบแล้ว):** ใช้กติกาเดิม `clock.now() >= expires_at` ตอบไม่ได้ ระบบตอบกลับใน LINE ว่าหมดเวลา (ใช้กติกา Transaction ของการปฏิเสธทางธุรกิจในข้อคำตอบซ้ำ)
* **การทดสอบกับ LINE จริง (R3-Q12 ข, ตอบแล้ว):** สภาพแวดล้อมทดสอบบน AWS สำหรับทดสอบร่วมกัน คน 3 ใช้ Tunnel ระหว่างพัฒนา CI ใช้ Secret ทดสอบ (ข้อ 2.1.1)

### 4.1 หน้าเว็บพยาบาล "ข้อเสนอเข้าเวรของฉัน" (ตกลงแล้ว)

**ที่มา:** การแข่งขันเน้น Native AWS Services ทีมจึงถามผู้จัดว่าใช้ LINE Messaging API ได้ไหม NTT ยืนยันแล้วว่าใช้ได้ งาน LINE ในข้อ 4 จึงเดินตามแผนเดิม ทีมตกลงเพิ่มหน้าเว็บสำหรับพยาบาลเป็นช่องทางเสริม

* **บทบาทของสองช่องทาง:** LINE ใช้รับการแจ้งเตือนและตอบอย่างรวดเร็ว หน้าเว็บใช้ดูรายการ Offer และติดตามสถานะของตัวเอง และตอบจากหน้าเว็บได้ด้วย ทั้งสองช่องทางใช้ข้อมูลและกติกาจาก Backend เดียวกัน
* **ลำดับงาน:** ทำ LINE ตามข้อ 4 ก่อน (PR L และ PR K) แล้วจึงทำหน้าเว็บเป็น PR แยก (PR N ข้อ 6) หน้าเว็บไม่ขวางการส่งมอบงาน LINE
* **สิ่งที่หน้าแสดง:** เฉพาะ Offer ของพยาบาลผู้ใช้งาน ได้แก่ หอผู้ป่วย วันและเวลาเวร เส้นตายในการตอบ ปุ่ม Accept และ Reject เมื่อยังตอบได้ สถานะ (รออนุมัติ, ได้รับมอบหมาย, ถูกปฏิเสธ, ถูกยกเลิก, หมดเวลา) และเหตุผลที่ตอบไม่ได้หรือถูกยกเลิก เช่น กำลังรออนุมัติจากอีกเคสหนึ่ง **[ตรวจแล้ว]** `OfferView` ที่ `outreach_service.list_offers()` คืนมีข้อมูลครบแล้ว: `ward_name`, `shift_start_at`, `shift_end_at`, `expires_at`, `status`, `can_accept`, `can_reject`, `blocked_reason` (`CASE_STOPPED`, `OFFER_EXPIRED`, `AWAITING_OTHER_CASE`), `cancellation_reason`, `is_assigned`, `is_reserve` "รออนุมัติ" คือ `status = ACCEPTED` และ `is_assigned = false`
* **Accept ยังไม่ใช่การยืนยันให้เข้าเวร:** หน้าต้องเขียนให้ชัดว่าพยาบาลได้รับมอบหมายเมื่อ Head Nurse อนุมัติและระบบ Execute สำเร็จแล้วเท่านั้น
* **API สำหรับผู้สมัคร:** Route ใหม่ที่ไม่อยู่ใต้ `/demo` อ่านรายการผ่าน `list_offers()` และตอบผ่าน `outreach_service.record_response()` ตัวเดียวกับ LINE และหน้าจำลอง ไม่สร้างกติกาการตอบชุดที่สอง ตัวพนักงานมาจากตัวตนที่ระบบยืนยันแล้วเท่านั้น Route ไม่รับ `staff_id` จากผู้ใช้ทั้งตอนอ่านและตอนตอบ ส่วนการตรวจว่า Offer เป็นของพนักงานคนนั้น `record_response()` ทำอยู่แล้ว (ข้อ 4) Path ที่เสนอคือ `GET /me/offers` และ `POST /me/offers/{outreach_id}/response` ยืนยันใน PR 0
* **ตัวตนในรอบนี้:** ใช้ตัวตนจำลองเดิม (Header `X-Demo-User`) หน้าและเอกสารต้องเขียนว่าเป็นโหมด Demo และไม่อ้างว่ามีระบบ Login สำหรับใช้งานจริง ระบบ Login จริงอยู่นอกรอบ 3 (ข้อ 2.2)
* **แยกจากหน้าจำลอง:** นำ Component ของ `demo/line-sim` มาใช้ได้ เช่น การ์ด Offer ปุ่มตอบ และข้อความสถานะ แต่หน้าผู้ใช้ไม่มีตัวเลือกสลับพนักงาน และไม่เรียก API ใต้ `/demo/line-sim` **[ตรวจแล้ว]** `GET /demo/line-sim/offers` รับ `staff_id` จาก Query จึงอ่าน Offer ของใครก็ได้ หน้า `demo/line-sim` เดิมใช้ทดสอบต่อตามเดิม
* **ตอบจากหลายช่องทาง:** การตอบผ่าน LINE และหน้าเว็บพร้อมกันกันด้วยกติกาและ Lock ใน `record_response()` ที่มีอยู่ ช่องทางที่ตอบทีหลังได้การปฏิเสธ (`409` บนหน้าเว็บ หรือข้อความในแชตของ LINE) แล้วแสดงสถานะล่าสุด
* **การอัปเดตหน้า:** ในช่วง Demo หน้าอ่านรายการใหม่เป็นระยะ ไม่เพิ่มระบบแจ้งเตือนใหม่ใน PR นี้
* **ข้อดีที่ได้เพิ่ม:** พยาบาลมีที่รวมของ Offer ไม่ต้องย้อนหาในแชต และยังตอบได้แม้การส่งข้อความ LINE บางครั้งไม่สำเร็จ (Offer ยังเป็น `SENT` จนกว่าจะ `FAILED` ตามข้อ 4)

## 5. จุดที่เสี่ยงพังเงียบ

* **สองทางตอบ Offer:** ถ้า Webhook เขียนการตอบเองแทนการเรียก `record_response()` กติกาเส้นตาย, การพัก Offer และลำดับ Lock จะมีสองที่ และจะเพี้ยนกันโดยไม่มี Error
* **Webhook ซ้ำ:** การตอบรับซ้ำอาจได้ `409` จากกติกาเดิมซึ่งปลอดภัย แต่การปฏิเสธซ้ำหรือคำตอบที่มาถึงสลับลำดับต้องมี Test
* **ความลับหลุด:** Test ที่บันทึก Request จริงหรือ log ที่พิมพ์ Header อาจพาโทเค็นเข้า repo
* **คะแนนไม่ตรงกับที่ Solver ใช้:** ถ้าคำอธิบายคำนวณจากค่าปัจจุบันของคนแทนค่าใน Snapshot ตัวเลขจะไม่ตรงกับอันดับ
* **ค่าน้ำหนักจาก Policy ปัจจุบัน:** ถ้าคำอธิบายอ่านค่าน้ำหนักจาก Policy แทน `weights` ใน Snapshot เมื่อ Policy ถูกแก้ (เช่น Seed `ignore_workload()`) ผลรวมรายพจน์ของ Plan เก่าจะไม่เท่ากับ `penalty` โดยไม่มี Error ต้องมี Test ที่แก้ Policy หลังวางแผนแล้วตรวจว่าคะแนนยังเท่าเดิม
* **แถวกันซ้ำของ Webhook Commit แยกจากผลของการตอบ:** ถ้าเก็บก่อนแล้วการตอบพัง คำตอบหายถาวรเพราะ Event ที่ส่งซ้ำถูกทิ้ง ถ้าเก็บหลังแบบแยก Transaction สอง Request พร้อมกันอาจประมวลซ้ำ ต้องมี Test ทั้งสองแบบ
* **หน้าเว็บพยาบาลรับ `staff_id` จากผู้ใช้:** ถ้าหน้าผู้ใช้เรียก `GET /demo/line-sim/offers?staff_id=` หรือ Route ใหม่รับ `staff_id` จาก Query ผู้ใช้จะเห็น Offer ของคนอื่นได้โดยไม่มี Error ต้องมี Test ที่ส่งตัวตนหนึ่งแล้วขอ Offer ของอีกคน
* **ข้อความ Offer ที่ไม่ได้ส่ง หรือส่งช้าเกินไป:** ถ้าเครื่องล่มหลัง Wave Commit แล้วไม่มีงานส่งบันทึกไว้ คนจะไม่ได้รับ Offer และ Offer จะหมดเวลาเอง ถ้าส่งซ้ำโดยไม่ตรวจสถานะก่อน คนจะได้ Offer ที่ใช้ไม่ได้แล้ว
* **Clock ของ Demo กับเวลาจริงของ LINE:** ระบบใช้ Clock ที่เลื่อนได้ ส่วน LINE ใช้เวลาจริง ข้อความที่แสดงเส้นตายในแชตต้องใช้เวลาของระบบ และการเลื่อน Clock ใน Demo จะทำให้ข้อความในแชตดูไม่ตรงกับนาฬิกาบนโทรศัพท์

## 8. สิ่งที่ยังไม่ได้ตรวจ

* **ตรวจกับเอกสาร LINE แล้ว (2026-10-14)** สิ่งที่คำตอบ R3-Q7, R3-Q8 และ R3-Q10 พึ่ง ตรวจแล้วและตรงกับคำตอบ ไม่ต้องเปลี่ยนคำตอบ มีแค่รายละเอียดที่เพิ่มในข้อ 4 จุดที่ตรวจมีดังนี้
  * ลายเซ็นของ Webhook ([Verify webhook signature](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/))
  * `webhookEventId`, `deliveryContext.isRedelivery`, การส่ง Event ซ้ำที่ต้องเปิดเองและไม่รับประกันลำดับ ([Receive messages](https://developers.line.biz/en/docs/messaging-api/receiving-messages/))
  * `X-Line-Retry-Key`, ความหมายของ `409` และ Retry key ไม่รับประกันว่าข้อความถึงคน ([Retry failed API requests](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/))
  * Reply token ใช้ครั้งเดียวภายในประมาณหนึ่งนาที, Push ส่งได้ไม่เกิน 5 ข้อความต่อ Request, รูปของ Postback event ([Messaging API reference](https://developers.line.biz/en/reference/messaging-api/))
* ยังไม่ได้ตรวจกับเอกสารของ LINE: ความยาวสูงสุดของ `postback.data` (แหล่งรองบอก 300 ตัวอักษร ข้อมูลที่ใช้สั้นกว่านั้นมาก), ตัวเลขของ Rate limit และโควตาข้อความรายเดือนของ Push คน 3 ตรวจตอนทำ PR L
* ทีมมีบัญชี LINE Official Account หรือ Channel สำหรับทดสอบแล้วหรือยัง ยังไม่รู้
* ค่าใช้จ่ายของ LLM ต่อ Plan ยังไม่รู้ ต้องวัดจากการทดสอบ Bedrock จริง 20 ถึง 30 เคส และยังไม่ได้ตรวจว่าเครดิต AWS ครอบคลุม Bedrock
* ค่าใช้จ่ายของสภาพแวดล้อมทดสอบบน AWS ยังไม่ได้ประเมิน
* ปิดแล้วตามรีวิว PR #60: เรื่อง `penalty` ใน Snapshot เป็น `float` ที่แปลงจาก `Fraction` ตอนนี้เทียบกับ `penalty_exact` แบบ `Fraction` แทน `float` (ข้อ 3) จึงไม่มีเศษจากการแปลง
