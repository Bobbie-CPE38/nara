## กลุ่มที่ 1: จัดงานของรอบ

### R3-Q1 รอบ 3 คน 1 ทำอะไร

**ที่มา:** ช่องของคน 1 ในรอบ 3 ว่าง เพราะงานเดิม (การจัดการเคสหลัง `MANUAL_HANDOFF`) ย้ายไปทำในรอบ 2 แล้ว งานของคน 1 ที่เหลือในตารางคือ LangGraph (รอบ 5) และ LLM สรุปสถานการณ์ (รอบ 6)

**ก. งานค้างใน `workflow.md` ข้อ 12 ฝั่ง Roster และ Event (แนะนำ)**
- ทำอะไร: ตั้ง Roster เป็น `COMPLETED`, `GET /roster?staff_id=`, แก้ `end_at` ของการลา, ธง "อยู่เวรแต่ไม่พร้อม"
- ข้อดี: เป็นงานในส่วนที่คน 1 ดูแลอยู่แล้ว ไม่ชนไฟล์กับคน 2 และคน 3 ในรอบนี้ และปิดช่องที่ทำให้ข้อมูล Demo ไม่สมจริง (เวรที่จบแล้วยังเป็น `ASSIGNED`)
- ข้อเสีย: เป็นงานเล็กหลายชิ้น ไม่ใช่ฟีเจอร์ใหญ่ที่เห็นชัดในการนำเสนอ

**ข. ดึง LangGraph ของรอบ 5 มาทำก่อน**
- ข้อดี: งานใหญ่ของคน 1 เสร็จเร็ว
- ข้อเสีย: `next-move.md` เตือนไว้ว่า LangGraph แตะ `orchestrator.py` ที่ทุก Handler พึ่ง ควรทำตอนคนอื่นไม่ได้แก้ Handler แต่รอบ 3 คน 3 ต้องแก้เส้นทางส่ง Offer และคำตอบ จึงชนกัน

**ค. ช่วยงาน LINE ของคน 3**
- ทำอะไร: เช่น หน้าจัดการ `CONTACTS` (ผูกพนักงานกับบัญชี LINE) หรือโหมดสลับระหว่างจำลองกับของจริง
- ข้อดี: LINE เป็นงานเสี่ยงสุดของรอบ มีคนช่วยตรวจ
- ข้อเสีย: สองคนแก้ส่วนเดียวกัน ขัดกับหลัก "รายละเอียดข้างในแต่ละคนออกแบบเอง"

**ง. ดึง `NO_SHOW` ของรอบ 5 (คน 2) มาทำ**
- ข้อดี: เป็นเส้นทางรับ Event แบบใหม่ ซึ่งคน 1 ทำมาตั้งแต่รอบ 1
- ข้อเสีย: ต้องตกลงกับคน 2 ว่าย้ายงานจากเขา และต้องมีข้อมูล check-in ใน `ATTENDANCE` ซึ่งยังไม่มีเส้นทางเขียน

**ที่มา:** รอบ 2 ใช้ PR เอกสาร → PR 0 → PR งาน เข้า `staging` ตรง ไม่มี Branch รวม และคำตอบเป็นการตัดสินใจร่วมกัน

**ข. ข้าม PR 0 ให้ PR เอกสารเขียน `workflow.md` เลย**
- ข้อดี: ลด PR หนึ่งตัว
- ข้อเสีย: รีวิวเอกสารกับรีวิวการแก้ Contract ปนกัน รอบ 2 แยกไว้เพราะเหตุนี้

## กลุ่มที่ 2: คำอธิบายอันดับ (คน 2)

### R3-Q2 ตัวเลขของคำอธิบายมาจากไหน

**ที่มา:** Plan เก็บค่าต่อคนไว้ใน `input_snapshot` แล้ว (ชั่วโมงสัปดาห์นี้, เวรติดกัน, OT, แหล่งที่มา, `penalty`, อยู่ใน Wave แรกไหม) และชี้ไป Policy ที่ใช้

**ก. คำนวณตอนอ่าน จาก `input_snapshot` กับ Policy ที่ Plan ชี้ (แนะนำ)**
- ข้อดี: ไม่มี Migration ตัวเลขตรงกับที่ Solver ใช้จริง ณ ตอนวางแผน
- ข้อเสีย: ทุกครั้งที่อ่านต้องคำนวณใหม่ (เล็กน้อย) และถ้า `input_snapshot` ขาดค่าใดของ Plan เก่า ต้องรองรับกรณีนั้น

**ข. เก็บคะแนนรายพจน์ลงตารางตอนวางแผน**
- ข้อดี: อ่านง่าย Query ได้
- ข้อเสีย: ต้องมี Migration เก็บข้อมูลซ้ำกับ `input_snapshot` และต้องแก้ `create_plan()` ซึ่งเพิ่งเปลี่ยนใน PR B

**ค. คำนวณจากค่าปัจจุบันของพนักงาน**
- ข้อดี: ไม่ต้องอ่าน Snapshot
- ข้อเสีย: ตัวเลขไม่ตรงกับที่ทำให้ได้อันดับนั้น ถ้าชั่วโมงทำงานเปลี่ยนหลังวางแผน คำอธิบายจะผิด

---

### R3-Q3 คำอธิบายอยู่ตรงไหนใน API

**ก. ช่องใหม่ในแต่ละ `candidates[]` ของ `GET /cases/{id}` (แนะนำ)**
- ข้อดี: หน้าเคสอ่านครั้งเดียวได้ครบ ไม่มี Route ใหม่
- ข้อเสีย: คำตอบของ `GET /cases/{id}` ใหญ่ขึ้น และหน้า `approvals` ที่อ่าน Route นี้อยู่แล้วต้องรับช่องใหม่ (ไม่พัง เพราะเป็นช่องเพิ่ม)

**ข. Route ใหม่ เช่น `GET /cases/{id}/ranking`**
- ข้อดี: แยกชัด โหลดเมื่อเปิดดูเท่านั้น
- ข้อเสีย: หน้าเว็บเรียกสองครั้ง และต้องตกลง Path ใหม่

---

### R3-Q4 คำอธิบายมีแค่ตัวเลข หรือมีประโยคด้วย

**ก. ตัวเลขรายพจน์ บวกเหตุผลสั้นจากรหัสตายตัว (แนะนำ)**
- ตัวอย่าง: "Wave แรก: เติม Skill ICU", "อันดับต่ำกว่าเพราะชั่วโมงสัปดาห์นี้ 40 ชม."
- ข้อดี: คนอ่านเข้าใจโดยไม่ต้องรู้สูตร ข้อความแปลได้ในหน้าเว็บเพราะ API ส่งรหัส ไม่ต้องใช้ LLM
- ข้อเสีย: ต้องตกลงชุดรหัสเหตุผล

**ข. ตัวเลขอย่างเดียว**
- ข้อดี: งานน้อยสุด
- ข้อเสีย: Head Nurse ต้องรู้สูตรจึงจะอ่านออก

**ค. ประโยคจาก LLM**
- ข้อดี: อ่านเป็นธรรมชาติ
- ข้อเสีย: LLM อยู่รอบ 6 และทีมยังไม่ได้เลือกว่าจะทำ

---

### R3-Q5 หน้าไหนแสดงคำอธิบาย

**ก. หน้า `cases/[id]` อย่างเดียว (แนะนำ)**
- ข้อดี: เป็นหน้าของคน 2 เอง งานไม่ข้ามคน
- ข้อเสีย: ผู้อนุมัติต้องกดเข้าหน้าเคสจึงจะเห็นว่าทำไมคนนี้ได้อันดับนั้น

**ข. หน้า `cases/[id]` และหน้า `approvals`**
- ข้อดี: ผู้อนุมัติเห็นเหตุผลตอนตัดสิน
- ข้อเสีย: หน้า `approvals` เป็นของคน 1 ต้องมี PR ของคน 1 เพิ่ม

## กลุ่มที่ 3: LINE จริง (คน 3)

### R3-Q6 LINE จริงแทนหน้าจำลอง หรืออยู่คู่กัน

**ก. สองโหมดสลับด้วย env ค่าเริ่มต้นเป็นโหมดจำลอง (แนะนำ)**
- ข้อดี: CI, Test และ Demo ที่ไม่มีอินเทอร์เน็ตยังใช้ได้ ไม่มีความลับก็รันได้ หน้า `demo/line-sim` ยังใช้ทดสอบได้
- ข้อเสีย: มีสองเส้นทางส่ง Offer ต้องดูแลทั้งคู่

**ข. LINE จริงอย่างเดียว เลิกใช้หน้าจำลอง**
- ข้อดี: โค้ดน้อยกว่า
- ข้อเสีย: ทุกคนต้องมีบัญชี LINE และ Channel ทดสอบ CI ต้องจำลอง LINE เอง และ Demo พึ่งอินเทอร์เน็ต

### R3-Q7 Webhook ประมวลคำตอบยังไง

**ก. ตรวจ Signature แล้วเรียก `outreach_service.record_response()` ตัวเดียวกับหน้าจำลอง ใน Request เดียวกัน (แนะนำ)**
- ข้อดี: กติกาเส้นตาย, การพัก Offer และลำดับ Lock มีที่เดียว Test เดิมของการตอบ Offer ใช้ได้ต่อ
- ข้อเสีย: LINE ต้องได้คำตอบเร็ว ถ้าการตอบรับพาไปตรวจ Safety และสร้างคำขออนุมัติใน Request เดียวกัน อาจช้า ต้องวัด

**ข. รับ Webhook แล้วเก็บลงคิว ให้ Job ประมวลทีหลัง**
- ข้อดี: ตอบ LINE เร็วเสมอ
- ข้อเสีย: ต้องมีตารางคิวและ Job งานใหม่ และผู้สมัครไม่ได้รู้ผลทันที

---

### R3-Q8 กัน Webhook ที่ LINE ส่งซ้ำยังไง

**ที่มา:** LINE ส่ง Webhook เดิมซ้ำได้เมื่อไม่ได้คำตอบทันเวลา แต่ละ Event มีรหัสของตัวเอง

**ก. เก็บรหัส Event ที่ประมวลแล้วในตารางใหม่ ซ้ำแล้วตอบ 200 โดยไม่ทำอะไร (แนะนำ)**
- ข้อดี: กันซ้ำได้แน่นอนทุกชนิดของ Event
- ข้อเสีย: มี Migration หนึ่งตัว

**ข. พึ่งกติกาเดิม: ตอบรับซ้ำได้ `409` อยู่แล้ว**
- ข้อดี: ไม่มี Migration
- ข้อเสีย: ใช้ได้กับการตอบรับ แต่การปฏิเสธที่ถูกส่งซ้ำ หรือ Event ชนิดอื่นในอนาคต ไม่มีอะไรกัน และผู้สมัครอาจได้ข้อความ Error ทั้งที่ตอบไปถูกแล้ว

---

### R3-Q9 ผูกพนักงานกับบัญชี LINE ยังไง

**ที่มา:** `CONTACTS.line_uid` มีคอลัมน์แล้วแต่ไม่มีแถวไหนและไม่มีโค้ดอ่าน LINE ให้ `userId` ที่ต่างกันไปตาม Provider จึงต้องได้จากการที่ผู้ใช้คุยกับบัญชีของเราก่อน

**ก. ผู้ดูแลใส่ `line_uid` เองผ่าน Seed หรือคำสั่ง (แนะนำสำหรับรอบ 3)**
- ข้อดี: งานน้อย พอสำหรับ Demo ที่มีคนไม่กี่คน
- ข้อเสีย: ใช้จริงไม่ได้ ต้องรู้ `userId` ของแต่ละคนเอง

**ข. ผู้ใช้ส่งรหัสยืนยันในแชต ระบบผูกเอง**
- ข้อดี: ใช้ได้จริง
- ข้อเสีย: งานเพิ่มทั้งการออกรหัส การหมดอายุ และหน้าจอ

---

### R3-Q10 ส่ง Offer ทาง LINE ไม่สำเร็จ ทำยังไง

**ก. Offer ยังเป็น `SENT` บันทึก log และ Audit ว่าส่งไม่สำเร็จ ไม่ย้อน ไม่ทำให้เคส `FAILED` (แนะนำ)**
- ข้อดี: ตรงกับกติกาเดิมที่ว่าการแจ้งหลัง Commit พังต้องไม่ทำให้งานที่ Commit แล้วกลายเป็นพัง ผู้สมัครที่ไม่ได้ข้อความจะหมดเวลาเองใน 300 วินาที เคสเดินต่อ
- ข้อเสีย: เสียเวลา 300 วินาทีของคนนั้น

**ข. ตั้ง Offer เป็น `FAILED` ทันที (ค่ามีใน Enum แล้ว) แล้วให้เคสคำนวณใหม่**
- ข้อดี: เคสหาคนถัดไปทันที
- ข้อเสีย: ต้องเพิ่มเส้นทางเขียน `FAILED` และกติกาว่า Offer ที่ `FAILED` นับยังไงในเพดานและในการติดต่อซ้ำ

---

### R3-Q11 ผู้สมัครตอบใน LINE หลังเส้นตาย

**ก. ใช้กติกาเดิม ตอบไม่ได้ แล้วตอบกลับในแชตว่าหมดเวลา (แนะนำ)**
- ข้อดี: กติกาเดียวกับหน้าจำลอง ผู้สมัครรู้ผล
- ข้อเสีย: ต้องใช้ Reply API ซึ่งมีเงื่อนไขเวลาของ reply token

**ข. ไม่ตอบกลับ**
- ข้อดี: งานน้อย
- ข้อเสีย: ผู้สมัครไม่รู้ว่าคำตอบไม่ถูกนับ

---

### R3-Q12 ทดสอบกับ LINE จริงยังไง

**ที่มา:** Webhook ต้องมี URL สาธารณะแบบ HTTPS เครื่องพัฒนาไม่มี

**ก. CI ทดสอบด้วย Request ที่เซ็นด้วย Secret ทดสอบ ส่วนการลองกับ LINE จริงใช้ Tunnel บนเครื่องคน 3 (แนะนำ)**
- ข้อดี: CI ไม่ต้องพึ่งอินเทอร์เน็ตและไม่ต้องมีความลับจริง
- ข้อเสีย: การลองจริงทำได้บนเครื่องเดียว และต้องเขียนวิธีตั้ง Tunnel ไว้

**ข. Deploy เครื่องทดสอบสาธารณะ**
- ข้อดี: ทุกคนลองได้
- ข้อเสีย: เกินขอบเขตของโปรเจกต์ตอนนี้ และต้องดูแลความลับบนเครื่องนั้น

### R3-Q14 ประโยคจาก LLM สร้างเมื่อไหร่ และเก็บไหม

**ที่มา:** R3-Q4 เลือกประโยคจาก LLM การเรียก LLM ใช้เวลาหลายวินาทีและมีค่าใช้จ่ายต่อครั้ง ส่วนหน้า `cases/[id]` อ่าน `GET /cases/{id}` ซ้ำทุก 2 วินาที

**ก. สร้างครั้งเดียวหลัง Plan ถูก Commit โดย Job แล้วเก็บลงตาราง หน้าแสดงตัวเลขทันที และแสดงประโยคเมื่อพร้อม (แนะนำ)**
- ข้อดี: เรียก LLM ครั้งเดียวต่อ Plan ไม่ถือ Lock ของการวางแผน ไม่ทำให้ Request ไหนช้า ประโยคไม่เปลี่ยนทุกครั้งที่เปิดหน้า
- ข้อเสีย: ต้องมี Migration ตารางเก็บประโยค และงานใหม่ใน Job

**ข. สร้างตอนอ่าน แล้วเก็บไว้ใน Cache ชั่วคราว**
- ข้อดี: ไม่มี Migration
- ข้อเสีย: การอ่านครั้งแรกช้า Cache หายเมื่อ Backend เริ่มใหม่ และหน้าเว็บที่อ่านซ้ำทุก 2 วินาทีอาจเรียก LLM ซ้ำระหว่างที่ครั้งแรกยังไม่เสร็จ

**ค. สร้างเมื่อผู้ใช้กดปุ่ม "อธิบาย" เท่านั้น**
- ข้อดี: เรียก LLM เฉพาะเมื่อมีคนต้องการ
- ข้อเสีย: ผู้ใช้ต้องรอหลายวินาทีหลังกด และต้องเพิ่ม Route กับปุ่ม

### R3-Q15 ใช้ LLM ของผู้ให้บริการไหน และเก็บความลับยังไง

**ก. เรียกผ่านตัวกลางตัวเดียวในโค้ด เลือกผู้ให้บริการด้วย env และมีตัวปลอมสำหรับ CI และเครื่องที่ไม่มีความลับ (แนะนำ)**

### R3-Q16 LLM ใช้ไม่ได้ หรือข้อมูลอะไรส่งให้ LLM ได้

**ข. LLM ใช้ไม่ได้ให้แสดงตัวเลขอย่างเดียว และส่งชื่อพนักงานได้**
- ข้อดี: ประโยคอ่านเป็นธรรมชาติกว่า งานน้อยกว่า
- ข้อเสีย: ชื่อพนักงานออกไปยังผู้ให้บริการภายนอก และเมื่อ LLM ล่ม Head Nurse เห็นแค่ตัวเลข

- ข้อดี: ไม่มี Migration ได้ผลเร็ว
- ข้อเสีย: Request ที่ทำให้เกิด Wave ช้าลงเมื่อ LINE มีปัญหา และถ้า Backend ล่มระหว่างนั้น จำนวนครั้งหาย

### R3-Q18 Offer ที่ `FAILED` นับยังไง

**ที่มา:** ค่า `FAILED` มีใน Enum และหน้าเคสมีสถานะ `OFFER_FAILED` แล้ว แต่ยังไม่มีโค้ดเขียน

**ก. นับเหมือน Offer ที่ `TIMEOUT`: ถือว่าเคสนี้ติดต่อคนนั้นแล้ว ไม่ส่งซ้ำในเคสเดียวกัน ไม่นับในเพดาน Offer และเขียน Audit ใหม่ `OFFER_DELIVERY_FAILED` (แนะนำ)**
- ข้อดี: ใช้กติกาที่มีอยู่ เคสหาคนถัดไปได้ทันที
- ข้อเสีย: คนที่ส่งไม่ถึงเพราะเหตุชั่วคราวเสียสิทธิ์ในเคสนั้น

**ข. ให้กลับไปต่อท้ายคิวได้หนึ่งครั้ง เหมือนคำขออนุมัติที่หมดเวลา**
- ข้อดี: ไม่เสียผู้สมัครเพราะปัญหาของระบบส่งข้อความ
- ข้อเสีย: ต้องขยายกติกาการกลับเข้าคิวของรอบ 2 ซึ่งตอนนี้ผูกกับคำขออนุมัติที่หมดเวลาเท่านั้น

### R3-Q15 คำตอบฉบับเต็ม

เลือก **ก. เรียก LLM ผ่านตัวกลางเดียวใน Backend เลือกผู้ให้บริการและโมเดลผ่าน config และมีตัวปลอมสำหรับ CI**

ผู้ให้บริการจริงในรอบ 3 คือ **Amazon Bedrock แบบ On-demand** โดยต้องตรวจสิทธิ์ใช้เครดิตและทดสอบโมเดลก่อนเปิดใช้งานจริง

**1. ผู้ให้บริการและโมเดล**

ใช้ Amazon Bedrock On-demand เพราะโปรเจกต์มีแผน Deploy บน AWS อยู่แล้ว ทีมไม่ต้องดูแลเครื่องรันโมเดลเอง และสามารถให้สิทธิ์ Backend ผ่าน IAM Role ได้

Bedrock เป็นบริการเรียกโมเดล ไม่ใช่ชื่อโมเดล ดังนั้นต้องระบุ `LLM_MODEL_ID` และ `AWS_REGION` ให้ชัดเจนก่อนใช้งานจริง โดยเลือกจากผลทดสอบ:

- อธิบายคะแนนและข้อมูลผู้สมัครเป็นภาษาไทยได้ถูกต้อง
- ไม่แต่งตัวเลขหรือเหตุผลที่ไม่มีในข้อมูล
- ตอบตามรูปแบบที่ Backend ต้องการ
- ความเร็วและค่าใช้จ่ายเหมาะกับ Demo

ยังไม่ล็อกชื่อโมเดลในคำตอบนี้ ให้ทดสอบกับชุดข้อมูลของระบบก่อน แล้วบันทึกรุ่นที่เลือกไว้ใน config และผลการเรียกทุกครั้ง

**2. เครดิต AWS**

ต้องตรวจว่าเครดิตจากการแข่งขันครอบคลุม Bedrock และโมเดลที่จะใช้หรือไม่ โดยดู **Billing → Credits → Applicable products** ของเครดิตนั้น ไม่ถือว่าเครดิต US$350 ใช้ได้กับทุกบริการโดยอัตโนมัติ [เอกสารเครดิต AWS](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/useconsolidatedbilling-credits.html)

ค่าใช้จ่าย LLM เป็นส่วนหนึ่งของงบ AWS ทั้งหมด ต้องแบ่งงบให้ Backend ฐานข้อมูลและบริการอื่นด้วย

**3. ตัวกลาง LLM ใน Backend**

ให้โค้ดส่วนสร้างคำอธิบายเรียกผ่านตัวกลางเดียว เช่น `llm_service.generate_explanation()` ไม่เรียก AWS SDK กระจายตาม Route หรือ Service ต่าง ๆ

ตัวกลางรับข้อมูลที่เตรียมแล้ว และคืนผลรูปแบบเดียวกัน:

- ข้อความคำอธิบาย
- provider และ model ที่ใช้
- จำนวน token
- ระยะเวลาที่ใช้
- สถานะผลลัพธ์

รอบ 3 ทำตัวเชื่อมสองแบบ:

| ตัวเชื่อม | ใช้เมื่อ |
|---|---|
| `bedrock` | ทดสอบจริงและระบบบน AWS |
| `fake` | CI และการพัฒนาแบบไม่เรียกโมเดลจริง |

ตัวปลอมต้องให้ผลคงที่เพื่อทดสอบได้ ไม่ต้องมี credential และไม่เรียกอินเทอร์เน็ต

การมีตัวกลางทำให้เปลี่ยนผู้ให้บริการภายหลังได้โดยไม่ต้องแก้ทุกจุดที่ใช้คำอธิบาย แต่ผู้ให้บริการใหม่ยังต้องมีตัวเชื่อมของตัวเอง ไม่ใช่เปลี่ยน env แล้วรองรับได้ทันทีโดยไม่มีโค้ด

**4. หน้าที่ของ LLM**

LLM ใช้เรียบเรียงคำอธิบายจากข้อมูลที่ Backend คำนวณไว้แล้ว ได้แก่:

- คะแนนรายพจน์และน้ำหนัก
- เป้าหมาย Headcount, Role และ Skill ที่ผู้สมัครเติม
- กลุ่มผู้สมัครที่ Solver เลือก
- อันดับและข้อมูลที่ใช้เรียงผู้สมัคร

LLM ไม่มีสิทธิ์คำนวณคะแนนใหม่ เปลี่ยนอันดับ เปลี่ยนผล Hard Rules หรือ Safety เลือกผู้สมัคร อนุมัติ หรือสร้างเวร

ข้อมูลที่ส่งให้ต้องแยกให้ชัดว่า:

- `plan_penalty` ใช้ตัดสินการเลือกกลุ่ม
- `ranking_key` ใช้เรียงผู้สมัครภายใน Plan

ไม่ให้ LLM เดาเหตุผลจากคะแนนรวมอย่างเดียว เช่น อ้างว่าผู้สมัครอันดับต่ำกว่าเพราะชั่วโมงทำงาน ทั้งที่ลำดับจริงถูกตัดสินด้วยพจน์อื่นก่อน

ตัวเลขและอันดับที่แสดงบนหน้าเว็บต้องอ่านจาก Backend โดยตรง ส่วนข้อความจาก LLM เป็นคำอธิบายประกอบ

**5. การเก็บความลับและสิทธิ์ AWS**

บน AWS ให้ใช้ **IAM Role ของบริการที่รัน Backend** พร้อมสิทธิ์เฉพาะการเรียกโมเดลที่จำเป็น AWS SDK รับ temporary credentials จาก Role ไม่ฝัง Access Key ลงในโค้ดหรือ image [เอกสาร AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_use-resources.html)

บนเครื่องพัฒนาให้ใช้ AWS profile และ temporary credentials ตามวิธีที่ทีมกำหนด

กติกาที่ใช้ร่วมกัน:

- ห้าม commit credential ลง repo
- `.env.example` มีเฉพาะชื่อ config และค่าตัวอย่าง
- ไม่ส่ง credential ไป Frontend
- ไม่ใช้ตัวแปร `NEXT_PUBLIC_*` สำหรับความลับ
- ไม่บันทึก credential ลง log
- CI ไม่ใช้ credential จริง

Provider, model, Region และค่าควบคุมอ่านจาก env ส่วน credential บน AWS อ่านผ่าน IAM Role ไม่ต้องคัดลอก Access Key มาใส่ env

**6. Config และเพดานเริ่มต้น**

เสนอค่าเริ่มต้นดังนี้:

| Config | ค่าเริ่มต้น | ความหมาย |
|---|---:|---|
| `LLM_ENABLED` | `false` | ต้องเปิดใช้งานอย่างชัดเจน |
| `LLM_PROVIDER` | `fake` | CI และเครื่องที่ไม่ได้ตั้งค่าใช้งานจริง |
| `LLM_MODEL_ID` | กำหนดหลังทดสอบ | รุ่นโมเดลที่ใช้จริง |
| `AWS_REGION` | กำหนดตาม Deployment | Region ที่รองรับโมเดลที่เลือก |
| `LLM_MAX_OUTPUT_TOKENS` | `1024` | เพดานคำตอบต่อครั้ง |
| `LLM_REQUEST_TIMEOUT_SECONDS` | `15` | Timeout ฝั่ง client ต่อ attempt |
| `LLM_MAX_RETRIES` | `1` | Retry เพิ่มได้สูงสุดหนึ่งครั้ง |

Bedrock Converse มี `maxTokens` สำหรับจำกัดคำตอบจริง ไม่พึ่งเพียง prompt ว่า “ตอบสั้น” ค่า 1,024 เป็นเพดาน ไม่ใช่ปริมาณที่จะใช้ทุกครั้ง และ token ไม่เท่ากับจำนวนคำหรือตัวอักษรภาษาไทย [เอกสาร Bedrock](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_InferenceConfiguration.html)

ต้องจำกัด input ด้วย โดยกำหนดเพดานหลังเลือกโมเดลและวัดตัวอย่างเคส ส่งเฉพาะข้อมูลที่จำเป็น ไม่ส่ง Audit ทั้งหมดหรือประวัติสนทนาสะสม

Timeout ฝั่ง client ไม่ใช่ตัวรับประกันว่าไม่มีค่าใช้จ่าย หากคำขอไปถึงบริการแล้วแต่ client ไม่ได้รับคำตอบ การเรียกนั้นอาจยังมีค่าใช้จ่าย จึงต้องจำกัด retry และตรวจยอดใช้งานประกอบ

**7. จังหวะเรียกและการใช้ผลซ้ำ**

เสนอให้สร้างคำอธิบายหนึ่งครั้งต่อ **Plan รุ่นหนึ่งและชุดข้อมูลที่ใช้อธิบาย** แล้วเก็บผลไว้

- เปิดหน้าเคสหรือ refresh ไม่เรียกใหม่
- การ polling ไม่ทำให้เรียก LLM ซ้ำ
- ถ้างานเดียวกันกำลังรัน ให้คำขออื่นรอหรือใช้สถานะของงานเดิม
- สร้างคำอธิบายใหม่เมื่อข้อมูลที่เกี่ยวข้องหรือรุ่น prompt เปลี่ยน
- ใช้ข้อมูล snapshot ที่ผูกกับคำอธิบายนั้น เพื่อไม่ให้ข้อความเก่าปะปนกับตัวเลขใหม่

หากรายชื่อผู้สมัครมากเกินขอบเขต input/output ให้แสดงรายละเอียดตัวเลขครบ และจำกัดส่วนคำอธิบายตามขอบเขตที่ทีมกำหนด ไม่เพิ่มเพดาน token หรือแบ่งเรียกหลายครั้งโดยอัตโนมัติ

Retry เฉพาะข้อผิดพลาดชั่วคราว ไม่ retry กรณี credential ผิด config ผิด หรือคำตอบถูกตัดเพราะถึงเพดาน และต้องตั้ง SDK ให้จำนวน attempt รวมไม่เกินสองครั้งตามกติกานี้

**8. เมื่อสร้างคำอธิบายไม่ได้**

Workflow จัดเวรต้องดำเนินต่อได้ เพราะ LLM เป็นส่วนอธิบายผล ไม่ใช่ตัวตัดสินความปลอดภัย

เมื่อ timeout, เรียกไม่ได้, คำตอบถูกตัด หรือรูปแบบไม่ถูกต้อง:

- แสดงคะแนนและข้อเท็จจริงจาก Backend ต่อไป
- แจ้งว่า “คำอธิบายยังไม่พร้อม”
- ไม่เปลี่ยนเคสเป็น `FAILED` เพียงเพราะสร้างคำอธิบายไม่ได้
- ไม่เรียกใหม่ต่อเนื่องโดยไม่มีเพดาน

หากตั้ง `LLM_PROVIDER=bedrock` แล้วเรียกผิดพลาด ห้ามเปลี่ยนเป็น `fake` แบบเงียบ ๆ เพราะผู้ใช้จะเข้าใจว่าเป็นคำอธิบายจากโมเดลจริง

การสร้างคำอธิบายต้องไม่ถือ Lock ของ Workflow ระหว่างรอ API และไม่ขวางการตอบ Offer การอนุมัติ หรือ Job ของระบบ

**9. งบประมาณ**

เสนอให้กัน **US$10 เป็นงบทดลอง LLM เริ่มต้น** แยกจากงบบริการ AWS อื่น ตัวเลขนี้เป็นงบทดลอง ไม่ใช่ประมาณการค่าใช้จ่ายทั้งหมดของโปรเจกต์

ต้องมี:

- เพดาน token ต่อคำขอ
- เพดานจำนวนคำขอสำหรับช่วงทดลอง
- การจำกัด retry
- การเก็บผลไว้ใช้ซ้ำ
- สวิตช์ปิด LLM ผ่าน config
- AWS Budget สำหรับแจ้งเตือนค่าใช้จ่าย

AWS Budget ไม่ใช่ตัวหยุดค่าใช้จ่ายทันที เพราะข้อมูลค่าใช้จ่ายและการแจ้งเตือนอาจล่าช้า [เอกสาร AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)

หากบังคับเพดานงบใน Backend ต้องตรวจและกันงบสำหรับคำขอที่กำลังรันด้วย ไม่ตรวจเฉพาะยอดของคำขอที่เสร็จแล้ว เพราะหลายคำขอพร้อมกันอาจทำให้เกินเพดานได้

**10. การเก็บ usage และต้นทุนสำหรับนำเสนอ**

บันทึกการเรียกแต่ละครั้งอย่างน้อย:

| ข้อมูล | จุดประสงค์ |
|---|---|
| `case_id`, `plan_id` | ผูกการเรียกกับเคสและ Plan |
| provider, model และ Region | ระบุสิ่งที่ใช้และอัตราราคา |
| รุ่น prompt และรุ่นข้อมูล | ตรวจย้อนกลับและแยกผลเก่า/ใหม่ |
| input/output/total tokens | วัดปริมาณใช้งานจริง |
| ระยะเวลา | วัดความเร็ว |
| สถานะและหมายเลข attempt | รวมการเรียกที่ retry |
| estimated cost และอัตราราคาที่ใช้ | ประมาณต้นทุนตรวจย้อนกลับได้ |

Bedrock Converse คืนจำนวน token ผ่าน `usage.inputTokens`, `usage.outputTokens` และ `usage.totalTokens` ให้ใช้ค่าที่ API รายงาน ไม่ประมาณจากจำนวนตัวอักษร [เอกสาร Converse](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)

หากคำขอล้มเหลวจนไม่ได้รับ usage ให้บันทึกว่าไม่ทราบ ไม่ลงเป็นศูนย์ และตรวจยอดกับ AWS Billing ประกอบ ค่าใช้จ่ายที่ Backend คำนวณเป็นค่าประมาณ ไม่ใช่ยอดบิลยืนยัน

สำหรับโมเดลข้อความที่คิดราคา input/output ต่อหนึ่งล้าน token:

ค่าใช้จ่ายต่อเคส =
(input tokens รวม ÷ 1,000,000 × ราคา input)
+ (output tokens รวม ÷ 1,000,000 × ราคา output)

ต้องรวม retry และการสร้างคำอธิบายใหม่ทุกครั้ง หากใช้ caching, reasoning หรือรูปแบบคิดราคาอื่น ให้คำนวณตามรายการราคาของโมเดลนั้น [ราคา Bedrock](https://aws.amazon.com/bedrock/pricing/)

**11. การทดสอบและเกณฑ์ก่อนเปิดใช้จริง**

CI ใช้ `fake` ที่ให้ผลคงที่และไม่เรียกอินเทอร์เน็ต ทดสอบอย่างน้อย:

- ส่งคะแนน เป้าหมายและอันดับให้ตัวกลางได้ถูกต้อง
- บังคับ config ของ token, timeout และ retry
- เปิดหน้าเดิมซ้ำไม่เรียกใหม่
- คำขอพร้อมกันของงานเดียวกันไม่สร้างการเรียกซ้ำ
- timeout และคำตอบผิดรูปแบบไม่กระทบ Workflow
- บันทึก usage และรวม attempt ได้ถูกต้อง
- ความลับไม่อยู่ใน response หรือ log

การทดสอบ Bedrock จริงเป็นขั้นแยกบนสภาพแวดล้อมที่มีสิทธิ์เรียก ทดลองเคสเล็ก กลางและใหญ่ประมาณ 20–30 เคสก่อนยืนยัน model ID

รายงานสำหรับนำเสนอให้ใช้ผลวัดจริง ได้แก่:

- จำนวนครั้งที่เรียกต่อเคส
- input/output tokens เฉลี่ยและสูงสุด
- ต้นทุนประมาณต่อเคส
- เวลาในการตอบ
- จำนวนคำตอบที่ไม่ผ่านการตรวจรูปแบบหรือไม่ตรงกับข้อมูล

เมื่อได้ผลแล้วจึงปรับเพดาน 1,024 tokens และงบทดลองตามหลักฐาน โดยบันทึกการเปลี่ยน config ไว้ให้ทีมทราบ

| R3-Q2 | ก คำนวณตอนอ่าน ไม่มี Migration | ค่าน้ำหนักอ่านจาก Policy ตอนอ่านไม่ได้ เพราะ Policy ถูกแก้ทับได้ ตอนวางแผนจึงเก็บ `weights` และค่าตรงของชั่วโมง, OT และ `penalty` เป็น `"เศษ/ส่วน"` ลง `input_snapshot` ซึ่งเป็น `JSONB` จึงยังไม่มี Migration Plan เก่าที่ไม่มี key เหล่านี้คืน `score = null` |

| R3-Q10, R3-Q17 | ส่งซ้ำรวม 3 ครั้งแล้ว `FAILED` | ตรวจกับเอกสาร LINE แล้ว งานส่งบันทึกกับแถว Offer ใน Transaction ของ Wave, ใช้ `X-Line-Retry-Key` ตัวเดียวตลอด, `409` ถือว่ารับแล้ว, `429` ส่งซ้ำโดยไม่นับครั้ง, `401` และ `403` หยุดส่งและแจ้ง Error โดยไม่ตั้ง `FAILED`, `4xx` อื่นเป็น `FAILED` ได้เลย, ตรวจสถานะ Offer ก่อนส่งซ้ำและก่อนเขียน `FAILED` |
| R3-Q21, R3-Q22 | Parameter Store, ตารางรหัสผูกบัญชี | แอปอ่านความลับจาก env ส่วน PR D โหลดจาก Parameter Store เข้า env การใช้รหัสผูกบัญชีทำใน Transaction เดียวและสำเร็จได้ครั้งเดียว |

## ข้อตกลงเพิ่ม: หน้าเว็บพยาบาล

ทีมถามผู้จัดการแข่งขันว่าใช้ LINE Messaging API ได้ไหม เพราะการแข่งขันเน้น Native AWS Services NTT ยืนยันแล้วว่าใช้ได้ คำตอบเรื่อง LINE ข้างบนจึงคงเดิม ทั้งสามคนตกลงเพิ่มสิ่งต่อไปนี้ (รายละเอียดอยู่ในข้อ 4.1 ของร่าง)

| เรื่อง | ข้อตกลง |
|---|---|
| หน้าเว็บพยาบาล | เพิ่มหน้า "ข้อเสนอเข้าเวรของฉัน" เป็นช่องทางเสริมของ LINE ดูรายการ Offer ติดตามสถานะ และตอบได้ |
| อยู่รอบไหน | รอบ 3 เป็น PR แยก (PR N) |
| กติกาการตอบ | ใช้ `record_response()` ตัวเดียวกับ LINE ไม่มีกติกาชุดที่สอง |
| ตัวตน | ใช้ตัวตนจำลองของ Demo (`X-Demo-User`) และเขียนให้ชัดว่าเป็นโหมด Demo ระบบ Login จริงอยู่นอกรอบ 3 Header นี้ตั้งเองได้ เครื่องทดสอบบน AWS จึงต้องมีด่าน Basic Auth ของ PR D ครอบทุก Path ยกเว้น Webhook ของ LINE (เพิ่มตามรีวิวของ PR #60) |
| อยู่หลังงานไหน | หลัง PR L และ PR K |
| สิ่งที่ไม่ทำใน PR นี้ | ระบบแจ้งเตือนใหม่ และฟีเจอร์จัดเวรอื่น |
