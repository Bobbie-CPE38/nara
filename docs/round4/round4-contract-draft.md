## 3. Contract ของ Cross-Ward (คน 2)

* **ความหมาย (R4-Q4 ค):** มีสองแบบ
  * **ดึงคนที่ว่าง:** คนจากหออื่นที่ไม่มีเวรทับช่วงเวลานั้น เข้า Pool เหมือนคนในหอ ไม่แตะ Roster ของหอต้นทาง
  * **ย้ายคนที่อยู่เวร:** คนที่มีแถว `ASSIGNED` ในเวรของหออื่นที่ทับช่วงเวลานั้น เข้า Pool พร้อม**เวรต้นทาง** (แถว Roster ที่จะถูกยกเลิก) เมื่ออนุมัติแล้ว แถวต้นทางเป็น `CANCELLED` และแถวใหม่ของเวรปลายทางถูกสร้างใน Transaction เดียวกัน (R4-Q20 ก) ไม่ผ่านเส้นทางรับ Event บันทึก Audit ว่าย้ายไปเคสไหน ชื่อ Action ตกลงใน PR 0 ห้ามใช้ `ASSIGNMENT_CANCELLED` ซ้ำ เพราะ Action นั้นเป็นของเส้นทางรับ Event (ข้อ 3 และ 7.1 ของ `workflow.md`) Timeline จะอ่านผิดว่ามีคนแจ้งยกเลิก
  * **เวรต้นทางแบบไหนย้ายได้ (R4-Q26 ค):** ทุกเวรที่ทับเวลา รวมเวรที่ทับบางส่วนและเวรที่เริ่มแล้ว
  * **เวลาที่ทำจริงใน Roster (R4-Q31 ก):** เพิ่มคอลัมน์เวลาเริ่มจริงและเวลาจบจริงใน `ROSTER_ASSIGNMENT` (Migration) ค่าว่างแปลว่าตามเวลาของเวร
    * เวรต้นทางที่ยังไม่เริ่มและทับเวรปลายทางทั้งเวร: แถวต้นทางเป็น `CANCELLED` ตาม R4-Q20 ก
    * เวรต้นทางที่เริ่มแล้ว หรือทับบางส่วน: แถวต้นทางยังเป็น `ASSIGNED` แต่ตั้งเวลาจบจริงเป็นเวลาย้าย ชั่วโมงที่ทำไปแล้วจึงยังนับ แถวปลายทางตั้งเวลาเริ่มจริงเป็นเวลาย้าย ถ้าเวรปลายทางเริ่มไปแล้ว
    * **[ตรวจแล้ว]** ทุกตัวที่อ่านเวลาจาก Roster ต้องเปลี่ยนไปใช้เวลาจริงในรอบนี้ ได้แก่ `working_time_service` (ชั่วโมงและเวรติดกัน), `CandidateContext` ของ Hard Rules (เวรชน, เวลาพัก, ชั่วโมงรายวันและรายสัปดาห์), การนับคนที่อยู่เวรของ Gap (แถวที่จบก่อนเวลาต้องไม่นับว่าอยู่เวรหลังเวลาจบจริง), Job ที่ตั้ง `COMPLETED` (รอบ 3 PR R) และหน้า Roster ถ้าตัวไหนยังอ่านเวลาของเวรตรง ๆ จะพังเงียบ
    * Roster หลังย้าย (ข้อถัดไป) ใช้เวลาจริงเหล่านี้
* **หอบ้านกับหอต้นทางเป็นคนละเรื่อง (ตามรีวิว PR #73):** `CandidateSource` บอกหอบ้านของคนเทียบกับหอปลายทาง ส่วน**เวรต้นทาง**บอกว่าคนนั้นถูกย้ายออกจากเวรของหอไหน สองค่านี้ต้องเก็บแยกกันใน Plan และคำขอ ตัวอย่าง: พยาบาลหอบ้าน A ที่ตอนนี้อยู่เวรของหอ B ถูกย้ายกลับมาเวรของหอ A ได้ `source = SAME_WARD` แต่หอ B เสียคน การอนุมัติสองหอ (ข้อ 4) และการไม่อนุมัติเอง (ข้อ 5) ต้องดูจาก "มีเวรต้นทางของหออื่น" ไม่ใช่ดูจาก `source` อย่างเดียว
* **Roster ที่ใช้ตรวจการย้าย (ตามรีวิว PR #73):** การตรวจ Hard Rules ของคนที่ถูกย้ายใช้ Roster หลังย้ายแล้ว คือเอาแถวของเวรต้นทางออก ใส่แถวของเวรปลายทาง และคงแถวอื่นทั้งหมดไว้ แล้วตรวจทุกข้อจาก Roster นี้ (เวรชน, เวลาพัก, ชั่วโมงรายวันและรายสัปดาห์, เวรติดกัน) ไม่ใช่แค่ข้ามการตรวจ `SHIFT_CONFLICT` เพราะแถวต้นทางยังถูกนับในชั่วโมงทำงานและเวรติดกัน ใช้ Roster หลังย้ายแบบเดียวกันทั้งตอนวางแผน, Safety และการตรวจครั้งสุดท้ายตอนอนุมัติ
* **เวรต้นทางต้องไม่ขาดคน (ตามรีวิว PR #73):** กฎ `SOURCE_WARD_MINIMUM_VIOLATION` ตอนนี้ตรวจแค่จำนวนคน (`assigned_count - 1 >= effective_minimum`) ไม่ได้ตรวจ Role และ Skill และตรวจทีละผู้สมัคร ร่างเดิมที่เขียนว่า "กฎรับประกันว่าไม่เกิด Gap" จึงผิด **การย้ายต้องรักษาครบทั้งจำนวนคน Role และ Skill ของเวรต้นทาง (R4-Q24 ก)** คำนวณ Gap ของเวรต้นทางแบบที่คนนั้นไม่อยู่ ด้วยตัวคำนวณ Gap ตัวเดียวกับเคส ถ้ามี Gap ในเรื่องใด คนนั้นย้ายไม่ได้ ตรวจตอนวางแผนและตรวจซ้ำตอนย้ายจริง (ข้อถัดไป) กฎ `SOURCE_WARD_MINIMUM_VIOLATION` ต้องขยายจากจำนวนคนเป็นทั้งสามเรื่อง
* **ย้ายหลายคนจากเวรต้นทางเดียวกัน (R4-Q25 ตกลงแล้ว):** ปัญหาเกิดได้สองแบบ คือเคสเดียวขาดตั้งแต่ 2 คนจึงมีคำขอของสองคนจากเวรต้นทางเดียวกันรออนุมัติพร้อมกัน และสองเคสต่างหอเลือกคนจากเวรต้นทางเดียวกัน แม้แต่ละเคสขาดคนเดียว (เคสที่ขาด 1 คนไม่เกิดปัญหานี้ในเคสเดียว เพราะคนที่ตอบรับทีหลังเป็นตัวสำรอง ไม่มีคำขออนุมัติ)
  * **ตรวจเวรต้นทางตอนย้ายจริง:** ตอนที่คำขออนุมัติครบและจะย้ายจริง ล็อก `SHIFT` ของเวรต้นทางและเวรปลายทางเรียงตาม `shift.id` แล้วตรวจเวรต้นทางจากข้อมูลล่าสุดใน Transaction เดียวกับการยกเลิกแถวต้นทางและการสร้างแถวปลายทาง (R4-Q20) ถ้าไม่ผ่าน จบคำขอและยกเลิก Offer พร้อมเหตุผล แล้วคำนวณเคสใหม่เพื่อเลื่อนตัวสำรองหรือส่ง Wave ถัดไป แบบเดียวกับ Safety ไม่ผ่าน **ไม่ทำให้เคสเป็น `FAILED`** ลำดับ Lock นี้บันทึกในข้อ 6.11 ของ `workflow.md`
  * **ข้อยกเว้นของ Q38 ที่เพิ่มในรอบ 4:** การตรวจนี้ใช้เฉพาะการย้ายคนที่อยู่เวร และตรวจเฉพาะกฎเวรต้นทาง เหตุผลที่ยกเว้นได้คือกฎนี้ขึ้นกับสถานะของเวรอื่นที่เปลี่ยนได้ระหว่าง Safety กับการอนุมัติ ต่างจากกฎประจำตัวคน เช่น เวลาพัก กฎอื่นยังไม่ตรวจซ้ำตาม Q38 Test `test_execution_does_not_recheck_safety` ต้องแก้ให้ยกเว้นกฎนี้
  * **Plan หนึ่งเลือกคนจากเวรต้นทางเดียวกันได้ไม่เกินหนึ่งคน (R4-Q25 ก):** เป็นข้อจำกัดของการวางแผนเพื่อลดกรณีที่คนตอบรับแล้วถูกยกเลิก **ไม่ใช่ตัวรับประกันความปลอดภัย** และอาจเลือกได้น้อยกว่าที่เวรต้นทางให้ย้ายได้จริง การตรวจตอนย้ายจริงยังจำเป็นเสมอ เพราะกันผลจากเคสอื่นได้ทางเดียว **ใช้กับทุก Wave (R4-Q30 ก):** `wave_service` ข้ามผู้สมัครที่เวรต้นทางเดียวกับคนในเคสนี้ที่ยังมี Offer ค้าง คำขอรออนุมัติ หรือถูกย้ายไปแล้ว และบันทึกเหตุผลใน `skipped` ด้วยรหัสใหม่ (ชื่อตกลงใน PR 0)
* **หอที่ให้ยืม (R4-Q5 ก):** ทุกหอที่ `is_active` ไม่มีตารางคู่หอ
* **Float Pool (R4-Q6 ก, R4-Q21 ก, R4-Q22 ก):** หอพิเศษใน `WARD` ที่มีคอลัมน์ใหม่ `is_float_pool` (Migration) พนักงานที่หอบ้านเป็นหอนี้ได้ `source = FLOAT_POOL` หอนี้ไม่มีเวรของตัวเอง ทุกที่ที่วนหอต้องกรองด้วยคอลัมน์นี้ คน Float Pool ไม่ต้องมีการอนุมัติฝั่งต้นทาง หอปลายทางอนุมัติอย่างเดียว
* **การเลือกและอันดับ (R4-Q7 ก):** Pool เดียว Solver เดิม น้ำหนักแหล่งที่มาเป็นตัวทำให้คนในหอถูกเลือกก่อน
* **กติกาที่ต้องยึด:**
  * Hard Rules ทุกข้อใช้กับคนข้ามหอเหมือนคนในหอ ตัวตรวจยังเป็น `hard_rule_service` ตัวเดียว
  * `source` และเวรต้นทางเก็บใน Snapshot ของ Plan และ `CANDIDATE_ITEMS` ตอนวางแผน
  * Lock แถว `STAFF` ของ Pool ทั้งหมดตามลำดับ ID เหมือนเดิม การย้ายคนที่อยู่เวรต้องล็อก `SHIFT` ทั้งสองเวรเรียงตาม ID ก่อนแก้ Roster
  * คนหนึ่งคนมี Offer ค้างหลายเคสได้ตามกติกาเดิม (รอบ 1) สิ่งที่ห้ามคือเวรที่จัดแล้วทับกัน หรือการตอบรับที่ขัดกับกติกาเดิม
  * Seed Scenario ใหม่ที่มีหลายหอ และ Golden Case เดิมต้องได้ผลเหมือนเดิม (Golden Path ยังเขียว)

## 4. Contract ของผู้อนุมัติ (คน 2)

* **กรณีข้ามหอ (R4-Q8 ข, R4-Q15 ก, R4-Q16 ข):**
  * คำขอที่มีเวรต้นทางของหออื่น (ข้อ 3): Head Nurse ของทั้งหอต้นทางและหอปลายทางต้องอนุมัติ ทั้งสองหอกดได้พร้อมกัน ต้องอนุมัติครบสองหอจึงจัดเวร หอใดปฏิเสธคือปฏิเสธทั้งคำขอ ใช้เส้นตายเดียวกับคำขอปกติ หอต้นทางคือหอของ**เวรต้นทาง** ไม่ใช่หอบ้านของคน
  * คนที่ว่างจากหออื่น และคน Float Pool: หอปลายทางอนุมัติอย่างเดียว เหมือนคำขอปกติ
  * `APPROVAL_REQUEST` เก็บผู้ตัดสินได้คนเดียว (ข้อ 1) จึงต้องเก็บการตัดสินของแต่ละหอแยกกัน (Migration) รูปของตารางหรือคอลัมน์ตกลงใน PR 0
* **Supervisor ช่วยเมื่อ Head Nurse ช้า (R4-Q8, R4-Q14 ก, R4-Q17 ข, R4-Q18 ก):** Supervisor กดอนุมัติหรือปฏิเสธแทนได้เมื่อคำขอรอถึงเวลาที่กำหนด เช่น คำขอมีเวลา 15 นาที (`approval_timeout_seconds` = 900) Supervisor เริ่มกดได้ที่นาทีที่ 10 ช่วงที่ Supervisor กดได้จึงเท่ากับ เวลาของคำขอ − เวลาที่ Supervisor เริ่มกดได้ (ตัวอย่างนี้คือ 5 นาที) ใช้กับคำขอทุกแบบ และแทนได้ทั้งหอต้นทางและหอปลายทาง เวลาเริ่มเป็นคอลัมน์ใหม่ใน `APPROVAL_POLICY` ค่าเดียวทั้งโรงพยาบาล (Seed 600 วินาที, CHECK มากกว่า 0 และน้อยกว่า `approval_timeout_seconds`) ทุกหอเปิดให้ Supervisor เสมอ
* **Supervisor ในข้อมูล (R4-Q9 ก, R4-Q14 ก):** Role ใหม่ `SUPERVISOR` เป็นแถวข้อมูลใน `ROLE` ไม่มี Migration แต่ Seed ต้องเพิ่มแถวนี้ การอนุมัติ Supervisor กดได้หลังเวลาที่กำหนดเท่านั้น ส่วนเส้นออกจาก `MANUAL_HANDOFF` (ข้อ 6.12) Supervisor ทำได้ทุกหอทันที เพราะไม่มีเส้นตายให้นับ
* **ตรวจสิทธิ์ยังไง (แก้ตามรีวิว PR #73):** ร่างเดิมเขียนว่าแก้ที่ `manages_ward()` จุดเดียว ซึ่งผิด (ข้อ 1)
  * `manages_ward()` คงไว้ตามเดิม ไม่รับ Role เพราะ `handoff_service.py:269` ใช้ตรวจคนที่ถูกจัดเวร ไม่ใช่คนกด
  * เพิ่มตัวตรวจสิทธิ์ของคนกดตัวใหม่ตัวเดียว ที่รับ Role, หอบ้าน, หอที่จะทำ และเวลาที่คำขอรอแล้ว (สำหรับการอนุมัติ) แล้วให้การอนุมัติและเส้นออกจาก `MANUAL_HANDOFF` เรียกตัวนี้แทนการตรวจ Role กับ `manages_ward()` แยกกัน
  * `required_approver_role` ยังเก็บ Role เดียว (`HEAD_NURSE`) ตัวตรวจใหม่รับ `SUPERVISOR` เพิ่มตามกติกาข้างบน ไม่เปลี่ยนคอลัมน์
  * การอนุมัติสองหอตรวจคนกดกับหอของเวรต้นทางแยกจากหอของเวรปลายทาง
  * **Supervisor ไม่ทำงานอื่นของ Head Nurse (R4-Q23 ก):** การแก้วันกลับของการลา และการแจ้ง Event `ASSIGNMENT_CANCELLED`, `PATIENT_SURGE`, `REQUIREMENT_CHANGED` ยังเป็นของ Head Nurse เท่านั้น สองที่นี้ไม่เปลี่ยน
* **กติกาที่ต้องยึด:**
  * การเพิ่ม Role ต้องไม่ทำให้ Test เรื่อง `403` ของรอบ 2 และ 3 (`test_approval_decision.py`, `test_manual_handoff.py` และ Test ของการแก้การลา) เปลี่ยนผล
  * เวลาที่ Supervisor เริ่มกดได้ใช้ Clock ของระบบ (`now >= requested_at + เวลาเริ่ม`) แบบเดียวกับเส้นตายของคำขอ
  * คำขอที่หมดเวลายังใช้กติกาของรอบ 2 (กลับไปต่อท้ายคิวหนึ่งครั้ง)

## 5. Contract ของ Auto-Approval (คน 3)

**เป้าหมาย (มติทีม 2026-10-15):** ลดภาระของคนกดไม่ให้หนักเกินไป ไม่ใช่วัดความวิกฤตของคนไข้

* **เงื่อนไข (R4-Q10 ตอบตามข้อเสนอใหม่):** Head Nurse ไม่ต้องเจอคำขอค้างเกินจำนวนที่รับไหว ส่วนที่เกินให้ระบบอนุมัติแทน
  * `ratio × จำนวนผู้อนุมัติของหอ` โดย `ratio` คือค่าใน Policy เดิม (2) เปลี่ยนความหมายเป็น "จำนวนคำขอที่ผู้อนุมัติหนึ่งคนรับไหว" ไม่ต้องมี Migration (เพดานจริงดูข้อ `incoming_count` ข้างล่าง)
  * จำนวนผู้อนุมัติ = Head Nurse ของหอที่ Active นับจากข้อมูลที่มีอยู่ ไม่ได้นับเฉพาะคนที่อยู่เวรตอนนั้น
  * ลำดับการอนุมัติเองในโหมดอนุมัติเอง: คำขอที่รอนานที่สุดก่อน เพราะใกล้หมดเวลา
  * **หอที่ไม่มี Head Nurse ที่ Active เลย (R4-Q27 ข):** เพดานเป็น 0 ระบบอนุมัติเองทุกรายการที่อนุมัติเองได้ ทีมรับความเสี่ยงที่รีวิวทักไว้ (ถ้า Head Nurse คนเดียวของหอถูก Deactivate การอนุมัติโดยคนของหอนั้นหายไป) Audit ของการอนุมัติเองบันทึกจำนวนผู้อนุมัติเป็น 0 ให้ตรวจย้อนได้
  * ไม่อนุมัติเองให้คนข้ามหอ (`CROSS_WARD` และ `FLOAT_POOL`) และคำขอที่มีเวรต้นทางของหออื่น (ข้อ 3) ไม่ว่า `source` จะเป็นอะไร คนกดต้องดูเสมอ
  * **นับคิวและโหมดอนุมัติเองต่อเนื่อง (R4-Q28, R4-Q32 ก, R4-Q33 ก):** นับทุกคำขอที่รออนุมัติในหอ รวมคำขอที่ระบบอนุมัติเองไม่ได้ เมื่อคิว**เกิน**เพดาน (มากกว่า ไม่ใช่เท่ากับ) หอนั้นเข้า**โหมดอนุมัติเอง** Job อนุมัติเองต่อไปเรื่อย ๆ คำขอที่เข้ามาระหว่างนั้นถูกอนุมัติเองด้วย (ในรอบ Job ถัดไป) และ**หยุดเมื่อไม่เหลือคำขอที่อนุมัติเองได้** คำขอที่ต้องให้คนดู (ข้ามหอ, Float Pool, มีเวรต้นทางของหออื่น) ยังรอคนกดตามปกติ หลังหยุดแล้ว ต้องรอให้คิวเกินเพดานอีกครั้งจึงเข้าโหมดใหม่
  * โหมดอนุมัติเองเป็นสถานะต่อหอที่ต้องอยู่ข้ามรอบของ Job จึงต้องเก็บใน DB (Migration) รูปตกลงใน PR 0 อ่านและเขียนสถานะนี้หลังล็อก `WARD` เท่านั้น
  * **กันการนับคิวพร้อมกัน (R4-Q29 ก):** ล็อกแถว `WARD` ของหอปลายทางก่อนนับคิว ทั้งใน Job อนุมัติเองและในการตัดสินของคน `WARD` อยู่หน้าสุดของลำดับ Lock (`WARD` → `SHIFT` เรียงตาม ID → คำขอ → Offer → เคส → Staff) **[ตรวจแล้ว]** ตอนนี้ไม่มีเส้นทางไหนล็อก `WARD` จึงเพิ่มหน้าลำดับเดิมได้ แก้ข้อ 6.11 ของ `workflow.md` พร้อม Test สอง Connection ทั้ง Job กับ Job และ Job กับคนกด
* **`incoming_count` (R4-Q11 ก, R4-Q19 ก):** เพดานจริง = ค่าที่ต่ำกว่าระหว่าง `ratio` × จำนวน Head Nurse กับ `incoming_count` เช่น หอที่มี Head Nurse 1 คน เพดานคือ 2 หอที่มี 8 คน เพดานคือ 10 Supervisor ไม่นับเป็นผู้อนุมัติของหอ เพราะกดได้หลังเวลาที่กำหนดเท่านั้น
* **ทางเดินของการอนุมัติเอง (R4-Q12 ก):** Safety ตรวจเหมือนเดิม การตอบรับสร้างคำขอตามปกติ Job ตรวจเงื่อนไขซ้ำหลังล็อกแล้วตัดสินผ่าน `approval_service.decide()` ตัวเดียวกับคนกด ตั้ง `approval_mode = AUTO` Actor เป็น `system` `approver_id` เป็น `NULL` บันทึกจำนวนคำขอที่รอ จำนวนผู้อนุมัติ และเพดานลง Audit ไม่ตัดสินใน Transaction ของการตอบรับ เพราะลำดับ Lock (ข้อ 1)
* **คนเห็นการอนุมัติเอง (R4-Q13 ก):** หน้า `approvals` มีรายการ "ระบบอนุมัติแทน" แยกจากรายการรอ และ Timeline ของหน้า `cases/[id]` แสดง Audit
* **กติกาที่ต้องยึด:**
  * ช่อง `role_id = None` ที่ข้ามการตรวจสิทธิ์ใช้ได้เฉพาะเมื่อตรวจเงื่อนไขผ่านใน Transaction เดียวกัน
  * Job ตัดสินคำขอหนึ่งครั้ง และไม่ตั้งคำขอที่ตัดสินแล้วเป็นหมดเวลา
  * Golden Case มี Head Nurse 1 คน เพดาน 2 และขาด 1 คน คนที่ตอบรับทีหลังเป็นตัวสำรอง ไม่มีคำขออนุมัติ คิวจึงมีไม่เกิน 1 รายการ ไม่เข้าโหมดอนุมัติเอง Golden Path จึงไม่เปลี่ยน
  * PR 0 แก้ข้อความเรื่อง Ratio ผู้ป่วยทั้ง 3 ที่ (ข้อ 1) ให้ตรงความหมายใหม่

## 9. สิ่งที่ยังไม่ได้ตรวจ

* ยังไม่ได้ลองขยาย Pool จริง จึงยังไม่รู้ว่า Solver ใช้เวลาเท่าไรเมื่อ Pool ใหญ่ขึ้นหลายหอ (เพดานเวลาเดิม 3 วินาที ข้อ 6.14 ของ `workflow.md`)
* ยังไม่ได้ตรวจว่าหน้า `approvals`, `handoff` และ `cases/[id]` แสดงหอบ้านของผู้สมัครหรือไม่ (งานของคน 1 ตาม R4-Q1 ก)
* ยังไม่ได้ตรวจว่าการเปลี่ยนแถว Roster ของเวรต้นทาง (R4-Q4 ค) ไปกระทบเส้นทางรับ Event `ASSIGNMENT_CANCELLED` และ Merge Window ของหอต้นทางยังไง
* `event_service` ตรวจแค่ Role ของ Head Nurse ตอนรับ Event ที่ Head Nurse แจ้ง ไม่ตรวจว่าเป็นหอของเวร ยังไม่ได้ตรวจว่าตั้งใจแบบนี้หรือไม่ ถ้า R4-Q23 ให้ Supervisor แจ้ง Event ได้ ต้องตรวจเรื่องนี้ก่อน
