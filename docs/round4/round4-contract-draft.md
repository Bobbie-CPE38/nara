* Auto-Approval มีไว้ลดภาระของคนกด ไม่ใช่วัดความวิกฤตของคนไข้ นับทุกคำขอที่รอในหอ เมื่อคิวเกินเพดาน (ค่าที่ต่ำกว่าระหว่าง `ratio` × จำนวน Head Nurse กับ `incoming_count`) ระบบอนุมัติแทนคำขอที่อนุมัติเองได้**ทั้งหมด** ไม่ใช่แค่ส่วนที่เกิน คำขอข้ามหอและการย้ายเวรรอคนกดเสมอ

## 3. Contract ของ Cross-Ward (คน 2)

* **ความหมาย (R4-Q4 ค):** มีสองแบบ
  * **ดึงคนที่ว่าง:** คนจากหออื่นที่ไม่มีเวรทับช่วงเวลานั้น เข้า Pool เหมือนคนในหอ ไม่แตะ Roster ของหอต้นทาง
  * **ย้ายคนที่อยู่เวร:** คนที่มีแถว `ASSIGNED` ในเวรของหออื่นที่ทับช่วงเวลานั้น เข้า Pool พร้อม**เวรต้นทาง** เมื่อย้ายจริง แถวต้นทางถูกยกเลิกหรือถูกตัดที่เวลาย้าย (ข้อย่อยถัดไป) และแถวใหม่ของเวรปลายทางถูกสร้างใน Transaction เดียวกัน ไม่ผ่านเส้นทางรับ Event บันทึก Audit ว่าย้ายไปเคสไหน ชื่อ Action ตกลงใน PR 0 ห้ามใช้ `ASSIGNMENT_CANCELLED` ซ้ำ เพราะ Action นั้นเป็นของเส้นทางรับ Event (ข้อ 3 และ 7.1 ของ `workflow.md`) Timeline จะอ่านผิดว่ามีคนแจ้งยกเลิก
  * **เวรต้นทางแบบไหนย้ายได้ (R4-Q26 ค, R4-Q31 ก, R4-Q34 ข):** ทุกเวรที่ทับเวลา รวมเวรที่ทับบางส่วนและเวรที่เริ่มแล้ว
    * **เวลาจริงใน Roster:** เพิ่มคอลัมน์เวลาเริ่มจริงและเวลาจบจริงใน `ROSTER_ASSIGNMENT` (Migration) ค่าว่างแปลว่าตามเวลาของเวร
    * **เวลาย้าย:** ค่าที่มากที่สุดระหว่าง เวลาเริ่มของเวรปลายทาง, เวลาเริ่มของเวรต้นทาง และเวลาที่อนุมัติครบ ต้องน้อยกว่าทั้งเวลาจบของเวรต้นทางและเวลาจบของเวรปลายทาง ช่วงที่ครอบเวรปลายทางจึงไม่ว่างเสมอ (แก้ตามรีวิวรอบสาม) ตัวอย่าง: เวรต้นทาง 00:00 ถึง 08:00 เวรปลายทาง 00:00 ถึง 04:00 คำขอสร้าง 03:55 อนุมัติครบ 04:05 เวลาย้ายคือ 04:05 ซึ่งไม่น้อยกว่าเวลาจบของเวรปลายทาง จึงย้ายไม่ได้ คำขอจบตามข้อ "ผลที่คนกดเห็น" ข้างล่าง ด้วยเหตุผล "ช่วงเวลาของเวรปลายทางผ่านไปแล้ว"
    * **แถวต้นทาง:** ถ้าเวลาย้ายคือเวลาเริ่มของเวรต้นทาง (ยังไม่ได้ทำส่วนใดเลย) แถวต้นทางเป็น `CANCELLED` ตาม R4-Q20 ก ไม่อย่างนั้นแถวต้นทางยังเป็น `ASSIGNED` และตั้งเวลาจบจริงเป็นเวลาย้าย ชั่วโมงที่ทำไปแล้วจึงยังนับ
    * **แถวปลายทาง:** ตั้งเวลาเริ่มจริงเป็นเวลาย้าย ถ้าเวลาย้ายมากกว่าเวลาเริ่มของเวรปลายทาง
    * **ช่วงทำงานต่อเนื่อง:** ส่วนที่ทำแล้วของเวรต้นทางกับส่วนของเวรปลายทางที่ต่อกันที่เวลาย้าย นับเป็นช่วงทำงานต่อเนื่องเดียว สำหรับกฎเวลาพักและเวรติดกัน เวลาพักวัดกับเวรก่อนและหลังช่วงนี้ **[ตรวจแล้ว]** `insufficient_rest()` ตอนนี้ถือว่าสองเวรที่ต่อกันพัก 0 ชั่วโมงและปฏิเสธ ต้องแก้ให้รู้จักช่วงต่อเนื่องนี้ ชั่วโมงรายวันและรายสัปดาห์นับเวลาจริงของทั้งสองส่วน
    * **Gap นับคนตามช่วงเวลา (ตกลงแล้ว 2026-10-15):** **[ตรวจแล้ว]** ตอนนี้การนับคนของ Gap นับแถวทั้งเวร ไม่ได้ดูช่วงเวลา ต้องเปลี่ยนทั้งระบบ นิยามที่ตกลง:
      * เวรไม่ขาดคนเมื่อทุกช่วงเวลาที่ยังเหลือ ตั้งแต่ `max(Backend Clock ตอนประเมิน, เวลาเริ่มเวร)` จนถึงเวลาจบ มีคนครบทั้งจำนวนคน Role และ Skill
      * แต่ละคนนับเฉพาะช่วงปฏิบัติงานของแถว Roster ของตัวเอง (เวลาเริ่มจริงถึงเวลาจบจริง)
      * ช่วงเวลาเป็นแบบ `[start, end)` คนหนึ่งจบและอีกคนเริ่มเวลาเดียวกันถือว่าต่อกันพอดี ไม่มีช่วงว่าง
      * ถ้าช่วงใดขาด ยังถือว่ามี Gap และต้องระบุสิ่งที่ขาด จำนวน และช่วงเวลา การเติมคนได้เพียงบางช่วงยังปิดเคสเป็น `RESOLVED` ไม่ได้ ถ้าช่วงอื่นยังขาด
      * ช่วงที่ผ่านไปแล้วไม่ต้องหาคนแทนย้อนหลัง แต่ชั่วโมงที่ทำไปแล้วยังนับในกฎความล้า
      * ใช้นิยามเดียวกันทั้งหอต้นทางและหอปลายทาง และตรวจผลหลังย้ายซ้ำหลังได้ Lock ก่อนย้ายจริง
      * **ตกลงใน PR 0 ก่อนแยก implement:** รูปข้อมูลของ Gap ตามช่วงเวลา (แถว `STAFFING_GAP` และ API), วิธีส่งให้ Solver และการปรับ Safety
    * **[ตรวจแล้ว] ตัวอ่านที่ต้องเปลี่ยนไปใช้เวลาจริงในรอบนี้:** `working_time_service` (ชั่วโมงและเวรติดกัน), `CandidateContext` ของ Hard Rules (เวรชน, เวลาพัก, ชั่วโมงรายวันและรายสัปดาห์), การนับคนของ Gap (`gap_service` และการปิด Merge Window ที่ใช้ Gap), Job ที่ตั้ง `COMPLETED` (รอบ 3 PR R) และหน้า Roster ถ้าตัวไหนยังอ่านเวลาของเวรตรง ๆ จะพังเงียบ
    * **Test ที่ต้องมี:** ย้ายเวรในอนาคตที่ทับบางส่วน, ย้ายระหว่างเวร (เวรต้นทางเริ่มแล้ว), อนุมัติหลังเวรปลายทางเริ่ม, เวลาย้ายไม่น้อยกว่าเวลาจบของเวรต้นทาง และช่วงทำงานต่อเนื่องที่ไม่ถูกกฎเวลาพักปฏิเสธ
* **หอบ้านกับหอต้นทางเป็นคนละเรื่อง:** `CandidateSource` บอกหอบ้านของคนเทียบกับหอปลายทาง ส่วน**เวรต้นทาง**บอกว่าคนนั้นถูกย้ายออกจากเวรของหอไหน สองค่านี้ต้องเก็บแยกกันใน Plan และคำขอ ตัวอย่าง: พยาบาลหอบ้าน A ที่ตอนนี้อยู่เวรของหอ B ถูกย้ายกลับมาเวรของหอ A ได้ `source = SAME_WARD` แต่หอ B เสียคน การอนุมัติสองหอ (ข้อ 4) และการไม่อนุมัติเอง (ข้อ 5) ต้องดูจาก "มีเวรต้นทางของหออื่น" ไม่ใช่ดูจาก `source` อย่างเดียว
* **Roster หลังย้ายที่ใช้ตรวจกฎ (แก้ตามรีวิวรอบสอง):** ตรวจ Hard Rules ของคนที่ถูกย้ายจาก Roster หลังย้าย ซึ่งคงแถวอื่นทั้งหมดไว้ และ
  * เวลาย้ายคือเวลาเริ่มของเวรต้นทาง (ยังไม่ได้ทำส่วนใด): เอาแถวต้นทางออก ใส่แถวปลายทาง
  * ย้ายกลางเวรหรือทับบางส่วน (R4-Q34 ข): ตัดแถวต้นทางที่เวลาย้าย เก็บส่วนที่ทำไปแล้ว แล้วใส่แถวปลายทางตั้งแต่เวลาย้าย ห้ามเอาแถวต้นทางออกทั้งแถว เพราะชั่วโมงที่ทำแล้วจะหายจากกฎความล้า
  * ใช้ Roster หลังย้ายแบบเดียวกันตอนวางแผนและตอน Safety ตรวจทุกข้อ ไม่ใช่แค่ข้ามการตรวจ `SHIFT_CONFLICT`
* **เวรต้นทางต้องไม่ขาดคน (R4-Q24 ก):** กฎ `SOURCE_WARD_MINIMUM_VIOLATION` ตอนนี้ตรวจแค่จำนวนคน (`assigned_count - 1 >= effective_minimum`) และตรวจทีละผู้สมัคร ต้องขยายเป็นครบทั้งจำนวนคน Role และ Skill โดยคำนวณ Gap ของเวรต้นทางแบบที่คนนั้นไม่อยู่ ด้วยตัวคำนวณ Gap ตัวเดียวกับเคส ถ้ามี Gap ในเรื่องใด คนนั้นย้ายไม่ได้
* **ย้ายหลายคนจากเวรต้นทางเดียวกัน (R4-Q25 ตกลงแล้ว):** ปัญหาเกิดได้สองแบบ คือเคสเดียวขาดตั้งแต่ 2 คนจึงมีคำขอของสองคนจากเวรต้นทางเดียวกันรออนุมัติพร้อมกัน และสองเคสต่างหอเลือกคนจากเวรต้นทางเดียวกัน แม้แต่ละเคสขาดคนเดียว (เคสที่ขาด 1 คนไม่เกิดปัญหานี้ในเคสเดียว เพราะคนที่ตอบรับทีหลังเป็นตัวสำรอง ไม่มีคำขออนุมัติ)
  * **ตรวจเวรต้นทางตอนย้ายจริง:** ตอนที่คำขออนุมัติครบและจะย้ายจริง ล็อก `SHIFT` ของเวรต้นทางและเวรปลายทางเรียงตาม `shift.id` แล้วตรวจกฎเวรต้นทาง (จำนวนคน Role Skill) จากข้อมูลล่าสุด ใน Transaction เดียวกับการแก้แถวต้นทางและการสร้างแถวปลายทาง ถ้าไม่ผ่าน คำขอจบและ Offer ถูกยกเลิกพร้อมเหตุผล แล้วคำนวณเคสใหม่เพื่อเลื่อนตัวสำรองหรือส่ง Wave ถัดไป **ไม่ทำให้เคสเป็น `FAILED`**
  * **ผลที่คนกดเห็น (R4-Q35 ก, ขยายตามรีวิวรอบสาม):** ถ้าการตรวจตอนย้ายจริงไม่ผ่าน Commit การจบคำขอในสถานะ "ยกเลิกตอนย้ายจริง" ซึ่งไม่ใช่การปฏิเสธของคน พร้อมเหตุผลที่ตรงกับสิ่งที่ไม่ผ่าน มีสามแบบ คือ เวรต้นทางไม่พอ (จำนวนคน Role หรือ Skill), ช่วงเวลาของเวรปลายทางผ่านไปแล้ว และกฎของคนที่ถูกย้ายไม่ผ่าน (ระบุรหัสกฎ เช่น `INSUFFICIENT_REST`) ห้ามใช้ "เวรต้นทางไม่พอ" กับทุกกรณี บันทึก Audit พร้อมเหตุผล แล้ว API ของคนกดตอบ `200` พร้อมผลว่าไม่ได้ย้ายและเหตุผล จากนั้นคำนวณเคสใหม่เพื่อหาคนต่อ ไม่ทำให้เคสเป็น `FAILED` คำขอสองหอ: การตรวจทำตอนการอนุมัติที่ทำให้ครบสองหอ ถ้าไม่ผ่าน การอนุมัติของหอแรกเก็บไว้เป็นประวัติ และคำขอจบแบบเดียวกัน หน้า `approvals` แสดงผลนี้แยกจากการอนุมัติสำเร็จ ชื่อรหัสเหตุผลตกลงใน PR 0
  * **ข้อยกเว้นของ Q38 ที่เพิ่มในรอบ 4 (R4-Q34 ข):** ตอนย้ายจริงตรวจซ้ำสองอย่าง คือกฎเวรต้นทาง และกฎของคนที่ถูกย้ายที่ขึ้นกับเวลา (เวรชน, เวลาพัก, ชั่วโมงรายวันและรายสัปดาห์, เวรติดกัน) จาก Roster หลังย้ายที่ใช้เวลาย้ายจริง เพราะ Safety ตรวจด้วยเวลาที่ต่างจากเวลาย้ายจริง กฎอื่นของคน (เช่น สถานะ Active, Role, Skill) ไม่ตรวจซ้ำตาม Q38 ข้อยกเว้นนี้ใช้กับการย้ายคนที่อยู่เวรเท่านั้น คำขอแบบอื่นยังไม่ตรวจซ้ำ Test `test_execution_does_not_recheck_safety` ต้องแก้ให้ยกเว้นสองกรณีนี้
  * **Plan หนึ่งเลือกคนจากเวรต้นทางเดียวกันได้ไม่เกินหนึ่งคน (R4-Q25 ก, R4-Q30 ก):** ใช้กับทุก Wave `wave_service` ข้ามผู้สมัครที่เวรต้นทางเดียวกับคนในเคสนี้ที่ยังมี Offer ค้าง คำขอรออนุมัติ หรือถูกย้ายไปแล้ว และบันทึกเหตุผลใน `skipped` ด้วยรหัสใหม่ (ชื่อตกลงใน PR 0) เป็นข้อจำกัดของการวางแผน **ไม่ใช่ตัวรับประกันความปลอดภัย** การตรวจตอนย้ายจริงยังจำเป็นเสมอ
* **หอที่ให้ยืม (R4-Q5 ก):** ทุกหอที่ `is_active` ไม่มีตารางคู่หอ
* **Float Pool (R4-Q6 ก, R4-Q21 ก, R4-Q22 ก):** หอพิเศษใน `WARD` ที่มีคอลัมน์ใหม่ `is_float_pool` (Migration) พนักงานที่หอบ้านเป็นหอนี้ได้ `source = FLOAT_POOL` หอนี้ไม่มีเวรของตัวเอง ทุกที่ที่วนหอต้องกรองด้วยคอลัมน์นี้ คน Float Pool ไม่ต้องมีการอนุมัติฝั่งต้นทาง หอปลายทางอนุมัติอย่างเดียว
* **การเลือกและอันดับ (R4-Q7 ก):** Pool เดียว Solver เดิม น้ำหนักแหล่งที่มาเป็นตัวทำให้คนในหอถูกเลือกก่อน
* **กติกาที่ต้องยึด:**
  * Hard Rules ทุกข้อใช้กับคนข้ามหอเหมือนคนในหอ ตัวตรวจยังเป็น `hard_rule_service` ตัวเดียว
  * `source` และเวรต้นทางเก็บใน Snapshot ของ Plan และ `CANDIDATE_ITEMS` ตอนวางแผน
  * Lock แถว `STAFF` ของ Pool ทั้งหมดตามลำดับ ID เหมือนเดิม การย้ายคนที่อยู่เวรต้องล็อก `SHIFT` ทั้งสองเวรเรียงตาม ID ก่อนแก้ Roster
  * คนหนึ่งคนมี Offer ค้างหลายเคสได้ตามกติกาเดิม (รอบ 1) สิ่งที่ห้ามคือเวรที่จัดแล้วทับกัน หรือการตอบรับที่ขัดกับกติกาเดิม
  * Seed Scenario ใหม่ที่มีหลายหอ และ Golden Case เดิมต้องได้ผลเหมือนเดิม (Golden Path ยังเขียว)

## 4. Contract ของผู้อนุมัติ (คน 3, PR S)

* **กรณีข้ามหอ (R4-Q8 ข, R4-Q15 ก, R4-Q16 ข):**
  * คำขอที่มีเวรต้นทางของหออื่น (ข้อ 3): Head Nurse ของทั้งหอต้นทางและหอปลายทางต้องอนุมัติ ทั้งสองหอกดได้พร้อมกัน ต้องอนุมัติครบสองหอจึงจัดเวร หอใดปฏิเสธคือปฏิเสธทั้งคำขอ ใช้เส้นตายเดียวกับคำขอปกติ หอต้นทางคือหอของ**เวรต้นทาง** ไม่ใช่หอบ้านของคน
  * คนที่ว่างจากหออื่น และคน Float Pool: หอปลายทางอนุมัติอย่างเดียว เหมือนคำขอปกติ
  * `APPROVAL_REQUEST` เก็บผู้ตัดสินได้คนเดียว (ข้อ 1) จึงต้องเก็บการตัดสินของแต่ละหอแยกกัน (Migration) รูปของตารางหรือคอลัมน์ตกลงใน PR 0
* **Supervisor ช่วยเมื่อ Head Nurse ช้า (R4-Q8, R4-Q14 ก, R4-Q17 ข, R4-Q18 ก):** Supervisor กดอนุมัติหรือปฏิเสธแทนได้เมื่อคำขอรอถึงเวลาที่กำหนด เช่น คำขอมีเวลา 15 นาที (`approval_timeout_seconds` = 900) Supervisor เริ่มกดได้ที่นาทีที่ 10 ช่วงที่ Supervisor กดได้จึงเท่ากับ เวลาของคำขอ − เวลาที่ Supervisor เริ่มกดได้ (ตัวอย่างนี้คือ 5 นาที) ใช้กับคำขอทุกแบบ และแทนได้ทั้งหอต้นทางและหอปลายทาง เวลาเริ่มเป็นคอลัมน์ใหม่ใน `APPROVAL_POLICY` ค่าเดียวทั้งโรงพยาบาล (Seed 600 วินาที, CHECK มากกว่า 0 และน้อยกว่า `approval_timeout_seconds`) ทุกหอเปิดให้ Supervisor เสมอ
* **Supervisor ในข้อมูล (R4-Q9 ก, R4-Q14 ก):** Role ใหม่ `SUPERVISOR` เป็นแถวข้อมูลใน `ROLE` ไม่มี Migration แต่ Seed ต้องเพิ่มแถวนี้ การอนุมัติ Supervisor กดได้หลังเวลาที่กำหนดเท่านั้น ส่วนเส้นออกจาก `MANUAL_HANDOFF` (ข้อ 6.12) Supervisor ทำได้ทุกหอทันที เพราะไม่มีเส้นตายให้นับ

## 5. Contract ของ Auto-Approval (คน 3)

**เป้าหมาย (มติทีม 2026-10-15):** ลดภาระของคนกดไม่ให้หนักเกินไป ไม่ใช่วัดความวิกฤตของคนไข้

* **เพดาน (R4-Q10, R4-Q11 ก, R4-Q19 ก):** ค่าที่ต่ำกว่าระหว่าง `ratio` × จำนวน Head Nurse ที่ Active ของหอ กับ `incoming_count` เช่น หอที่มี Head Nurse 1 คน เพดานคือ 2 หอที่มี 8 คน เพดานคือ 10
  * `ratio` คือค่าใน Policy เดิม (2) เปลี่ยนความหมายเป็น "จำนวนคำขอที่ผู้อนุมัติหนึ่งคนรับไหว" ไม่ต้องมี Migration PR 0 แก้ข้อความเรื่อง Ratio ผู้ป่วยทั้ง 3 ที่ (ข้อ 1)
  * จำนวน Head Nurse นับคนที่ Active ของหอ ไม่ได้นับเฉพาะคนที่อยู่เวรตอนนั้น Supervisor ไม่นับ เพราะกดได้หลังเวลาที่กำหนดเท่านั้น
  * **หอที่ไม่มี Head Nurse ที่ Active เลย (R4-Q27 ข):** เพดานเป็น 0 ระบบอนุมัติเองทุกรายการที่อนุมัติเองได้ ทีมรับความเสี่ยงที่รีวิวทักไว้ (ถ้า Head Nurse คนเดียวของหอถูก Deactivate การอนุมัติโดยคนของหอนั้นหายไป) Audit บันทึกจำนวนผู้อนุมัติเป็น 0 ให้ตรวจย้อนได้
* **คิวและการอนุมัติเอง (R4-Q28, R4-Q32 ก, R4-Q33 ก):** นับทุกคำขอที่รออนุมัติในหอ รวมคำขอที่ระบบอนุมัติเองไม่ได้ ถ้าคิว**เกิน**เพดาน (มากกว่า ไม่ใช่เท่ากับ) Job อนุมัติเองคำขอที่อนุมัติเองได้**ทั้งหมด**ของหอนั้น เรียงจากรอนานที่สุดก่อน แล้วหยุดเมื่อไม่เหลือคำขอที่อนุมัติเองได้ ไม่ใช่หยุดที่เพดาน
  * **ผลที่ต้องรู้ (ตามรีวิวรอบสอง):** หอที่คิวเกินเพดานแค่หนึ่งรายการ คำขอที่อนุมัติเองได้ทุกรายการของหอนั้นถูกอนุมัติโดยไม่มีคนดู นี่คือพฤติกรรมที่ทีมตอบไว้ใน R4-Q28 ต่างจากข้อเสนอแรกที่หยุดที่เพดาน
  * **ทำในรอบเดียวของ Job (R4-Q36 ก):** ไม่มีสถานะ "โหมดอนุมัติเอง" ที่เก็บข้ามรอบ และไม่มี Migration ทุกรอบ Job ล็อก `WARD` นับคิว ถ้าเกินเพดาน อนุมัติเองคำขอที่อนุมัติเองได้ทั้งหมด ถ้าไม่เกิน ไม่ทำอะไร คำตอบ R4-Q28 ที่ว่า "คำขอที่เข้ามาระหว่างนั้นถูกอนุมัติเองด้วย" จึงหมายถึงคำขอที่ Commit ก่อน Job นับคิวในรอบนั้น คำขอที่เข้ามาหลังรอบนั้นรอคนกด จนกว่าคิวจะเกินเพดานอีกครั้ง
  * ไม่อนุมัติเองให้คนข้ามหอ (`CROSS_WARD` และ `FLOAT_POOL`) และคำขอที่มีเวรต้นทางของหออื่น (ข้อ 3) ไม่ว่า `source` จะเป็นอะไร คนกดต้องดูเสมอ การตรวจเวรต้นทางตอนย้ายจริง (ข้อ 3) จึงไม่เกิดในการอนุมัติเอง
* **กันการนับคิวพร้อมกัน (R4-Q29 ก):** ล็อกแถว `WARD` ของหอปลายทางก่อนนับคิว ทั้งใน Job อนุมัติเองและใน `decide()` ที่คนกด `WARD` อยู่หน้าสุดของลำดับ Lock (`WARD` → `SHIFT` เรียงตาม ID → คำขอ → Offer → เคส → Staff) แก้ข้อ 6.11 ของ `workflow.md` พร้อม Test สอง Connection ทั้ง Job กับ Job และ Job กับคนกด
  * **[ตรวจแล้ว] เส้นทางอื่นที่ล็อก `SHIFT`:** รับ Event และปิด Merge Window (`merge_window_service.lock_shift()`), จัดคนเองและปิดเคสใน `MANUAL_HANDOFF` (`handoff_service._lock_shift()`), Job ตั้งคำขอหมดเวลา (`approval_timeout_service` ผ่าน `lock_approval_attempt()`) ไม่มีเส้นทางไหนล็อก `WARD` ตอนนี้ และหลังรอบ 4 เส้นทางเหล่านี้ยังไม่ล็อก `WARD` จึงไม่มีทางไหนล็อก `WARD` หลัง `SHIFT` และไม่เกิด Deadlock กับลำดับใหม่ Job ตั้งคำขอหมดเวลาไม่ต้องล็อก `WARD` เพราะทำให้คิวสั้นลงเท่านั้น
  * ผลข้างเคียง: `decide()` ที่คนกดทุกครั้งต้องรอ Lock ของหอเดียวกัน (ช่วงสั้น)
* **ทางเดินของการอนุมัติเอง (R4-Q12 ก):** Safety ตรวจเหมือนเดิม การตอบรับสร้างคำขอตามปกติ Job ตรวจเงื่อนไขซ้ำหลังล็อก `WARD` แล้วตัดสินผ่าน `approval_service.decide()` ตัวเดียวกับคนกด ตั้ง `approval_mode = AUTO` Actor เป็น `system` `approver_id` เป็น `NULL` บันทึกจำนวนคำขอที่รอ จำนวนผู้อนุมัติ และเพดานลง Audit ไม่ตัดสินใน Transaction ของการตอบรับ เพราะลำดับ Lock (ข้อ 1)
* **คนเห็นการอนุมัติเอง (R4-Q13 ก):** หน้า `approvals` มีรายการ "ระบบอนุมัติแทน" แยกจากรายการรอ และ Timeline ของหน้า `cases/[id]` แสดง Audit
* **กติกาที่ต้องยึด:**
  * ช่อง `role_id = None` ที่ข้ามการตรวจสิทธิ์ใช้ได้เฉพาะเมื่อตรวจเงื่อนไขผ่านใน Transaction เดียวกัน
  * Job ตัดสินคำขอหนึ่งครั้ง และไม่ตั้งคำขอที่ตัดสินแล้วเป็นหมดเวลา
  * Golden Case มี Head Nurse 1 คน เพดาน 2 และขาด 1 คน คนที่ตอบรับทีหลังเป็นตัวสำรอง ไม่มีคำขออนุมัติ คิวจึงมีไม่เกิน 1 รายการ ไม่เกินเพดาน Golden Path จึงไม่เปลี่ยน

* **กรณีเงื่อนไขใหม่ทำให้เลือกคนครบไม่ได้ (R4-Q37 ก):** **[ตรวจแล้ว]** Solver ตอนนี้ถือว่าแบบจำลองแรกมีคำตอบเสมอเมื่อมีผู้สมัคร ถ้า CP-SAT ตอบว่าไม่มีคำตอบ ระบบตั้งเป็น `MODEL_INVALID` (`optimization/solver.py`) และ `optimization_service` ถือเป็นความผิดพลาดของระบบ เคสจึงเป็น `FAILED` ตัวอย่าง: หอปลายทางต้องการ 2 คน ผู้สมัครมีแค่ A และ B จากเวรต้นทางเดียวกัน แต่ละคนผ่านกฎ แต่ข้อจำกัด R4-Q25 ให้เลือกได้คนเดียว การลดเป้าหมายตามจำนวนผู้สมัครแบบเดิมแก้ไม่ได้ **ใช้แผนบางส่วน (แก้ตามรีวิวรอบสี่):** Solver ต้องหา**กลุ่มที่เลือกได้จริงพร้อมกัน**ที่ครอบได้มากที่สุดก่อน แล้วจึงเลือกกลุ่มที่ถูกที่สุดในบรรดากลุ่มที่ครอบได้เท่ากัน ห้ามหาค่าสูงสุดของแต่ละเป้าหมายแยกกันแล้วเอามาเป็นเป้าหมายพร้อมกัน เพราะค่าสูงสุดแยกกันอาจไม่มีกลุ่มไหนทำได้พร้อมกัน ตัวอย่าง: A กับ B อยู่เวรต้นทางเดียวกันจึงเลือกได้คนเดียว A มี Skill ICU อย่างเดียว B มี Skill ER อย่างเดียว หอปลายทางต้องการทั้งสอง Skill ถ้าหาแยกกันจะได้เป้าหมาย คน 1, ICU 1, ER 1 แต่ไม่มีกลุ่มไหนทำได้ เลือก A ขาด ER เลือก B ขาด ICU **วิธีเทียบว่ากลุ่มไหนครอบได้มากกว่า (R4-Q39 ก):** ส่วนที่ขาดนับเป็นคน-นาที (จำนวนที่ขาดในแต่ละช่วงคูณความยาวของช่วงเป็นนาที แล้วรวมทุกช่วง) เทียบตามลำดับ ดูจำนวนคนที่ขาดก่อน ถ้าเท่ากันดู Role ที่ขาด ถ้ายังเท่ากันดู Skill ที่ขาด ถ้ายังเท่ากันอีกใช้ลำดับเดิมของ Solver (คะแนนน้อยสุด, คนน้อยสุด, รหัสพนักงานน้อยสุด) ในตัวอย่าง ICU กับ ER ทั้งสองกลุ่มขาด Skill เท่ากันจึงตัดสินด้วยคะแนนเดิม ขั้นที่เพิ่มใช้เพดานเวลาเดิมร่วมกับขั้นอื่น ถ้าเวลาหมดตอนหากลุ่มที่ครอบได้มากที่สุด ใช้กลุ่มที่ดีที่สุดที่หาได้ (`FEASIBLE`) และถ้ายังไม่มีกลุ่มไหนเลย ใช้ทางเดิม `SOLVER_TIMEOUT` ไป `MANUAL_HANDOFF` **ถ้าครอบได้มากที่สุดเป็น 0** (ไม่มีใครช่วยช่วงไหนได้เลย) ใช้ทางเดิม `NO_FEASIBLE_PLAN` ไป `MANUAL_HANDOFF` **[ตรวจแล้ว]** Handler `optimize` มีทางนี้อยู่แล้ว ในตัวอย่างแรกของข้อนี้ (ต้องการ 2 คน มีแค่ A และ B จากเวรต้นทางเดียวกัน) Solver เลือก A หรือ B หนึ่งคน ส่ง Wave ไป แล้ว Gap ที่เหลือเดินต่อตามกติกาเดิม (Wave ถัดไป หรือ `MANUAL_HANDOFF` เมื่อหมดคน) ตรงกับหลักเดิมที่ผู้สมัครน้อยก็ยังได้ Wave ที่กว้างที่สุด ขั้นที่เพิ่มต้องอยู่ในเพดานเวลาเดิม ห้ามให้เคสเป็น `FAILED` เพียงเพราะเงื่อนไขใหม่ปิด Gap ไม่ได้ PR ที่เพิ่มเงื่อนไข (T4 สำหรับรายช่วง และ C2 สำหรับเวรต้นทาง) ต้องมี Test ของกรณีนี้ รวมกรณีผู้สมัครที่เลือกพร้อมกันไม่ได้และครอบคนละ Skill หรือคนละช่วง (ตัวอย่าง ICU กับ ER) ซึ่งต้องได้แผนบางส่วนที่ถูกต้อง ไม่ใช่ `MODEL_INVALID` หรือ `FAILED`
* ผู้สมัครที่ครอบได้บางช่วง ห้ามถือว่าปิด Gap ทั้งหมด ในตัวอย่าง ถ้าหอ A ขาดตั้งแต่ 00:00 Y ปิด Gap ทั้งหมดคนเดียวไม่ได้ เพราะช่วง 00:00 ถึง 02:00 ไม่มีคนครอบ แต่ Y ถูกเลือกให้ช่วยช่วงหลังได้ตามแผนบางส่วน (R4-Q37) และช่วงแรกยังเป็น Gap ต่อไป
* ช่วงที่เลือกเก็บใน Plan (`fill_targets` และ `TargetCredit` มีช่องช่วงเวลา) และส่งต่อถึง Offer คำขออนุมัติ และ Roster ให้ตรงกัน ไม่กลับไปใช้เวลาเต็มเวรเอง การเลือก Wave ถัดไป (`wave_service`) ก็เลือกตามช่วงแบบเดียวกัน

**3. Safety (PR T1)**
* **[ตรวจแล้ว]** จุดเดียวที่ถือว่าทำงานทั้งเวรคือ `hard_rule_service._check()` ที่สร้าง `proposed = ShiftSlot(shift.id, shift.start_at, shift.end_at)` แก้ที่ข้อมูลเข้า ไม่แก้ตัวกฎ
  * เก็บช่วงที่มาทำได้ในรายชื่อผู้สมัคร (`cover_start_at`, `cover_end_at` ใน `CANDIDATE_ITEMS`) ตอนเขียน Plan
  * `_check()` สร้าง `proposed` จากช่วงนี้แทนเวลาของเวร
  * Roster ที่ใช้ตรวจตัดแถวของเวรต้นทางให้จบที่ `cover_start_at` ในตัวอย่าง เวรหอ B ของ Y กลายเป็น 00:00 ถึง 02:00
  * กฎเวรชน ชั่วโมง และเวลาพักจึงเห็นหอ B 00:00 ถึง 02:00 และหอ A 02:00 ถึง 08:00 ไม่ทับกัน รวม 8 ชั่วโมง
* ตอนวางแผนและตอน Safety ใช้ `check_items()` ตัวเดียวกันและอ่านช่วงที่เก็บในรายชื่อ ผลจึงตรงกัน Safety ห้ามคำนวณช่วงใหม่เอง ถ้าเวลาย้ายจริง (ข้อ 3) ช้ากว่าช่วงที่วางแผนไว้ การตรวจตอนย้ายจริงใช้เวลาย้ายจริง และช่วงของหอปลายทางก่อนเวลาย้ายยังเป็น Gap ต่อไป
* **ช่วงทำงานต่อเนื่องตอนวางแผนและตอน Safety (แก้ตามรีวิวรอบสาม):** ตอนวางแผน ตอน Safety และตอนตรวจซ้ำตอนย้ายจริง แถวปลายทางยังไม่มี จึงยังไม่มีลิงก์ในข้อ 4 ตัวสร้างข้อมูลที่ใช้ร่วมกันต้องเอาลิงก์มาจาก**เวรต้นทางของผู้สมัคร** (คอลัมน์เวรต้นทางใน `CANDIDATE_ITEMS` ซึ่ง T1 เพิ่มพร้อมช่วงที่มาทำได้ **[ตรวจแล้ว]** ตอนนี้ `CANDIDATE_ITEMS` มีแค่ Plan, คน, อันดับ, `source`, เวรที่เสนอ และ Working Time Snapshot ยังไม่มีคอลัมน์นี้) แล้วรวมส่วนต้นทางที่ถูกตัดกับช่วงของปลายทางเป็นการปฏิบัติงานครั้งเดียว ก่อนตรวจกฎเวลาพักและเวรติดกัน **[ตรวจแล้ว]** `insufficient_rest()` ข้ามแค่เวรที่ทับกัน ส่วนเวรที่ต่อกันพอดีถือว่าพัก 0 ชั่วโมง ถ้าไม่รวม ตัวอย่าง Y ในข้อนี้จะถูกปฏิเสธทั้งตอนวางแผนและตอน Safety การรวมนี้อยู่ใน T1 พร้อม Test ของตัวอย่าง Y ซึ่งใส่ข้อมูลเวรต้นทางลงรายชื่อผู้สมัครเองใน Test เพราะยังไม่มีผู้สมัครจากการย้ายจริงจนกว่า C2 และ C3 จะเข้า
* T1 ส่งได้ก่อนโดยใช้ช่วงเต็มเวร พฤติกรรมเดิมไม่เปลี่ยน

**4. ช่วงทำงานต่อเนื่อง (ใช้แบบของคน 3, PR T2 บันทึกลิงก์ของแถว Roster, PR T1 รวมช่วงตอนวางแผน, PR C3 ใช้ตอนย้ายกลางเวร)**
* แถวปลายทางบันทึกว่าย้ายมาจากแถวต้นทางไหน ระบบรวมสองแถวเป็นการปฏิบัติงานครั้งเดียว**เฉพาะคู่ที่บันทึกไว้**
* **ไม่ใช้วิธีรวมแถวที่ต่อกันพอดีเอง** (ข้อเสนอเดิมของคน 2) เพราะ **[ตรวจแล้ว]** กฎเวลาพักตอนนี้ปฏิเสธเวรที่ต่อกันพอดีโดยไม่ได้ย้าย เช่น 16:00 ถึง 00:00 แล้ว 00:00 ถึง 08:00 (ทำงาน 16 ชั่วโมงติด) ถ้ารวมเองทุกคู่ที่ต่อกัน กฎนี้จะไม่ปฏิเสธอีก
* กฎเวลาพักตรวจระหว่างการปฏิบัติงานแต่ละครั้ง ไม่ตรวจระหว่างสองส่วนของการย้าย ชั่วโมงรายวันและรายสัปดาห์รวมเวลาทั้งสองส่วนโดยไม่นับซ้ำ และการนับเวรติดกันนับการปฏิบัติงานครั้งนี้ครั้งเดียว ไม่เพิ่มเพราะเปลี่ยนหอ

## 9. สิ่งที่ยังไม่ได้ตรวจ

* ยังไม่ได้ลองขยาย Pool จริง จึงยังไม่รู้ว่า Solver ใช้เวลาเท่าไรเมื่อ Pool ใหญ่ขึ้นหลายหอ (เพดานเวลาเดิม 3 วินาที ข้อ 6.14 ของ `workflow.md`)
* ยังไม่ได้ตรวจว่าหน้า `approvals`, `handoff` และ `cases/[id]` แสดงหอบ้านของผู้สมัครหรือไม่ (งานของคน 1 ตาม R4-Q1 ก)
* ยังไม่ได้ตรวจว่าการเปลี่ยนแถว Roster ของเวรต้นทาง (R4-Q4 ค) ไปกระทบเส้นทางรับ Event `ASSIGNMENT_CANCELLED` และ Merge Window ของหอต้นทางยังไง
* `event_service` ตรวจแค่ Role ของ Head Nurse ตอนรับ Event ที่ Head Nurse แจ้ง ไม่ตรวจว่าเป็นหอของเวร ยังไม่ได้ตรวจว่าตั้งใจแบบนี้หรือไม่ ถ้า R4-Q23 ให้ Supervisor แจ้ง Event ได้ ต้องตรวจเรื่องนี้ก่อน
* Gap ตามช่วงเวลา (R4-Q34 ข) ยังไม่ได้ลองกับข้อมูลจริง และยังไม่ได้ตรวจว่ากระทบเกณฑ์ของ Merge Window (Threshold) และ `effective_minimum` ยังไง
* ยังไม่ได้วัดว่า Solver รายช่วงใช้เวลาเท่าไรเมื่อมีหลายช่วงและหลายหอ ด่านของ T4 จึงต้องวัดเวลาด้วย (ข้อ 5.1 ข้อ 2)
