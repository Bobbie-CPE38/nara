## 3. LangGraph (คน 1)

**เป้าหมายที่เสนอ (R5-Q4 ก):** เปลี่ยนการเดินใน `_run_round()` เป็น Graph ของ LangGraph โดยไม่เปลี่ยนพฤติกรรม
* หนึ่ง Node ต่อหนึ่ง Handler ใน `HANDLERS` และ Edge ตาม `ALLOWED_TRANSITIONS`
* สถานะเคสใน DB ยังเป็นความจริงเดียว (D1) ไม่ใช้ Checkpointer ของ LangGraph เก็บสถานะ เพราะจะมีสองที่ที่บอกว่าเคสอยู่ไหน
* ทางเข้าทั้งสี่ (`advance()`, `resume()`, `recompute()`, `leave_handoff()`) และลายเซ็นของมันไม่เปลี่ยน ผู้เรียกทุกที่ไม่ต้องแก้
* Savepoint, Commit ครั้งเดียวต่อรอบ, `FAILED` พร้อม `WORKFLOW_FAILED` และการส่ง LINE หลัง Commit อยู่นอก Graph เหมือนเดิม
* การตรวจของ `_run_step()` (Handler เปลี่ยนสถานะเอง, คืน `FAILED`, `wait` ไม่ตรงกับสถานะ, Transition ที่ไม่อนุญาต, เกินจำนวนขั้น) ยังได้ `WorkflowError` เหมือนเดิม

**สิ่งที่ต้องพิสูจน์ว่าไม่เปลี่ยน:** Test เดิมทั้งหมดผ่านโดยไม่แก้ และมี Test ใหม่ที่เทียบลำดับแถว `CASE_STATUS_CHANGED` ของ Golden Case และ Scenario ของรอบ 4 ระหว่างตัวเดิมกับตัวใหม่ (R5-Q6)

**ทำไมต้องตกลงก่อน:** `next-move.md` เตือนว่า LangGraph แตะไฟล์กลางที่ทุก Handler พึ่ง ถ้า PR ของคน 2 และคน 3 แก้ Handler พร้อมกัน จะชนกัน ลำดับ PR อยู่ในข้อ 7

## 4. `NO_SHOW` (คน 2)

**ทาง check-in (R5-Q7 ข, R5-Q8 ก):**
* พยาบาลกด check-in เองในหน้า `/me/offers` หรือทาง LINE Route รับตัวตนจาก `X-Demo-User` อย่างเดียวแบบ Route อื่นของหน้านี้ check-in ทาง LINE เป็นงานของ H2 (คน 3) เป็นคำสั่งของ Webhook ที่ระบุตัวคนจากบัญชี LINE ที่ผูกแล้วเท่านั้น และเรียกฟังก์ชันกลางของ check-in ตัวเดียวกับ Route ของหน้าเว็บ
* Demo จำลองการ check-in ของตัวละครได้ผ่าน Route ใต้ `/demo/` และหน้า `demo/control` (R5-Q23 ก) เพราะคนดู Demo ไม่ได้สลับตัวตนทีละคน ชื่อและข้อความบนหน้าบอกชัดว่าเป็น "จำลองการ check-in" Route ของพยาบาลกับ Route จำลองเรียกฟังก์ชันกลางตัวเดียว
* การจำลองเขียน Audit ที่บอกว่า check-in นี้มาจากการจำลอง (Action และ payload ตกลงใน PR 0) แถวจาก Route ของพยาบาลบอกว่ามาจากตัวผู้กด
* **นาฬิกา:** `check_in_at` มาจาก `app.core.clock.now()` ตัวเดียวกับที่ Job ใช้ตรวจ `NO_SHOW` ไม่ใช่เวลาของเครื่อง **[ตรวจแล้ว]** Demo Clock หยุดนิ่งหลัง `POST /demo/reset` และเดินด้วย `POST /demo/clock/advance` ถ้า check-in อ่านเวลาเครื่อง คนที่กดแล้วอาจถูกนับเป็น `NO_SHOW` (ข้อเสนอของคน 2)
* `ATTENDANCE` เพิ่ม `shift_id` (NULL ได้) check-in จับคู่กับเวรตรงตัว
* Seed มี check-in ของทุกคนในเวรที่เริ่มแล้ว ไม่งั้นเลื่อน Clock แล้วทุกคนเป็น `NO_SHOW`
* **Migration ของ `ATTENDANCE.shift_id`:** NULL ได้ ไม่ Backfill **[ตรวจแล้ว]** Seed ไม่มีแถว `ATTENDANCE` แต่ Test เดิมสร้างแถวโดยไม่มีเวร (`test_case_score.py`, `test_hard_rule_schema.py`, `test_optimize.py`, `test_working_time_service.py`) แถวที่ไม่มี `shift_id` นับ OT ตามเดิม แต่ไม่นับเป็น check-in ของเวรใด
* **กันซ้ำ:** Unique (`staff_id`, `shift_id`) เฉพาะแถวที่มี `shift_id` กดซ้ำได้แถวเดิม ไม่สร้างแถวใหม่
* **check-in นอกช่วง:** ก่อนเวรเริ่มเกินเวลาที่ PR 0 กำหนด หรือหลังเวรจบ ถูกปฏิเสธ ใช้กติกาขอบเวลาตัวเดียวกับตัวตรวจ `NO_SHOW`
* **คนที่ถูกย้ายกลางเวร:** check-in ผูกกับเวรไหน (ต้นทางหรือปลายทาง) และ Handover ผูกกับแถว Roster แถวไหน ตกลงใน PR 0 เพื่อไม่ต้องแก้ความสัมพันธ์ย้อนหลัง (ข้อเสนอของคน 3)
* **สิทธิ์:** พยาบาลกดได้แค่ของตัวเอง ไม่มีใคร check-in แทนพยาบาลในการใช้งาน การจำลองมีแค่ใต้ `/demo/` ซึ่งต้องเข้าไม่ได้จากช่องทางสาธารณะของระบบจริง **[ตรวจแล้ว]** ด่าน `dev/line-webhook-proxy` เปิดแค่ Path ของ Webhook ทุก Path อื่นได้ `404` อยู่แล้ว แต่ `check_gate.py` และ `test_proxy.py` ทดสอบแค่ `/demo/reset` N1 เพิ่ม Route จำลองตัวใหม่ในรายการที่สองไฟล์นี้ตรวจ ด่านของเครื่อง AWS (รอบ 6 PR D) ต้องกันทุก Path ใต้ `/demo/` เช่นกัน

**ตัวตรวจ (R5-Q9 ก, R5-Q10 ก, R5-Q17 ก):**
* เวลาผ่อนผัน 15 นาทีเป็นค่าคงที่ใน `core/constants.py`
* **ทันหรือสาย ตัดสินจากเวลาของ check-in:** check-in **ทัน** เมื่อ `check_in_at <= start_at + เวลาผ่อนผัน` ไม่ใช่แค่มีแถว check-in อยู่ (ข้อเสนอของคน 2)
* Job ตรวจเวรที่ `Backend Clock > start_at + เวลาผ่อนผัน` (มากกว่าเท่านั้น ตรงเส้นตายพอดียังไม่ตั้ง `NO_SHOW`) และยังไม่จบ หาแถว Roster `ASSIGNED` ที่ไม่มี check-in **ที่ทัน** ของเวรนั้น และไม่มีแถว `STAFF_UNAVAILABILITY` ที่ทับเวรนั้นแล้ว
* **check-in สายที่มาก่อน Job รอบถัดไป:** เช่น check-in ตอน +16 นาที แล้ว Job รันตอน +16 นาที 20 วินาที Job ยังตั้ง `NO_SHOW` เพราะ check-in นี้ไม่ทัน แล้วเดินทางมาสายต่อทันทีใน Transaction เดียวกัน โดยใช้ `check_in_at` ที่มีอยู่ ถ้า check-in สายมาหลัง `NO_SHOW` ตั้งแล้ว Route เดินทางมาสายเอง ทั้งสองทางเรียกฟังก์ชันเดียวกัน
* สร้างแถว `reason = NO_SHOW`, Event `STAFF_UNAVAILABLE` และ Audit `UNAVAILABILITY_CREATED` (payload มี `reason`, ผู้เขียนเป็น Actor ของ Job) แล้วเข้า Merge Window เหมือนการลากะทันหัน
* ตรวจซ้ำกี่ครั้งก็ได้ผลเดียว (Job สองตัวพร้อมกันได้แถวเดียว)
* check-in กับ Job ตรวจ `NO_SHOW` ล็อกตามลำดับเดียวกันก่อนตัดสิน: `SHIFT` → แถว `ROSTER_ASSIGNMENT` ของคนนั้น → (ถ้าเดินทางมาสายต่อ) `APPROVAL_REQUEST` และ `CANDIDATE_OUTREACH` ที่จะยกเลิก → เคส → `STAFF` ตรงกับลำดับเดิมของข้อ 6.11 (`SHIFT` / `ROSTER_ASSIGNMENT` → คำขอหรือ Offer → เคส → `STAFF`) และเหมือนการปิด Window ที่ล็อก `SHIFT` ก่อนแก้ Roster อีกฝั่งตรวจซ้ำหลังล็อก ไม่มี Event ซ้ำ และไม่ยกเลิกเวรผิดคน (ข้อเสนอของคน 3 และคน 2)
* `NO_SHOW` หลายเวรติดกันได้แถวใหม่ทุกเวร และแจ้งลาย้อนหลังไม่เปลี่ยน `reason` จาก `NO_SHOW` (กติกาเดิมของ `database-schema.md`)

**ผลต่อ Roster (R5-Q11 ข):** แถวของคนที่ไม่มาเป็น `CANCELLED` เมื่อ check-in มาสาย ระบบสร้างแถวใหม่ที่ `actual_start_at` = เวลา check-in และลด `end_at` ของแถว `NO_SHOW` เป็นเวลา check-in ตามกติกาเดิม

**Handover ของแถวใหม่ตอนมาสาย:** ถ้าแถวที่ถูกยกเลิกมี Handover (คนนั้นเป็นคนแทน) แถวใหม่ได้ Handover แถวใหม่หนึ่งแถวผ่านฟังก์ชันกลาง เนื้อหาสร้างใหม่ด้วยช่วงเวลาจาก `check_in_at` ส่วน Handover ของแถวเก่าไม่ใช้งานแล้วแต่อยู่ในประวัติ ถ้าแถวที่ถูกยกเลิกไม่มี Handover (คนเดิมของเวร) แถวใหม่ไม่ได้ Handover (ข้อเสนอของคน 3)

**มาสายหลังมีคนแทนแล้ว (R5-Q12, R5-Q22 ก):** หลัง check-in ประเมิน Gap ที่เหลือก่อน แล้วตามขั้นของคนแทน
1. ได้ Offer แล้วแต่ยังไม่ตอบ: ยกเลิกเฉพาะ Offer ที่เกินจำนวนที่เคสยังขาดหลังคนที่มาสายถูกนับ
2. ตอบรับแล้วรออนุมัติ: ยกเลิกเฉพาะคำขอที่เกินจำนวนที่เคสยังขาดหลังคนที่มาสายถูกนับ
3. ได้เวรแล้วแต่ยังไม่ check-in: ไม่ยกเลิก
4. check-in แล้ว: ไม่ยกเลิก

คนแทนที่ได้เวรแล้วจึงอยู่ต่อเสมอ และเวรเกินคนได้ Head Nurse ตัดสินเองว่าจะให้ใครกลับ (ยังไม่มีปุ่มสำหรับเรื่องนี้ในรอบ 5) เหตุผลและ Audit ของการยกเลิกในขั้น 1 และ 2 ตกลงใน PR 0

เคสไม่หยุดหาคนของ Gap ที่ยังขาด (R5-Q22 ก) PR 0 เขียนกติกาว่าเมื่อเกินความต้องการ ยกเลิก Offer หรือคำขอของใครก่อน

**ลำดับ PR:** การสร้างแถวใหม่ตอนมาสายใช้ฟังก์ชันกลางของ H1 ซึ่งตัดสินเองว่าต้องสร้าง Handover ไหมตามกติกาข้างบน N2 ห้ามสร้างแถว Roster เอง (ข้อเสนอของคน 2)

## 5. Handover (คน 3)

**เนื้อหา (R5-Q13 ก):** ข้อมูลจาก DB ล้วน เก็บใน `content` เป็น jsonb ที่มีรูปตายตัว เช่น เวร หอ เหตุที่ขาด (ลา, ยกเลิก, `NO_SHOW`) ช่วงเวลาที่ต้องมาทำ จำนวนผู้ป่วย Requirement ของเวร และคนที่อยู่เวรด้วยกัน รูปของ `content` ตกลงใน PR 0 เพราะหน้าเว็บของคน 1 ต้องอ่าน

**เมื่อไรสร้าง (R5-Q14):**
* หนึ่งแถวต่อหนึ่ง `roster_assignment_id` ของคนที่ได้เวรแทน สร้างใน Transaction เดียวกับการจัดเวร และเขียน Audit `HANDOVER_GENERATED`
* ทุกทางที่สร้างเวรเรียกฟังก์ชันกลางตัวเดียว ไม่มีทางไหนเขียน Handover เอง มีห้าทาง: อนุมัติ, อนุมัติเอง, จัดเองใน `MANUAL_HANDOFF`, การย้าย และ**แถวใหม่ตอนมาสาย** สี่ทางแรกสร้าง Handover หนึ่งแถวเสมอ ทางที่ห้าสร้างเฉพาะเมื่อแถวที่ถูกยกเลิกมี Handover (ข้อ 4)
* เพิ่ม `STRUCTURED_HANDOVER.roster_assignment_id` เป็น NOT NULL พร้อม Unique Constraint กันการสร้างซ้ำ ทั้งเมื่อเรียกซ้ำและเมื่อสอง Connection จัดเวรพร้อมกัน **[ตรวจแล้ว]** ตารางไม่มีแถวเลยเพราะไม่เคยมีผู้เขียน จึงตั้ง NOT NULL ได้โดยไม่ต้อง Backfill
* ย้ายกลางเวรซ้ำได้ Handover แถวใหม่ทุกครั้ง หน้าเว็บแสดงอันล่าสุดก่อน (R5-Q20 ก)
* Handover เก็บไว้ไม่ลบ ไม่มีคอลัมน์สถานะ (R5-Q21 ก) **Handover ใช้งานอยู่** เมื่อแถว Roster เป็น `ASSIGNED` **และ** `Backend Clock < effective_end_at` (`actual_end_at` ถ้ามี ไม่งั้นเวลาจบเวร) เท่านั้น ไม่ใช่ตรวจแค่สถานะ เพราะ **[ตรวจแล้ว]** C3 เก็บแถวต้นทางของการย้ายกลางเวรเป็น `ASSIGNED` และตั้ง `actual_end_at` เป็นเวลาย้าย (ข้อเสนอของคน 3)
* Handover ที่ไม่ใช้งานแล้วหายจากรายการปัจจุบันของหน้าเว็บและหยุดส่งทาง LINE แต่ยังอยู่ในประวัติ
* เวรที่ยังไม่เริ่มอ่าน Handover ได้เลยเพื่อเตรียมตัว ไม่ต้องรอเวลาเริ่ม
* แนวทางของรอบ 6: ถ้าใช้ LLM เขียนข้อความ ให้บันทึก `PENDING` ใน Transaction นี้แล้วประมวลผลภายหลัง LLM ล้มต้องไม่ย้อนการจัดเวร

**ใครเห็น (R5-Q15 ข, R5-Q16 ก):** คนที่มาแทนเห็นในหน้า `/me/offers` และได้ทาง LINE Head Nurse เห็นในหน้าเคส การย้ายคนไม่มี Handover ฝั่งต้นทาง

**ส่งทาง LINE (H2):** สร้างแถว Handover ใน Transaction ของการจัดเวร ส่ง LINE หลัง Commit เท่านั้น ส่งล้มไม่ย้อนการจัดเวรและ Handover ไม่หาย ตรวจว่า Handover ยังใช้งานอยู่ซ้ำก่อนส่งและทุกครั้งที่ลองใหม่ H2 ขยาย `line_delivery_service` เองให้ส่ง Handover ได้ บันทึกความตั้งใจส่งใน Transaction เดียวกับ Handover แล้ว Job ส่งต่อ ได้ Retry key, ลองไม่เกิน 3 ครั้ง และการกู้หลังเครื่องล่มแบบเดียวกับ Offer (R5-Q24 ก) มี Migration ของที่เก็บสถานะการส่ง

## 7.1 ข้อตกลงที่ PR 0 ต้องเขียน (ตกลงแล้ว 2026-10-16)

1. **ขอบเวลาของ check-in:** รับ check-in ตั้งแต่ 60 นาทีก่อนเวรเริ่มจนถึงเวลาจบเวร ค่า 60 นาทีเป็นค่าคงที่ใน `core/constants.py` ที่เดียวกับเวลาผ่อนผัน check-in หลังเวลาผ่อนผันยังรับ แต่นับเป็นมาสาย ฟังก์ชันกลางตัวเดียวตัดสินขอบเวลา ทั้ง Route ของ N1 และ Job ของ N2 เรียกตัวนี้
2. **check-in แข่งกับ Job และเส้นตาย:** ทั้งสองทางล็อก `SHIFT` แล้วแถว Roster ของคนนั้นในเวรนั้นก่อนตัดสิน (ลำดับเต็มในข้อ 4) ฝั่งที่ได้ล็อกทีหลังอ่านข้อมูลใหม่หลังล็อก ลำดับ Lock ต้องเข้ากับข้อ 6.11 **ที่เส้นตายพอดี (`Backend Clock == start_at + เวลาผ่อนผัน`) Job ยังไม่ตั้ง `NO_SHOW`** Job ตั้งได้เมื่อ `Backend Clock > start_at + เวลาผ่อนผัน` เท่านั้น check-in ทันเมื่อ `check_in_at <= start_at + เวลาผ่อนผัน`
3. **คนที่ถูกย้ายกลางเวร:** check-in ที่ทันของแถวใดแถวหนึ่งใน**โซ่ของการย้ายที่บันทึกไว้** (ตามลิงก์จากแถวปลายทางย้อนไปจนถึงแถวแรกของงานต่อเนื่อง) นับต่อไปถึงทุกแถวถัดไปในโซ่ เช่น check-in ที่ X แล้วย้าย X → Y → Z แถว Z ถูกยกเว้นแม้ Y ไม่มี check-in ของตัวเอง ไม่สร้างแถว `ATTENDANCE` หรือ OT ซ้ำ (ข้อเสนอของคน 3) **แต่ห้ามข้ามการตรวจแถวปลายทางโดยไม่มีเงื่อนไข** ถ้าไม่มี check-in ที่ทันในโซ่เลย (เช่น ย้ายทั้งเวรก่อนเวรต้นทางเริ่ม จึงไม่เคย check-in ที่ต้นทาง) แถวปลายทางต้องถูกตรวจตามปกติ Handover ผูกกับแถวปลายทาง
4. **รูปของ `content`:** ตาราง Key และชนิดของค่าใน `workflow.md` แบบเดียวกับรูปของ API ในข้อ 9 มีเลขเวอร์ชันของรูปข้อมูล เวลาเป็น ISO 8601 พร้อม timezone ระบุ Key ที่ว่างได้
5. **Audit ของ check-in:** Action เดียว (เช่น `ATTENDANCE_CHECKED_IN`) ใส่ `source` = `SELF` หรือ `SIMULATED` ใน payload ผู้เขียนเป็นพยาบาลเมื่อกดเอง และเป็น Actor ของ Demo เมื่อจำลอง ค่าใหม่เพิ่มใน `enums.py` ใน PR 0
6. **ยกเลิก Offer หรือคำขอของใครก่อน เมื่อมาสายแล้วเกิน:** **ความครอบคลุมมาก่อนขั้นและอันดับ** เก็บชุดคนที่ปิด Gap รายช่วงที่เหลือได้มากที่สุดก่อน (นับตาม Gap รายช่วงของรอบ 4 คนที่ครอบไม่เต็มช่วงไม่ได้ปิดช่วงที่ไม่ได้ครอบ) ถ้าครอบได้เท่ากัน เก็บคนที่ไปไกลกว่า (คำขอที่รออนุมัติก่อน Offer ที่ยังไม่ตอบ) ถ้ายังเท่ากัน เก็บคนที่อันดับใน Plan ดีกว่า ที่เหลือยกเลิกด้วยเหตุผลใหม่ (เช่น `NO_LONGER_NEEDED`) และเขียน Audit การตัดสินว่า Gap ปิดแล้วใช้กติกาเดียวกับ `recompute()`
