## กลุ่มที่ 2: LangGraph (คน 1)

### R5-Q4 LangGraph ทำอะไรในระบบนี้

**ที่มา:** D2 บอกว่า Orchestrator ออกแบบให้ห่อด้วย LangGraph ได้โดยไม่แก้ Handler แต่เอกสาร "ทางเลือก" ที่ `workflow.md` ข้อ 12 อ้างไม่มีใน repo

**ก. ห่อแค่การเดินระหว่าง Handler พฤติกรรมไม่เปลี่ยน DB ยังเป็นความจริงเดียว (แนะนำ)**
- ทำอะไร: Node ละ Handler, Edge ตาม `ALLOWED_TRANSITIONS`, ไม่ใช้ Checkpointer ทางเข้าทั้งสี่ไม่เปลี่ยน
- ข้อดี: ได้ Graph ที่แสดงและอธิบายได้ ไม่เสี่ยงกับ D1, D3, D4, D11 และเปิดทางให้ LLM Node ของรอบ 6
- ข้อเสีย: ได้ประโยชน์ทางการใช้งานน้อย งานส่วนใหญ่คือพิสูจน์ว่าไม่มีอะไรเปลี่ยน

**ข. ใช้ Checkpointer ของ LangGraph เก็บสถานะด้วย**
- ข้อดี: ใช้ความสามารถ Resume ของ LangGraph เต็มที่
- ข้อเสีย: มีสองที่ที่บอกว่าเคสอยู่ไหน ขัดกับ D1 ต้องเขียน Contract ใหม่หลายข้อ

**ค. ไม่ใช้ LangGraph เขียนเหตุผลไว้ และให้คน 1 ทำงานอื่น**
- ข้อดี: ไม่เพิ่ม Dependency และไม่เสี่ยงไฟล์กลาง
- ข้อเสีย: ไม่ตรงกับแผนที่เสนอไว้ (ถ้าการแข่งขันต้องการเห็น Agent Framework)

### R5-Q5 เพิ่ม Dependency ยังไง

**ก. เพิ่ม `langgraph` แบบล็อกรุ่นตรงตัว และบอกใน PR ว่าทุกคนต้อง Restart Backend (แนะนำ)**
- ข้อดี: ทุกเครื่องได้รุ่นเดียวกัน
- ข้อเสีย: ต้องอัปเดตเองเมื่อจะเปลี่ยนรุ่น

**ข. ล็อกแค่รุ่นหลัก (`>=x,<x+1`)**
- ข้อดี: ได้ Patch อัตโนมัติ
- ข้อเสีย: เครื่องที่ติดตั้งคนละวันได้คนละรุ่น

### R5-Q6 พิสูจน์ว่าพฤติกรรมไม่เปลี่ยนยังไง

**ก. Test เดิมทั้งหมดผ่านโดยไม่แก้ และ Test ใหม่เทียบลำดับแถว `CASE_STATUS_CHANGED` ของ Golden Case และ Scenario ของรอบ 4 กับค่าที่บันทึกจากโค้ดก่อน G (แนะนำ)**
- ข้อดี: จับการเปลี่ยนลำดับที่ Test เดิมไม่ได้ตรวจ
- ข้อเสีย: ต้องบันทึกค่าตั้งต้นก่อนเริ่มแก้

**ข. Test เดิมผ่านอย่างเดียว**
- ข้อดี: ไม่มีงานเพิ่ม
- ข้อเสีย: Test เดิมตรวจสถานะสุดท้ายเป็นส่วนใหญ่ ลำดับกลางทางเปลี่ยนได้โดยไม่มีใครเห็น

## กลุ่มที่ 3: `NO_SHOW` (คน 2)

### R5-Q7 check-in มาจากไหน

**ที่มา:** `ATTENDANCE` ไม่มี Route หรือ Service ใดเขียน และ Seed ไม่มีแถว ถ้าไม่มีทางบันทึก ทุกคนจะเป็น `NO_SHOW` ทุกเวร

**ก. Route ของ Demo บันทึก check-in และปุ่มในหน้า `demo/control` (แนะนำ)**
- ข้อดี: ทดสอบได้ทันที ไม่ต้องมีระบบภายนอก
- ข้อเสีย: Seed ต้องมี check-in ของทุกคนในเวรที่เริ่มแล้ว ไม่งั้น Demo เลื่อน Clock แล้วทุกคนเป็น `NO_SHOW`

**ข. พยาบาลกด check-in เองในหน้า `/me/offers` หรือ LINE**
- ข้อดี: ใกล้การใช้งานจริง
- ข้อเสีย: งานหน้าเว็บและ LINE เพิ่ม และ Demo ยังต้องมีทางกดแทนคนอื่นอยู่ดี

**ค. ถือว่าทุกคนมา ยกเว้นคนที่ Demo สั่งว่าไม่มา**
- ข้อดี: ไม่ต้องสร้าง check-in ให้ทุกคน
- ข้อเสีย: ไม่ใช่ "ไม่มี check-in" ตามกติกาเดิม และใช้ `ATTENDANCE` ไม่ได้

### R5-Q8 จับคู่ check-in กับเวรยังไง

**ที่มา:** `ATTENDANCE` ไม่มี `shift_id` มีแค่ `staff_id` และเวลา

**ก. เพิ่ม `ATTENDANCE.shift_id` (NULL ได้) (แนะนำ)**
- ข้อดี: ไม่ต้องเดาจากเวลา เวรติดกันหรือเวรที่ถูกย้ายกลางเวรไม่สับสน
- ข้อเสีย: มี Migration และแถวเก่า (ถ้ามี) ไม่มีค่า

**ข. จับจากเวลา: check-in ในช่วง `[start_at - X, start_at + เวลาผ่อนผัน]` นับเป็นของเวรนั้น**
- ข้อดี: ไม่มี Migration
- ข้อเสีย: ต้องตกลง X และเวรที่ต่อกันพอดีได้ check-in เดียวกันสองเวร

### R5-Q9 เวลาผ่อนผันเก็บที่ไหน

**ก. ค่าคงที่ 15 นาทีใน `core/constants.py` (แนะนำ)**
- ข้อดี: ตรงกับสมมติฐานเดิม ไม่มี Migration
- ข้อเสีย: แก้ต่อหอไม่ได้

**ข. คอลัมน์ใหม่ใน Policy ที่ Head Nurse แก้ได้**
- ข้อดี: แต่ละหอตั้งเองได้
- ข้อเสีย: Migration และหน้า Policy เพิ่ม

### R5-Q10 เมื่อตรวจพบ `NO_SHOW` แล้ว Event เข้า Merge Window ไหม

**ที่มา:** การลากะทันหันเข้า Merge Window ก่อนเปิดเคส แต่ `NO_SHOW` เกิดหลังเวรเริ่มแล้วเสมอ การรอ Window ทำให้หาคนช้าลงอีก

**ก. เข้า Window เหมือนการลา (ใช้ `merge_window_seconds` ของเวร)**
- ข้อดี: ทางเดียวกับการลา ไม่มีกรณีพิเศษ หลายคนไม่มาพร้อมกันได้เคสเดียว
- ข้อเสีย: ช้าลงเท่าความยาวของ Window

**ข. ปิด Window ทันทีสำหรับ `NO_SHOW`**
- ข้อดี: เปิดเคสเร็วที่สุด
- ข้อเสีย: คนที่ไม่มาสองคนในรอบตรวจเดียวกันต้องรวมเป็นเคสเดียวเอง ไม่งั้นได้สองเคส

### R5-Q11 แถว Roster ของคนที่ไม่มาเป็นอะไร

**ที่มา:** การลาตั้งแถวทั้งแถวเป็น `CANCELLED` แต่รอบ 4 มีเวลาเริ่มและจบจริงในแถวแล้ว และกติกาเดิมให้ "มาสาย" ลด `end_at` ของการไม่พร้อมเป็นเวลา check-in

**ก. ตั้งทั้งแถวเป็น `CANCELLED` เหมือนการลา มาสายแล้ว Head Nurse จัดเวรเองหรือเปิดแถวใหม่**
- ข้อดี: ทางเดียวกับการลา ตัวอ่าน Roster ไม่ต้องรู้จัก `NO_SHOW`
- ข้อเสีย: คนที่มาสายไม่กลับเข้าเวรเอง ชั่วโมงทำงานไม่นับจนกว่าจะมีคนจัดให้

**ข. ตั้งแถวเป็น `CANCELLED` และเมื่อ check-in มาสาย ระบบสร้างแถวใหม่ที่ `actual_start_at` = เวลา check-in**
- ข้อดี: ชั่วโมงทำงานและ Gap ถูกต้องเอง ใช้คอลัมน์ของรอบ 4
- ข้อเสีย: ต้องตอบ R5-Q12 ด้วย เพราะคนที่มาสายอาจทับกับคนแทน

### R5-Q12 มาสายหลังมีคนแทนแล้ว

**ก. ยอมให้เวรเกินคน คนแทนยังทำต่อ และ Head Nurse ตัดสินเองว่าจะให้ใครกลับ**
- ข้อดี: ไม่มีการยกเลิกเวรของคนที่เดินทางมาแล้ว
- ข้อเสีย: เกินคนบนกระดาษ และ OT ของสองคน

**ข. ถ้าคนแทนยังไม่ได้เริ่มงาน ยกเลิกคนแทน**
- ข้อดี: ไม่เกินคน
- ข้อเสีย: ต้องรู้ว่าคนแทนเริ่มงานหรือยัง ซึ่งต้องใช้ check-in ของคนแทนด้วย

## กลุ่มที่ 4: Handover (คน 3)

### R5-Q13 Handover มีอะไรบ้าง

**ที่มา:** `STRUCTURED_HANDOVER.content` เป็น jsonb ที่ยังไม่มีรูป ไม่มีโค้ดใดเขียนหรืออ่าน

**ก. ข้อมูลจาก DB ล้วน รูปตายตัว ไม่ใช้ LLM (แนะนำ)**
- ทำอะไร: เวร หอ ช่วงเวลาที่ต้องมาทำ เหตุที่ขาด จำนวนผู้ป่วย Requirement ของเวร (Role, Skill) และคนที่อยู่เวรด้วยกัน
- ข้อดี: ทดสอบได้ตรง ไม่ขึ้นกับบริการภายนอก
- ข้อเสีย: ไม่มีข้อมูลทางคลินิกของผู้ป่วย เพราะระบบไม่มีข้อมูลนั้น

**ข. ข้อมูลจาก DB และประโยคสรุปจาก LLM (`fake` ในรอบนี้)**
- ข้อดี: อ่านง่ายกว่า
- ข้อเสีย: LLM สรุปสถานการณ์อยู่ในรอบ 6 และต้องทำ Lease กับ Retry แบบ PR X ซ้ำ

### R5-Q14 สร้าง Handover เมื่อไร

**ก. หนึ่งแถวต่อหนึ่งคนที่มาแทน สร้างใน Transaction เดียวกับที่คนนั้นได้เวร (แนะนำ)**
- ข้อดี: Handover กับการได้เวรสำเร็จหรือล้มพร้อมกัน
- ข้อเสีย: ต้องแก้ทางที่สร้างเวรทุกทาง (อนุมัติ, อนุมัติเอง, จัดเองใน `MANUAL_HANDOFF`, การย้าย)

**ข. หนึ่งแถวต่อเคส สร้างเมื่อเคสเป็น `RESOLVED`**
- ข้อดี: จุดเดียว
- ข้อเสีย: คนแรกที่ได้เวรในเคสหลายคนไม่เห็นอะไรจนคนสุดท้ายได้เวร และเคสที่จบด้วย `UNRESOLVED` ไม่มี Handover ให้คนที่ได้เวรไปแล้ว

**ก. คนที่มาแทนเห็นในหน้า `/me/offers` และ Head Nurse เห็นในหน้าเคส (แนะนำ)**
- ข้อดี: ใช้หน้าที่มีอยู่
- ข้อเสีย: ต้องมี Route อ่านที่ตรวจว่าเป็นคนที่มาแทนจริง

**ข. แบบ ก และส่งทาง LINE ด้วย**
- ข้อดี: คนที่มาแทนไม่ต้องเปิดหน้าเว็บ
- ข้อเสีย: LINE จริงยังไม่ได้ลอง (R5-Q2) และข้อความยาวต้องจัดรูปใหม่

### ข้อตกลงของ R5-Q23

พยาบาลไม่ check-in แทนกัน เพราะข้อมูลนี้ยืนยันว่าใครมาทำงาน และมีผลต่อ `NO_SHOW` กับการหาคนแทน จึงแยกสองบริบท

* **การใช้งาน:** พยาบาลกด check-in ให้ตัวเองเท่านั้น Route ใช้ตัวตนของผู้กด (`X-Demo-User`) ไม่รับ `staff_id` เพื่อเลือกคนอื่น
* **Demo:** ผู้สาธิตจำลองการมาถึงของตัวละครได้ เช่น "ให้ 201 มาถึงตอนนี้" โดยไม่ต้องสลับตัวตนหลายครั้ง Route นี้อยู่ใต้ `/demo/` ชื่อและข้อความบนหน้าต้องบอกชัดว่าเป็น "จำลองการ check-in" ไม่ใช่การ check-in
* Route ใต้ `/demo/` ต้องเข้าไม่ได้จากช่องทางสาธารณะของระบบจริง
