# คำถามเรื่องระบบล็อกอินและแยกบทบาท (user / staff / head nurse / supervisor)

> เขียนเมื่อ 2026-10-21 ตามที่คน 1 ขอ: เปลี่ยนเว็บจากการ "จำลองตัวตนด้วย Demo" ไปเป็นระบบที่แยกบุคคลและบทบาทจริง
> ตัวเลือกที่เขียนว่า "แนะนำ" คือตัวเลือกที่ผู้เขียนแนะนำพร้อมเหตุผล ข้อที่ไม่มีตัวเลือกแนะนำคือข้อที่ไม่มีเหตุผลพอจะเลือกแทนทีม คำตอบเป็นการตัดสินใจร่วมกันของทั้งสามคน
> วิธีตอบ: เขียนเลขคำถามตามด้วยตัวอักษรของตัวเลือก เช่น `AUTH-Q1 ก` ถ้าไม่ตรงกับตัวเลือกไหนให้เขียนคำตอบเองได้ ข้อที่มีหลายส่วน (เช่น AUTH-Q4) ตอบเป็นรายส่วน
> ข้อที่ติด ★ คือข้อที่ต้องตอบก่อน ถ้ายังไม่ตอบ ออกแบบต่อไม่ได้

## ระบบเป็นอย่างไรตอนนี้ (ตรวจจากโค้ดเมื่อ 2026-10-21)

คำตอบของข้อต่อไปนี้ควรอ่านโดยรู้ว่าของเดิมเป็นอย่างไร ข้อเท็จจริงทั้งหมดตรวจจากโค้ดใน `staging` ไม่ได้เดา

* **ไม่มีการล็อกอิน (ข้อ D9 ของ `workflow.md`):** Backend รู้ว่าใครทำอะไรจาก header `X-Demo-User: <staff_id>` (`backend/app/api/dependencies.py`) ใครส่ง header นี้ก็เป็นคนนั้นได้ทันที ไม่มีรหัสผ่านหรือ session
* **บทบาทมีอยู่แล้ว และมีกฎสิทธิ์อยู่แล้ว:** `approval_service` ตรวจว่าผู้อนุมัติมี Role ที่ต้องการและเป็นคนของหอที่เวรสังกัด (`ApproverRoleError`) ผู้อนุมัติมีสองแบบคือ `HEAD_NURSE` กับ `SUPERVISOR` (`ApproverCapacity`) กฎพวกนี้ทำงานถูกต้อง แต่ตอนนี้ **ไม่มีอะไรพิสูจน์ว่าผู้เรียกเป็นคนนั้นจริง** เพราะตัวตนมาจาก header ที่ใครก็ตั้งได้
* **เว็บ "เปลี่ยนตัวตน" ด้วยตัวเลือก:** หน้าอนุมัติ หน้าส่งต่อ และหน้า My offers มีช่อง "ทำในฐานะ" (`ActingAs`) ให้เลือกพนักงาน 900, 950 ฯลฯ ซึ่งคือการสาธิต ไม่ใช่ล็อกอิน
* **ส่วนใหญ่ใช้ `X-Demo-User` แต่ไม่ตรวจสิทธิ์ตามบทบาท:** Dashboard, เช็ค Gap (`/gap/*`), รายการเคสของหน้า Handoff (`GET /cases`) และ `POST /events` ต้องมี `X-Demo-User` แต่คนไหนเรียกก็ได้ ส่วนหน้าเคสรายตัว (`GET /cases/{id}` และ `/cases/{id}/audit`), `/clock` และ `/demo/*` ไม่ต้องใช้ตัวตนเลย
* **ส่วนของ Demo:** `/demo/*` (รีเซ็ตข้อมูล, เลื่อนและหยุดนาฬิกา, จำลองเช็คอิน) ไม่ต้องใช้ตัวตนเช่นกัน
* **ด่านบน AWS:** Caddy ใช้ HTTP Basic Auth รหัสเดียวร่วมกันทั้งทีมครอบทุก Path ยกเว้น `POST /api/line/webhook` (ข้อ 6.17 และ 6.30) ใครผ่านด่านแล้วเป็นใครก็ได้ผ่าน `X-Demo-User`
* **LINE ผูกตัวตนแยกอยู่แล้ว:** พยาบาลผูกบัญชี LINE ด้วยโค้ด `LINK <code>` (`line_webhook_service.py`) นั่นคือการผูก LINE กับ staff ไม่ใช่การล็อกอินเว็บ

## กลุ่มที่ 1: เป้าหมายและขอบเขต

### AUTH-Q1 ★ ระบบล็อกอินนี้ทำเพื่ออะไร และต้อง "จริง" แค่ไหน

**ที่มา:** คำว่า "เหมือนงานจริง" มีได้สองระดับ ระดับแรกคือหน้าตาและพฤติกรรมเหมือนระบบจริง ระดับที่สองคือปลอดภัยพอให้พยาบาลจริงใช้ ระดับที่สองเพิ่มงานหลายอย่างที่ระดับแรกข้ามได้

**ก. ให้เหมือนระบบจริงตอนสาธิต แต่ยังเป็นเครื่องทดสอบของทีม (แนะนำ)**
- ข้อดี: งานเล็กกว่ามาก ได้ล็อกอิน แยกบทบาท และ Backend ปฏิเสธสิทธิ์ที่ไม่ควรมีจริง เพียงพอให้เห็นระบบทำงานแบบแยกบุคคล
- ข้อเสีย: ไม่พร้อมสำหรับข้อมูลพยาบาลจริง จึงต้องบอกชัดว่าเป็นเครื่องทดสอบต่อไป

**ข. ปลอดภัยพอใช้กับพยาบาลจริง**
- ข้อดี: ใช้ได้จริงในโรงพยาบาลถ้าผ่านเกณฑ์
- ข้อเสีย: ต้องเพิ่ม การล็อกบัญชีเมื่อใส่รหัสผิดซ้ำ การกู้รหัสผ่าน การบังคับความยาวรหัส การเก็บ Log การเข้าถึง และเรื่องข้อมูลส่วนบุคคลตาม PDPA งานมากกว่า ก หลายเท่า และเกินเครื่องทดสอบ 350 USD ของทีม

### AUTH-Q2 ★ บทบาท "user" กับ "staff" ต่างกันอย่างไร และมีกี่บทบาท

**ที่มา:** ในฐานข้อมูลตอนนี้มีแค่ staff (พยาบาล) ที่มี Role และหอที่สังกัด Role ที่เกี่ยวกับการอนุมัติคือ head nurse กับ supervisor ยังไม่มีตาราง "user" แยก และยังไม่มีบทบาทผู้ดูแลระบบ

**ก. มีสามบทบาท คือ staff (พยาบาลทั่วไป), head nurse และ supervisor โดยทุกคนคือแถวใน `staff` เดียวกัน ล็อกอินด้วยบัญชีที่ผูกกับ staff (แนะนำ)**
- ข้อดี: ไม่สร้างตารางตัวตนใหม่ ใช้ Role และหอที่มีอยู่ ลำดับสิทธิ์ตรงกับกฎอนุมัติที่ทำงานอยู่แล้ว
- ข้อเสีย: ไม่มีที่สำหรับบัญชีของคนที่ไม่ใช่พยาบาล

**ข. เพิ่มบทบาทที่สี่ "admin" (ผู้ดูแลระบบ) ที่สร้างบัญชีและดูแลข้อมูล และเก็บแยกจากพยาบาล**
- ข้อดี: แยกหน้าที่ดูแลระบบออกจากงานพยาบาลชัดเจน ปุ่มเช่นรีเซ็ตข้อมูลหรือสร้างบัญชีอยู่ที่ admin ที่เดียว
- ข้อเสีย: ต้องมีตารางหรือ Flag ใหม่ และต้องตัดสินว่า admin ใครเป็น

**ค. บทบาทตามที่คนตอบอธิบายเอง** (เช่น "user" คือผู้ใช้ทั่วไปที่ไม่ใช่พยาบาลเลย เช่นเจ้าหน้าที่ธุรการ)
- ถ้าเลือกทางนี้ ขอให้เขียนว่าบทบาทนั้นทำอะไรได้และเห็นหน้าไหน

### AUTH-Q3 ★ แต่ละบทบาทเห็นหน้าไหนและทำอะไรได้

**ที่มา:** ต้องมีตารางนี้ก่อนจึงจะกำหนดการกั้นฝั่ง Backend และเมนูของเว็บได้ ตารางข้างล่างเป็นข้อเสนอตั้งต้นที่แปลงจากหน้าและ API ที่มีอยู่ ตอบได้ว่า "ตามนี้" หรือแก้เป็นช่องที่ไม่ตรง

| ความสามารถ | staff | head nurse | supervisor |
|---|:-:|:-:|:-:|
| ดูข้อเสนอเวรของตัวเอง ตอบรับหรือปฏิเสธ (My offers) | ได้ | ได้ | ได้ |
| เช็คอินเวรของตัวเอง | ได้ | ได้ | ได้ |
| แจ้งลา (สร้าง Event ของตัวเอง) | ได้ | ได้ | ได้ |
| ดู Roster และเช็ค Gap ของหอตัวเอง | ดูได้ (ข้อ AUTH-Q10) | ได้ | ทุกหอ |
| ดูหน้าเคสและ Audit | ของที่เกี่ยวข้อง (ข้อ AUTH-Q10) | ของหอตัวเอง | ทุกหอ |
| อนุมัติหรือปฏิเสธคำขอที่รอ | ไม่ได้ | หอตัวเอง | ทุกหอ รวมคำขอที่ข้ามหอ |
| ปิดเคสที่ส่งต่อให้คน (Handoff) | ไม่ได้ | หอตัวเอง | ทุกหอ |
| รายงาน Event ที่ทำให้เวรขาด (`POST /events` มี 4 แบบ: ผู้ปฏิบัติงานไม่ว่าง, ยกเลิกการจัดเวร, ผู้ป่วยล้น, เปลี่ยนความต้องการของเวร) | ไม่ได้ | ได้ | ได้ |
| หน้า Demo control, LINE simulator, รีเซ็ตข้อมูล, หยุดนาฬิกา | ไม่เห็น | ไม่เห็น | ไม่เห็น (ยกเว้นเมื่อเปิดโหมด Demo ตามข้อ AUTH-Q11) |

**ข้อที่ต้องตัดสินในตารางนี้:**
* **ก.** ตามตารางนี้
* **ข.** ตามตารางนี้ แต่ supervisor เห็นหน้า Demo control ได้เสมอ เพื่อใช้เตรียมข้อมูลสาธิต
* **ค.** แก้ตารางเอง (ระบุช่องที่ไม่ตรง)

## กลุ่มที่ 2: การพิสูจน์ตัวตน

### AUTH-Q4 ★ ล็อกอินด้วยอะไร

**ที่มา:** วิธีล็อกอินกำหนดว่าต้องมีตารางรหัสผ่านไหม ต้องตั้งค่าบริการภายนอกไหม และต้องจัดการกู้รหัสอย่างไร พยาบาลผูก LINE กับระบบอยู่แล้วด้วยโค้ด `LINK`

**ก. รหัสพนักงานกับรหัสผ่านที่ระบบเก็บเอง (แนะนำ)**
- ข้อดี: ไม่พึ่งบริการภายนอก ทำและทดสอบในเครื่องได้ทั้งหมด รหัสผ่านเก็บเป็น hash (เช่น argon2 หรือ bcrypt) ไม่เก็บตัวจริง
- ข้อเสีย: ต้องมีตารางเก็บ hash จัดการการตั้งและเปลี่ยนรหัส (AUTH-Q5) และรับผิดชอบความปลอดภัยของรหัสเอง

**ข. ล็อกอินผ่าน LINE (LINE Login)** ซึ่งผูกกับ LINE ที่พยาบาลใช้รับข้อเสนอเวรอยู่แล้ว
- ข้อดี: ไม่ต้องมีรหัสผ่านของระบบ ไม่มีเรื่องลืมรหัส พยาบาลคุ้นกับ LINE
- ข้อเสีย: ต้องสร้าง LINE Login Channel เพิ่มและตั้งค่า callback URL ซึ่งต้องมีโดเมน HTTPS จริง (เครื่อง AWS ยังไม่ขึ้น) ทดสอบในเครื่องพัฒนายาก และพึ่ง LINE ถ้า LINE ล่ม เข้าระบบไม่ได้

**ค. ผ่าน SSO หรือผู้ให้บริการอื่น (เช่น Google, ระบบของโรงพยาบาล)**
- ข้อดี: ปลอดภัยและเป็นมาตรฐาน
- ข้อเสีย: ต้องมีผู้ให้บริการกับสิทธิ์ที่ทีมยังไม่มี งานตั้งค่ามาก

**ง. ก ก่อน แล้วเพิ่ม ข ในรอบหลัง**
- ข้อดี: ได้ระบบที่ใช้ได้เร็ว และเปิดทางให้ผูก LINE Login ทีหลังโดยไม่ทิ้งงานเดิม
- ข้อเสีย: ต้องออกแบบตารางตัวตนให้รองรับหลายวิธีตั้งแต่ต้น

### AUTH-Q5 ใครตั้งรหัสผ่านครั้งแรก และกู้อย่างไรเมื่อลืม

**ที่มา:** ข้อนี้ใช้เมื่อเลือก AUTH-Q4 ก หรือ ง ถ้าเลือก ข ข้ามได้

**ตอบเป็นสองส่วน:**

**ส่วนที่ 1 การสร้างบัญชีและตั้งรหัสครั้งแรก**
- **ก.** สคริปต์หรือหน้าของผู้ดูแล (supervisor หรือ admin ตาม AUTH-Q2) สร้างบัญชีและรหัสชั่วคราว บังคับเปลี่ยนรหัสตอนล็อกอินครั้งแรก (แนะนำ)
- **ข.** บัญชีทั้งหมดถูกสร้างจากข้อมูล Seed พร้อมรหัสเริ่มต้นเดียวกัน (ง่ายที่สุด ใช้ได้เฉพาะเครื่องทดสอบ ห้ามใช้บนเครื่องที่เปิดให้ภายนอกเข้า)
- **ค.** พยาบาลลงทะเบียนเองด้วยโค้ด `LINK` ที่ระบบมีอยู่ (ผูกกับการยืนยันตัวผ่าน LINE)

**ส่วนที่ 2 การกู้รหัสเมื่อลืม**
- **ก.** ผู้ดูแลรีเซ็ตให้เป็นรหัสชั่วคราวใหม่ (แนะนำ เพราะไม่ต้องมีระบบส่งอีเมล)
- **ข.** ส่งลิงก์รีเซ็ตทางอีเมลหรือ LINE (ต้องมีระบบส่งและเก็บ token)
- **ค.** ยังไม่มีการกู้ ถ้าลืมให้แจ้งทีมแก้ในฐานข้อมูลโดยตรง

### AUTH-Q6 การล็อกอินอยู่นานแค่ไหน และเก็บอย่างไร

**ที่มา:** หลังล็อกอินสำเร็จ ระบบต้องจำว่าใครกำลังใช้อยู่ การจำมีสองแบบหลัก

**ก. Session ฝั่งเซิร์ฟเวอร์ ส่งเป็น cookie แบบ `HttpOnly` และ `Secure` (แนะนำ)**
- ข้อดี: ยกเลิกทันทีได้ (ออกจากระบบ หรือผู้ดูแลตัดบัญชี) เบราว์เซอร์ส่ง cookie เองโดยไม่ต้องแก้โค้ดฝั่งหน้าเว็บมาก ซึ่งเข้ากับที่หน้าเว็บและ API อยู่ใน Domain เดียวกันอยู่แล้ว (ไม่ติด CORS)
- ข้อเสีย: ต้องมีตาราง session และงานล้าง session ที่หมดอายุ

**ข. Token แบบ JWT เก็บในเบราว์เซอร์**
- ข้อดี: ไม่ต้องมีตาราง session
- ข้อเสีย: ยกเลิกก่อนหมดอายุไม่ได้ทันที และถ้าเก็บใน `localStorage` โดน XSS ขโมยได้ง่ายกว่า cookie `HttpOnly`

**ตอบเพิ่ม:** อายุของการล็อกอิน เช่น 8 ชั่วโมงหรือหมดเมื่อไม่ใช้งาน 30 นาที ตัวอย่างค่าที่ใช้ได้กับกะพยาบาลคือ 8 ถึง 12 ชั่วโมง

### AUTH-Q7 ใส่รหัสผิดซ้ำจะทำอย่างไร

**ที่มา:** ระบบจริงต้องกันการเดารหัสซ้ำๆ แต่เครื่องทดสอบอาจข้ามได้

**ก. หน่วงเวลาและล็อกชั่วคราว เช่น ผิด 5 ครั้งล็อก 15 นาที (แนะนำถ้า AUTH-Q1 เลือก ข)**
- ข้อดี: กันการเดารหัส
- ข้อเสีย: ต้องเก็บจำนวนครั้งที่ผิดและเวลา และคนที่ถูกคนอื่นกลั่นแกล้งจะเข้าไม่ได้ชั่วคราว

**ข. ไม่ล็อก ใช้เพียงการหน่วงตอบ (rate limit ที่ Caddy หรือ API) (แนะนำถ้า AUTH-Q1 เลือก ก)**
- ข้อดี: ง่าย ไม่ล็อกคนผิดตัว
- ข้อเสีย: กันได้น้อยกว่า

**ค. ไม่ทำอะไรในรอบนี้ (ยอมรับความเสี่ยง เพราะเป็นเครื่องทดสอบที่ยังมีด่าน Basic Auth)**

## กลุ่มที่ 3: สิทธิ์ของแต่ละบทบาท

### AUTH-Q8 ★ กฎ "หอของใคร" และ "บทบาทของใคร" ต้องกันที่ Backend เสมอไหม

**ที่มา:** ตอนนี้กฎอนุมัติ (Role และหอ) อยู่ที่ `approval_service` และทำงานแล้ว แต่ตัวตนยังปลอมได้ ถ้ามีล็อกอิน ตัวตนจะมาจาก session ที่ Backend สร้างเอง ทำให้กฎเหล่านี้มีความหมายจริง คำถามคือกฎของ API อื่นๆ (เช่น ดูเคสของหออื่น, ปิดเคสของหออื่น) จะบังคับที่ Backend หรือซ่อนแค่ในหน้าเว็บ

**ก. Backend ปฏิเสธสิทธิ์ที่ไม่ควรมีทุกครั้ง (`403`) และเว็บซ่อนเมนูตามบทบาทเพิ่มเพื่อความสะดวก (แนะนำ)**
- ข้อดี: ปลอดภัยจริง ใครเรียก API ตรงก็ผ่านไม่ได้ เทสต์ตรวจได้ที่ API
- ข้อเสีย: ต้องไล่เพิ่มการตรวจสิทธิ์ให้ทุก Route ที่แก้หรืออ่านข้อมูลของหอ ซึ่งเป็นงานส่วนใหญ่ของ Backend

**ข. ซ่อนเฉพาะในหน้าเว็บ ส่วน Backend คงเดิม**
- ข้อดี: งานน้อย
- ข้อเสีย: ไม่ใช่การแยกบทบาทจริง ใครรู้ URL ของ API ก็ข้ามได้

### AUTH-Q9 Supervisor ต่างจาก head nurse แค่การข้ามหอ หรือมีสิทธิ์พิเศษอื่นด้วย

**ที่มา:** ในโค้ดตอนนี้ supervisor คือผู้ที่อนุมัติแทน head nurse ได้และอนุมัติคำขอที่ข้ามหอ (`ApproverCapacity.SUPERVISOR`) ยังไม่มีสิทธิ์อื่น

**ก. ต่างกันแค่ขอบเขตหอ: supervisor ทำสิ่งที่ head nurse ทำได้ในทุกหอ และอนุมัติคำขอข้ามหอได้ (แนะนำ ตรงกับโค้ดตอนนี้)**
- ข้อดี: ตรงกับกฎที่ใช้งานอยู่ ไม่ต้องเพิ่มกฎใหม่
- ข้อเสีย: supervisor ยังแก้ Roster หรือสร้างบัญชีไม่ได้ ถ้าต้องการต้องเพิ่มเป็นรอบหลัง

**ข. Supervisor มีสิทธิ์เพิ่ม เช่น สร้างและปิดบัญชีพนักงาน แก้ Roster ดู Audit ทั้งระบบ**
- ข้อดี: ใช้แทน admin ได้ ไม่ต้องมีบทบาทที่สี่
- ข้อเสีย: สิทธิ์ที่เพิ่มต้องมีหน้าและ API ใหม่ ขอบเขตงานใหญ่ขึ้น (ต้องระบุว่าเพิ่มอะไรบ้าง)

### AUTH-Q10 พยาบาลทั่วไป (staff) เห็นเคสและข้อมูลของคนอื่นแค่ไหน

**ที่มา:** ตอนนี้หน้าเคส Audit และเช็ค Gap อ่านได้โดยไม่ต้องบอกตัวตน ซึ่งเคสมีชื่อพนักงานที่ถูกเสนอเวร เหตุผลการข้าม และข้อความที่ AI สรุป ในระบบจริงข้อมูลนี้ไม่ควรเปิดให้ทุกคน

**ก. staff เห็นเฉพาะเคสที่ตัวเองเกี่ยวข้อง (เป็นคนที่ถูกเสนอเวรหรือเป็นคนลา) และ Roster ของหอตัวเอง (แนะนำ)**
- ข้อดี: ใกล้ระบบจริงที่สุดในเรื่องความเป็นส่วนตัว
- ข้อเสีย: ต้องเพิ่มการตรวจว่าคนนี้เกี่ยวข้องกับเคสไหน ซึ่งยังไม่มีตอนนี้

**ข. staff เห็นเคสทั้งหมดของหอตัวเอง แต่ไม่เห็นหออื่น**
- ข้อดี: ง่ายกว่า ใช้แค่หอที่สังกัดตัดสิน
- ข้อเสีย: เห็นข้อมูลเพื่อนร่วมหอมากกว่าที่จำเป็น

**ค. staff ไม่เห็นหน้าเคสเลย เห็นแค่ข้อเสนอเวรของตัวเอง**
- ข้อดี: เข้มสุด ข้อมูลน้อยที่สุด
- ข้อเสีย: พยาบาลดูผลของเคสที่ตัวเองลาไม่ได้ ซึ่งอาจขัดกับวิธีที่หน้าเว็บใช้อยู่

## กลุ่มที่ 4: ผลต่อของที่มีอยู่

### AUTH-Q11 ★ โหมด Demo อยู่ต่อไปไหม

**ที่มา:** เทสต์ของ Backend และ Frontend จำนวนมาก (ตอนนี้ Backend ราว 3,100 ข้อ Frontend ราว 460 ข้อ) เรียก API ด้วย `X-Demo-User` ถ้าเอาโหมดนี้ออก ต้องแก้เทสต์เหล่านั้นให้ล็อกอินก่อนเรียก และสคริปต์สาธิต (Demo control, LINE simulator) ที่ใช้ตัวตนจำลองก็ต้องเปลี่ยน

**ก. เก็บไว้สองโหมด: ตัวแปรสภาพแวดล้อมเลือกว่า Backend ใช้ตัวตนจาก `X-Demo-User` (โหมด Demo) หรือจาก session (โหมดจริง) (แนะนำ)**
- ข้อดี: เทสต์เดิมส่วนใหญ่ผ่านต่อโดยไม่ต้องแก้ ยังสาธิตด้วยหน้า Demo ได้ และเพิ่มเทสต์ของโหมดจริงแยกต่างหาก เครื่อง AWS ตั้งโหมดจริงได้ ส่วนเครื่องพัฒนาใช้ Demo
- ข้อเสีย: มีสองเส้นทางให้บำรุงรักษา และต้องมีเทสต์ที่ยืนยันว่าโหมดจริงปิดช่อง `X-Demo-User` ทั้งหมดจริง (ถ้าลืม จะเป็นช่องโหว่)

**ข. เอาโหมด Demo ออกถาวร ทุกอย่างผ่านล็อกอินเท่านั้น**
- ข้อดี: โค้ดเส้นเดียว ไม่มีช่องหลบ
- ข้อเสีย: ต้องแก้เทสต์เกือบทุกไฟล์ที่เรียก API ที่ต้องมีตัวตน และงานสาธิตต้องมีบัญชีล็อกอินของทุกตัวละคร เป็นงานใหญ่และเสี่ยงที่เทสต์จะพังเงียบ

**ค. เก็บโหมด Demo ไว้เฉพาะเครื่องพัฒนาและ CI ที่ตั้งธงเปิดชัดเจน ส่วนเครื่อง AWS บังคับโหมดจริงและเพิ่มเทสต์ที่ตรวจว่าตั้งธง Demo บน AWS แล้ว Stack ไม่ขึ้น**
- ข้อดี: ได้ข้อดีของ ก และกันความผิดพลาดที่เปิดโหมด Demo บนเครื่องที่ภายนอกเข้าถึง
- ข้อเสีย: งานเพิ่มเล็กน้อย (ตัวตรวจตอนเริ่ม)

### AUTH-Q12 ด่าน Basic Auth ของ Caddy บน AWS จะทำอย่างไร

**ที่มา:** ตอนนี้ Caddy ใช้ Basic Auth รหัสเดียวครอบทั้งเว็บ ถ้าเว็บมีล็อกอินเอง พยาบาลจะเจอการขอรหัสสองชั้น

**ก. คงไว้ในช่วงทดสอบ เอาออกเมื่อระบบล็อกอินผ่านการตรวจแล้ว (แนะนำ)**
- ข้อดี: ระหว่างที่ระบบล็อกอินยังใหม่ ยังมีด่านกันคนนอกอีกชั้น
- ข้อเสีย: ผู้ใช้ต้องกรอกรหัสสองครั้งในช่วงนั้น

**ข. เอาออกทันทีที่ระบบล็อกอินใช้งานได้ (ยกเว้น `POST /api/line/webhook` ที่ไม่ผ่านด่านอยู่แล้ว)**
- ข้อดี: ประสบการณ์เหมือนระบบจริง
- ข้อเสีย: ทุก Path ของ API ต้องพึ่งการตรวจ session ของ Backend อย่างเดียว ต้องทดสอบให้แน่ใจว่าไม่มี Path ไหนเปิดโล่ง (ตอนนี้ `/clock`, `/gap/*`, `/cases/*` เปิดโล่งหลังด่าน) และต้องแก้ `check-gate.sh`

**ค. คงไว้เฉพาะ `/demo/*` และ `/api/demo/*` (ใช้เป็นด่านของหน้า Demo) ส่วนที่เหลือพึ่งล็อกอินของระบบ**
- ข้อดี: ได้ประสบการณ์เหมือนระบบจริง และหน้า Demo ที่อันตราย (รีเซ็ต) ยังมีด่านรหัสของทีม
- ข้อเสีย: Caddyfile ซับซ้อนขึ้นและต้องเพิ่มกรณีทดสอบใน `test_gate.py`

### AUTH-Q13 ตัวตนในไฟล์ Audit และการผูก LINE

**ที่มา:** Audit ตอนนี้บันทึกผู้กระทำ (`actor`) จากตัวตนที่ส่งมา และ LINE ผูกกับ staff ด้วยโค้ด `LINK` ถ้าเพิ่มล็อกอิน ต้องตัดสินว่าสองอย่างนี้เกี่ยวกันอย่างไร

**ก. Audit บันทึกบัญชีที่ล็อกอิน (คนเดียวกับ staff) และการผูก LINE ยังเป็นเรื่องแยก: พยาบาลล็อกอินเว็บด้วยรหัสผ่านและผูก LINE ด้วยโค้ด `LINK` เหมือนเดิม (แนะนำ)**
- ข้อดี: ไม่แตะการทำงานของ LINE ที่ผ่านการตรวจแล้ว
- ข้อเสีย: บัญชีล็อกอินกับบัญชี LINE เป็นสองการผูกที่ต้องตรงกัน

**ข. ให้ผูก LINE ได้เฉพาะหลังล็อกอินเว็บ (ออกโค้ด `LINK` ให้ผู้ที่ล็อกอินอยู่ เพื่อให้ผูกกับบัญชีของตัวเองเท่านั้น)**
- ข้อดี: ผูกผิดคนไม่ได้ การผูกอยู่ภายใต้การล็อกอิน
- ข้อเสีย: แก้ขั้นตอนผูก LINE ที่เสร็จแล้ว (รอบ 3) ต้องแก้ทั้ง Backend หน้าเว็บ และเทสต์

## กลุ่มที่ 5: การจัดงาน

### AUTH-Q14 ★ ทำในรอบ 6 หรือรอบถัดไป

**ที่มา:** รอบ 6 เหลือขั้นที่ 6 (เปิดเครื่อง AWS และตรวจช่วง ข), B2 (Bedrock จริง), W (ย้าย Webhook) และปิดรอบ ระบบล็อกอินแตะ Backend, ฐานข้อมูล (Migration ใหม่), หน้าเว็บทั้งหมด, เทสต์เกือบทุกส่วน และ Contract ข้อ D9 ที่ทีมตกลงไว้แล้วว่าไม่มี login

**ก. เปิดรอบ 7 สำหรับเรื่องนี้ หลังปิดรอบ 6 (แนะนำ)**
- ข้อดี: ไม่ขวางการ Deploy และ B2/W ซึ่งต้องผ่านเครื่องจริงก่อน มีเวลาออกแบบและทำ Contract ให้เรียบร้อย การเปลี่ยน D9 เป็นเรื่องใหญ่ ควรมีร่างและรีวิวแบบรอบอื่น
- ข้อเสีย: เว็บบนเครื่อง AWS ที่เปิดให้ทีมทดสอบยังเป็นแบบ Demo ไปก่อน

**ข. ทำในรอบ 6 ก่อน Deploy เครื่องจริง**
- ข้อดี: เครื่องที่เปิดครั้งแรกมีล็อกอินเลย
- ข้อเสีย: ขั้นที่ 6 ล่าช้า ซึ่งเป็นเส้นทางที่ยาวที่สุดของรอบ งาน B2 และ W ที่ต้องใช้เครื่องจริงก็ล่าช้าตาม และเปลี่ยน Contract กลางรอบที่ใกล้ปิด

**ค. แยกเป็นสองส่วน: ใส่ล็อกอินฝั่ง Backend และหน้า login ในรอบ 6 เล็กๆ (บทบาทและตัวตนเท่านั้น) แล้วรอบถัดไปค่อยทำสิทธิ์ละเอียดและหน้าตาของแต่ละบทบาท**
- ข้อดี: ได้ตัวตนจริงบนเครื่องเร็วขึ้น
- ข้อเสีย: ต้องแบ่งงานให้ชัด ซึ่งเสี่ยงที่ครึ่งแรกทำแล้วยังใช้ไม่ได้จริงจนกว่าครึ่งหลังเสร็จ

### AUTH-Q15 ใครรับผิดชอบส่วนไหน

**ที่มา:** งานนี้แตะ Backend (ล็อกอิน สิทธิ์ ตาราง) หน้าเว็บ (หน้า login เมนูตามบทบาท) และ Caddy กับ AWS (ด่าน)

**ก. คน 1 ทำทั้งชุด เพราะเป็นเจ้าของหน้าเว็บและ AWS และเป็นคนเสนอเรื่องนี้**
- ข้อดี: ความรับผิดชอบชัด ออกแบบเป็นเนื้อเดียว
- ข้อเสีย: งานก้อนใหญ่อยู่ที่คนเดียว ซึ่งในรอบ 6 คน 1 มีน้ำหนักงานมากที่สุดอยู่แล้ว

**ข. แบ่งตามส่วน: คน 2 ทำล็อกอินและการตรวจสิทธิ์ใน Backend คน 1 ทำหน้าเว็บและด่าน AWS คน 3 ทำเรื่องผูก LINE (AUTH-Q13) และเทสต์ความปลอดภัย (แนะนำ)**
- ข้อดี: กระจายงานและแต่ละคนทำในส่วนที่ถนัด
- ข้อเสีย: ต้องตกลงรูป API ของล็อกอิน (cookie, ชื่อ Route, รูป `401` และ `403`) ก่อนเริ่ม ซึ่งเป็นสิ่งที่ Contract ต้องกำหนด

**ค. ให้ทีมตัดสินเมื่อเปิดรอบ (ไม่ตอบตอนนี้)**

### AUTH-Q16 เกณฑ์ที่ใช้ตัดสินว่าเสร็จ และสิ่งที่ผู้ตรวจ (อาจารย์) คาดหวัง

**ที่มา:** เกณฑ์ผ่านของแต่ละ PR ควรผูกกับสิ่งที่ผู้ประเมินจะดู ถ้าทีมรู้ว่าอาจารย์หรือเกณฑ์การส่งงานเน้นเรื่องใดเป็นพิเศษ (เช่น ความปลอดภัย, การแยกบทบาท, การออกแบบ, การสาธิต) จะตั้งความลึกของแต่ละข้อได้ตรง

**ตอบเป็นข้อความอิสระ** ว่าส่วนไหนของงานนี้ที่ต้องโชว์ให้ผู้ตรวจเห็น และมีกำหนดส่งหรือเกณฑ์ใดที่ต้องรู้ก่อน ถ้ายังไม่ทราบ ให้ตอบว่า "ยังไม่ทราบ" แล้วทีมจะตั้งเกณฑ์ตั้งต้นตามข้อ AUTH-Q1
