## 2. ขอบเขตรอบ 6

### 2.1 งานของแต่ละคน (ตามตาราง next-move ยังไม่ตัดสินรายละเอียด)

### 3.2 Bedrock จริงและการเลือกโมเดล (คน 2)

ตกลงแล้ว (R6-Q6 ก, R6-Q7 ก, R6-Q8 ก, R6-Q15 ก):
* **เพดานสองชั้น (R6-Q6 ก, ค่าตั้งต้นปรับได้ผ่านค่าตั้ง):** (1) เพดานในแอป 100 ครั้งต่อวันรวมทั้งทีม นับทุก Attempt ที่เรียก Bedrock จริงรวม Retry ใช้วันตามเวลา Asia/Bangkok เก็บตัวนับในฐานข้อมูลเพื่อไม่ให้การรีสตาร์ตล้างยอด และกัน Worker พร้อมกันไม่ให้เรียกเกิน (จองโควตาด้วยคำสั่ง UPDATE เดียวที่ตรวจเพดานในเงื่อนไขก่อนเรียก ไม่อ่านแล้วค่อยเพิ่ม) (2) AWS Budget Alert เฉพาะ Bedrock 20 USD ต่อเดือน ใช้ของผู้จัดถ้าครอบคลุมและทีมได้รับแจ้งเตือน ถ้าเป็นแค่งบรวมให้ขอตั้งการแจ้งเตือนเฉพาะ Bedrock เพิ่ม Budget Alert เป็นการเตือน ไม่ตัดการเรียกทันที
* **ที่มาของตัวเลข (ราคาตามที่ทีมให้มา ยังไม่ได้ตรวจกับราคา AWS):** 100 ครั้งมาจากสมมติฐานสามคน คนละ 15 เคสต่อวัน เคสละสองครั้งรวม Retry = 90 ปัดเป็น 100 (ยังไม่ใช่ปริมาณที่วัดได้) และ 20 USD มาจาก Amazon Nova 2 Lite แบบ Standard ใน Singapore Input 0.41 และ Output 3.39 USD ต่อล้านโทเคน Input 5,000 กับ Output 1,000 โทเคนต่อครั้ง = 0.00544 USD ต่อครั้ง ครบเพดาน 30 วัน = 16.32 USD (ตรวจด้วยโค้ดแล้ว) เผื่อเป็น 20 USD ถ้าใช้ reasoning ต้องนับโทเคนที่คิดเงินส่วนนั้นด้วย
* **ขนาดต่อคำขอ:** จำนวนคำขออย่างเดียวจำกัดค่าใช้จ่ายไม่ได้ จึงต้องมีเพดาน Input (ขนาด Prompt ที่ยอมส่ง) และเพดาน Output (`llm_max_output_tokens` ตอนนี้ 1,024) เป็นค่าตั้ง ค่าตั้งต้นตามสมมติฐาน Input 5,000 และ Output 1,000 โทเคน Payload ที่เกินเพดาน Input ไม่ถูกส่ง
* **ถึงเพดานรายวัน:** ไม่เรียก Bedrock เพิ่ม Plan ที่ยังไม่มีคำอธิบายขอไม่ได้จนวันถัดไป (ปุ่มปิด ข้อความตามข้อ 3.3) การจัดเวรและการอนุมัติทำงานต่อได้ตามปกติ ไม่มี "ข้อความสำรอง" ที่ถูกบันทึกเป็นคำอธิบาย
* **หลังลองจริง:** ตรวจจำนวนโทเคน ค่าใช้จ่าย และความเพียงพอของโควตา แล้วปรับค่าก่อน Demo การใช้ Nova 2 Lite ต้องยืนยันสิทธิ์บัญชีและเงื่อนไข Region ของผู้จัดก่อน (อยู่ในขั้น 1 ด้านล่าง)
* **ตัวกัน Test:** B1 เพิ่มตัวกันใน `conftest.py` แบบเดียวกับ `isolated_line` ของ L5: ตั้ง `LLM_PROVIDER=fake` และ `LLM_ENABLED=false` ทุก Test และ `pytest.fail()` ถ้ามีการเรียก Bedrock จริง Test ของ `bedrock` adapter ด้วย `Stubber` ปิดตัวกันเองอย่างชัดเจน
* **ตรวจตัวเลขในโค้ด:** ทุกตัวเลขในประโยคต้องอยู่ในชุดตัวเลขของ Payload (รวมเลขอันดับใน "อันดับ N") ไม่ตรงบันทึกเป็น `INVALID_OUTPUT` และไม่แสดงประโยค ห้าม LLM คำนวณผลรวมหรือค่าใหม่ ตัวตรวจต้องจัดการเลขไทย ทศนิยม และเครื่องหมายคั่น
* **เกณฑ์เลือกโมเดล:** ผ่านครบสี่ข้อ (1) ตัวตรวจรูปแบบทุกเคส (2) ตัวเลขตรง Payload ทุกเคส (3) ไม่อ้างชื่อหรือรหัสบุคคล เรียกคนว่า "อันดับ N" เท่านั้น (4) ค่าใช้จ่ายต่อ Plan ต่ำกว่าเพดาน เลือกตัวที่ถูกสุดที่ผ่านครบ ถ้าไม่มีตัวไหนผ่าน ห้ามลดเกณฑ์ ให้แก้ Prompt เป็นเวอร์ชันใหม่ (ตอนนี้ `rank-explanation-v2`) แล้วรันทั้งชุดใหม่ หรือใช้ `fake` ต่อ

**ขั้นตอนเลือกโมเดล (B1 แล้ว B2):**
1. **เตรียมก่อนเรียกจริงครั้งแรก:** คน 2 แจ้งว่าเครดิตและสิทธิ์โมเดลใน Region ใช้ได้ (ค้างจาก R5-Q2) ตั้ง Budget Alert และเพดานในแอป ใส่ตัวกัน Test เครื่อง AWS ผ่าน `check-gate.sh` แล้ว คน 2 จึงลองด้วย IAM Role ของเครื่อง (IAM Role อนุญาต `bedrock:InvokeModel` เฉพาะโมเดลที่เลือก)
2. **เขียนเกณฑ์ลงเอกสารก่อนลอง (PR 0):** เกณฑ์สี่ข้อ ชื่อโมเดล 2 ถึง 3 ตัวที่เปิดสิทธิ์แล้ว งบรวมของการลอง และเพดานค่าใช้จ่ายต่อ Plan เขียนก่อนเห็นผล เพื่อไม่ให้ปรับเกณฑ์ตามโมเดลที่ชอบ
3. **ทำชุดเคส 20 ถึง 30 เคสแล้วตรึงไว้:** สร้าง Payload จาก `explanation_service.build_payload()` เก็บเป็นไฟล์เดียวพร้อม `input_hash` ทุกโมเดลได้ข้อมูลเข้าเหมือนกัน ให้หลากหลาย: Plan ปกติ, `partial_plan` ที่คำอธิบาย `plan_penalty` ต่างไป, ผู้สมัครเกิน 10 คนที่ถูกตัดเหลือ 10, ผู้สมัครคนเดียว, คะแนนเท่ากันจนต้องดู `ranking_key` ยังไม่ได้ตรวจว่า Seed ปัจจุบันสร้าง Plan ได้ครบทุกแบบ ถ้าไม่ครบสร้างเคสสังเคราะห์เพิ่ม

7. **ตัดสิน:** ทำตารางโมเดลคูณเกณฑ์ ตัดตัวที่ตกข้อใดข้อหนึ่ง เลือกตัวที่ถูกสุดที่เหลือ
8. **ตั้งค่าและบันทึก:** ตั้ง `LLM_MODEL_ID`, `AWS_REGION` และราคาบนเครื่องเท่านั้น ไม่ใส่ใน repo เขียนผลและค่าใช้จ่ายจริงลง Description ของ B2 และตารางใน `workflow.md` Test ยังใช้ `fake` ส่วน `LLM_ENABLED=true` ตั้งหลัง E1 merge ตามข้อ 3.2.1 ข้อ 7

**ข้อจำกัด:** 20 ถึง 30 เคสคัดตัวที่พลาดบ่อยออกได้ แต่พิสูจน์ไม่ได้ว่าโมเดลไม่เคยพลาด ความเสี่ยงที่เหลือถูกกันด้วยตัวตรวจตัวเลขในโค้ดซึ่งทำงานทุกครั้งที่ระบบเรียกจริง

### 3.2.1 ที่เก็บบันทึกการเรียกและตัวห่อการเรียก (งานของ B1, แก้ตามรีวิว PR #104 ข้อ 3)

**ปัญหาที่ตรวจพบ [ตรวจแล้ว]:** `llm_call_log.explanation_id` เป็น `NOT NULL` และอ้าง `rank_explanation` (พร้อม `case_id` และ `plan_id` ที่ `NOT NULL`) ข้อมูลของชุดทดลองไม่มีเคสหรือ Plan และสรุปเคสไม่ใช่แถวของ `rank_explanation` จึงบันทึกด้วยโครงสร้างเดิมไม่ได้ และ `llm_service.generate_explanation()` เรียกตัวเชื่อมอย่างเดียว ไม่เขียนบันทึกและไม่จองโควตา (การเขียนบันทึกอยู่ใน `explanation_service._start_attempt` และ `_record` ซึ่งผูกกับ `rank_explanation`) B2 และ S จึงใช้ไม่ได้ถ้าไม่มีสิ่งต่อไปนี้ B1 จึงเป็นเจ้าของทั้งหมด และ B2, E1, S ต้องพึ่ง B1

**ข้อเสนอของร่างสำหรับ B1 (ยังไม่ตกลงรูปแน่นอน ต้องผ่านการรีวิว PR 0):**
1. **Migration ของ `llm_call_log`:** เพิ่ม `work_type` (`RANK_EXPLANATION`, `CASE_SUMMARY`, `MODEL_TRIAL`; แถวเดิมทั้งหมดเป็น `RANK_EXPLANATION`) ทำให้ `explanation_id`, `case_id`, `plan_id` เป็น NULL ได้ เพิ่ม `subject_id` (รหัสแถวสรุปเคส ไม่มี FK เพราะตารางนั้นยังไม่มีตอน B1) กับ `trial_run_id` และ `trial_case_key` (สำหรับชุดทดลอง) และ CHECK ตามชนิด: `RANK_EXPLANATION` ต้องมี `explanation_id`, `case_id`, `plan_id`; `CASE_SUMMARY` ต้องมี `subject_id` และ `case_id`; `MODEL_TRIAL` ต้องมี `trial_run_id` และ `trial_case_key` และไม่มี `case_id`/`plan_id` Unique เดิม (`explanation_id, attempt`) คงไว้ และเพิ่ม Unique บางส่วนของแต่ละชนิดที่เหลือ
2. **ตารางตัวนับ:** `llm_daily_usage` (วัน Asia/Bangkok, ขอบเขต `DEMO` หรือรหัสชุดทดลอง, จำนวนที่ใช้) จองโควตาด้วยคำสั่งเดียวแบบ `INSERT ... ON CONFLICT DO UPDATE SET used = used + 1 WHERE used < :cap RETURNING used` เพื่อไม่ให้ Worker พร้อมกันเกินเพดาน
3. **ตัวห่อการเรียกตัวเดียว** (ชื่อชั่วคราว `llm_gateway.call()`): (ก) จองโควตาของขอบเขตนั้นและ commit (ถ้าจองไม่ได้ คืนผล "ถึงเพดาน" โดยไม่เรียกตัวเชื่อมและไม่ใช้โควตา) (ข) เขียนแถวบันทึก `IN_FLIGHT` (ค) เรียก `llm_service.generate_explanation()` (ง) อัปเดตแถวด้วยผล โทเคน และค่าใช้จ่าย ทุก Attempt ผ่านตัวห่อนี้ รวม Retry ผู้เรียก (E1, S, B2) ถือหน้าที่ลองซ้ำเอง ตามที่ `generate_explanation()` เป็นอยู่
4. **ขอบเขตของชุดทดลอง:** ตัวห่อรับขอบเขต `DEMO` จากโค้ดของ Route ผู้ใช้เท่านั้น ขอบเขตชุดทดลองกำหนดได้จากสคริปต์ภายในที่ส่งรหัสชุดทดลองและเพดานของชุดเอง ไม่มี Route หรือพารามิเตอร์ของผู้ใช้ที่เลือกขอบเขตได้ (ตรงกับตารางข้อ 6)
5. **ค่าใช้จ่ายรวม:** ผลรวม `estimated_cost_usd` ทุก `work_type` ในเดือนเดียวกัน เทียบงบ 20 USD (Dashboard แสดง)
6. **B1 ปรับตัวประมวลผลเดิมของ `explanation_service` ให้เรียกผ่านตัวห่อนี้ด้วย (แก้ตามรีวิว PR #104 รอบสอง)** ตัวประมวลผลเดิม (`run_pending`, `_process_one`, `_start_attempt`, `_call`, `_record`) เรียกตัวเชื่อมและเขียน `llm_call_log` เอง ไม่ผ่านตัวนับ และเริ่มทำงานทันทีเมื่อ `LLM_ENABLED=true` (ตรวจแล้ว: `run_pending` ตรวจแค่ `llm_enabled` และ `llm_ready`, `optimize.py:34` เข้าคิวเมื่อ `llm_enabled`) ถ้าเปิดก่อนแปลงจะเรียก Bedrock โดยไม่นับโควตา B1 จึงแปลงเอง เพื่อให้ไม่มีทางเรียกตัวเชื่อม LLM นอกตัวห่อตั้งแต่ B1 merge เมื่อตัวนับถึงเพดาน แถวที่ถึงตาประมวลผลไม่ถูกเรียกและไม่ใช้โควตา (ข้อเสนอ: ตั้งเป็น `SKIPPED` พร้อมเหตุผล `QUOTA_EXHAUSTED` ซึ่ง E1 ใช้เป็นสถานะ "ถึงเพดาน" และเปิดให้ขอใหม่ตามข้อ 3.3) E1 ไม่ต้องแตะการเรียกตัวเชื่อมอีก S และ B2 เรียกตัวห่อโดยตรง
7. **เปิด LLM ในแอปหลัง E1 เท่านั้น:** `LLM_ENABLED=true` (ที่ทำให้ตัวประมวลผลเดิมทำงานและ `optimize.py` เข้าคิวอัตโนมัติทุก Plan) ห้ามตั้งบนเครื่อง AWS จนกว่า E1 merge เพราะก่อนหน้านั้นการเข้าคิวยังเป็นอัตโนมัติ ขัดกับ R6-Q19 แม้จะผ่านตัวห่อและมีเพดานแล้ว B2 รันชุดทดลองผ่านตัวห่อได้โดยไม่ต้องตั้ง `LLM_ENABLED` (ชุดทดลองเรียกจากสคริปต์ภายใน ไม่ใช่ตัวประมวลผลของแอป) ข้อ "เปิดใช้" ของข้อ 3.2 จึงแยกเป็นการตั้งโมเดลและ Region ตอน B2 กับการตั้ง `LLM_ENABLED=true` หลัง E1

### 3.3 คำอธิบายอันดับตามที่ผู้ใช้กดขอ (R6-Q19, คน 2 ฝั่ง Backend และคน 1 ฝั่งหน้าเว็บ)

เปลี่ยนจากโค้ดปัจจุบัน (เข้าคิวอัตโนมัติทุก Plan) เงื่อนไขหกข้อที่ตกลงแล้ว:
1. **ไม่เรียก LLM หลัง Ranking** หน้า Ranking แสดงอันดับ คะแนน และข้อมูลประกอบจากระบบตามปกติ การจัดเวรและการอนุมัติไม่รอ LLM `optimize.py` เลิกเรียก `explanation_service.enqueue()`
2. **กด "หน้าสรุปด้วย AI" จึงสร้างคำอธิบายของ Plan นั้น** ถ้ายังไม่มีผล ระบบสร้างงานให้ Job เรียก LLM แล้วบันทึกข้อความลงฐานข้อมูล
3. **สร้างสำเร็จครั้งเดียวต่อ Plan** เคยสร้างแล้วแสดงข้อความเดิมเสมอ เปิดซ้ำ รีเฟรช หรือกดจากหลายหน้าต่างต้องไม่เรียกใหม่ กำลังสร้างแสดงสถานะกำลังดำเนินการและไม่สร้างงานซ้ำ Plan ใหม่จากการจัดอันดับใหม่ถือเป็นคนละรายการ
4. **เมื่อถึงเพดาน ปิดปุ่มสำหรับ Plan ที่ยังไม่มีคำอธิบาย** พร้อมข้อความ "ใช้โควตาคำอธิบายจาก AI ครบแล้วในวันนี้ กรุณาลองใหม่ในวันถัดไป คุณยังดูอันดับและดำเนินการจัดเวรต่อได้ตามปกติ" Plan ที่มีคำอธิบายสำเร็จแล้วยังเปิดอ่านผลเดิมได้ เพราะไม่เรียก LLM และไม่ใช้โควตา
5. **ตรวจเพดานที่ Backend ด้วย** กันการเรียกผ่าน API และการกดพร้อมกัน นับทุก Attempt ที่เรียก Bedrock จริงรวม Retry ตามวัน Asia/Bangkok
6. **ล้มเหลวแสดงสถานะตามจริง** ไม่บันทึกข้อความแจ้งข้อผิดพลาดหรือข้อความถึงเพดานเป็นคำอธิบาย AI ที่สำเร็จ และไม่กระทบ Ranking การจัดเวร หรือการอนุมัติ

**ข้อเสนอของร่างเพื่อทำให้ข้อ 1 ถึง 6 ทำงานได้ (ยังไม่ตกลง):**
* Route ใหม่ `POST /cases/{id}/explanation` (ชื่อชั่วคราว) ของ Plan ล่าสุดของเคส ตอบเร็ว: ถ้ามีแถวอยู่แล้วคืนแถวเดิมโดยไม่สร้างใหม่ (ใช้ Unique `plan_id, prompt_version` เป็นด่านสุดท้ายเมื่อกดพร้อมกัน) ถ้ายังไม่มีสร้างแถว `PENDING` แล้วคืนทันที ไม่เรียก Bedrock ใน Request นี้ Job เดิมเรียก Bedrock ภายหลัง (Lease, Retry, `MAX_PER_SWEEP` ไม่เปลี่ยน)
* Backend ตรวจเพดานสองจุด: ตอนรับคำขอ ถ้าตัวนับของวันถึงเพดานแล้วตอบว่าถึงเพดานโดยไม่สร้างแถว และตอนเรียกจริงของ**ทุก Attempt** จองโควตาด้วยคำสั่งเดียวที่ตรวจเพดานในเงื่อนไข (ตามข้อ 3.2) ถ้าจองไม่ได้ ไม่เรียก Bedrock และแถวไม่เป็น `READY`
* `GET /cases/{id}` คืนสถานะของคำอธิบาย (ยังไม่เคยขอ, กำลังสร้าง, สำเร็จ, ล้มเหลว, ถึงเพดาน) และธงว่าขอได้ไหมตอนนี้ (ตัวนับของวันยังไม่ถึงเพดานหรือไม่) เพื่อให้ปุ่มปิดได้โดยไม่ต้องลองกด
* **ขอใหม่หลังล้มเหลวหรือถึงเพดาน (ตกลงแล้ว):** ใช้แถวเดิมของ Plan นั้นตาม Unique `plan_id, prompt_version` ไม่สร้างแถวใหม่ แต่เก็บประวัติ Attempt ของแถว (`llm_call_log` มีอยู่แล้ว) และห้ามล้างยอดโควตาที่ใช้ไปแล้ว
  * ถึงเพดาน: กดใหม่ได้เมื่อโควตาว่างหรือขึ้นวันใหม่ การปฏิเสธก่อนเรียก Bedrock ไม่ใช้โควตา
  * ล้มเหลวชั่วคราว: ขอใหม่ได้ภายใต้เพดานและจำนวน Attempt สูงสุดที่ทีมกำหนด (ตัวเลขเขียนใน PR 0 ตอนนี้ `llm_max_retries` ไม่เกิน 1 และไม่เกิน 2 Attempt ต่อแถวต่อรอบ) ห้ามกดเพื่อรีเซ็ตเพดาน Retry ตัวนับ Attempt ของแถวไม่ถูกล้างเมื่อขอใหม่
  * ข้อมูลหรือค่าตั้งไม่ถูกต้อง (เช่น ไม่มี `LLM_MODEL_ID`, Payload ไม่ผ่านการตรวจ): ต้องแก้สาเหตุก่อน ปุ่มไม่เปิด
  * สร้างสำเร็จแล้ว: อ่านผลเดิม ไม่เปิดให้สร้างซ้ำ
* **แถว `PENDING` ที่ค้างจากโค้ดเดิม (ข้อเสนอ ยังไม่ตกลง):** Plan ที่สร้างก่อน E1 merge อาจมีแถว `PENDING` ที่ถูกเข้าคิวอัตโนมัติไว้แล้ว E1 ต้องตัดสินว่าให้ Job ประมวลผลต่อ (กินโควตา) หรือตั้งเป็นสถานะที่ผู้ใช้ต้องกดขอเอง ข้อเสนอคือตั้งให้ผู้ใช้ต้องกดขอ เพื่อให้กติกา "ไม่เรียกโดยไม่มีคนกด" ไม่มีข้อยกเว้น
* กติกานี้ใช้กับ "สรุปสถานการณ์ของเคส" (ข้อ 4) ด้วย และใช้เพดานรวมเดียวกับคำอธิบายอันดับ (ตกลงแล้ว)
* ถ้า `PROMPT_VERSION` เปลี่ยนในอนาคต Plan เก่าที่มีคำอธิบายแล้วยังแสดงข้อความเดิม (ไม่สร้างใหม่เพราะ Prompt เปลี่ยน)

## 4. LLM สรุปสถานการณ์ (คน 3)

ตกลงแล้ว (R6-Q9 ก, R6-Q10 ก):
* สรุปของเคสหนึ่งเคสให้ Head Nurse อ่านในหน้า `cases/[id]`: ขาดกี่คนช่วงไหน ทำอะไรไปแล้ว (Wave กี่รอบ ตอบรับกี่คน) รออะไรอยู่ อ่านอย่างเดียว ไม่ใช่ข้อความที่ส่งหาพยาบาล
* เก็บในตารางใหม่ผูกกับเคสและสถานะของเคสที่สรุป (Migration ของ S) บันทึกการเรียกใช้ `llm_call_log` ที่มี `work_type = CASE_SUMMARY` และตัวห่อการเรียกที่ B1 สร้าง (ข้อ 3.2.1) S ไม่เพิ่มคอลัมน์ในตารางนั้น เพื่อให้เพดานในข้อ 3.2 นับค่าใช้จ่ายรวมที่เดียว
* **การเรียก (ตกลงแล้ว):** ผู้ใช้กดขอตามกติกาข้อ 3.3 ใช้เพดานรวมเดียวกับคำอธิบายอันดับ
* **ผูกกับเวอร์ชันข้อมูล (ตกลงแล้ว):** สถานการณ์ของเคสเปลี่ยนได้ สรุปแต่ละฉบับจึงผูกกับ Snapshot ของข้อมูลที่ใช้สรุป ถ้าข้อมูลเดิมแสดงผลเดิม ถ้าข้อมูลเปลี่ยน หน้าแสดงว่าสรุปฉบับนี้ล้าสมัยและให้ผู้ใช้กดสร้างฉบับใหม่ ฉบับก่อนหน้าเก็บเป็นประวัติ ไม่ถูกเขียนทับ
* **ข้อเสนอของร่าง (ยังไม่ตกลง) วิธีทำ Snapshot:** ใช้แบบเดียวกับคำอธิบายอันดับ คือ `input_hash` = SHA-256 ของ JSON แบบ Canonical ของ Payload ที่สรุป (ข้อ 6.15) ตารางสรุปมี Unique `case_id, input_hash, prompt_version` Payload ของสรุปเคสต้องคำนวณได้จาก DB ล้วนและเหมือนเดิมทุกครั้งเมื่อข้อมูลไม่เปลี่ยน ไม่มีเวลาปัจจุบันหรือเลขสุ่มปนอยู่ ไม่อย่างนั้น Hash จะเปลี่ยนทุกครั้งและผู้ใช้ต้องกดซ้ำโดยไม่จำเป็น
* ใช้แบบอย่างเดียวกับประโยคอธิบายอันดับ: Payload สร้างจาก DB ไม่มีชื่อหรือรหัสบุคคล เก็บ `PENDING` ใน Transaction ของการเปลี่ยนสถานะ Job ประมวลผลภายหลัง ล้มแล้วเคสไม่ล้ม (ข้อ 6.25) และใช้ตัวตรวจตัวเลขเดียวกับข้อ 3.2
* ผลที่ได้ห้ามมีผลต่อ Gap, Wave, Safety หรืออนุมัติ หน้าเว็บแสดงตัวเลขจริงจาก DB ข้างข้อความ และบอกว่าข้อความมาจาก LLM ถ้าสร้างไม่สำเร็จหน้าต้องใช้งานได้ตามปกติ

## 5. ข้อความอิสระของพยาบาล (คน 3)

ตกลงแล้ว (R6-Q11 ค, R6-Q12): **ไม่ใช้ LLM** งานนี้เหลือเป็นตัวตอบกลับแบบกำหนดไว้
* ข้อความ LINE ที่ไม่ใช่ `LINK`, `CHECKIN` หรือปุ่ม จะได้ข้อความตอบบอกวิธีกดปุ่มของ Offer ล่าสุด ตอนนี้ **[ตรวจแล้ว]** ข้อความอื่นถูกจดว่าได้รับแล้วและไม่ตอบ

* ไม่เก็บข้อความของพยาบาลใน DB หรือ Log นอกจากรหัส Event ที่ `LineWebhookEvent` เก็บอยู่แล้วเพื่อกันซ้ำ และไม่ส่งข้อความเข้า LLM ดังนั้นข้อกังวลเรื่อง prompt injection จากข้อความของพยาบาลไม่เกิดในรอบนี้ ถ้ารอบหลังจะให้ LLM อ่านข้อความอิสระ ต้องเปิดคำถามใหม่
* ข้อเสนอ ยังไม่ตกลง: ไม่ส่งตอบซ้ำเมื่อ LINE ส่ง Event เดิมมาอีก (ใช้ Dedup เดิม) และไม่ตอบข้อความจากกลุ่มหรือห้อง ตามที่คำสั่ง check-in ทำอยู่
