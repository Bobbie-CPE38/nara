### R6-Q2 รอบ 6 ทำอะไรบ้าง

**ที่มา:** `next-move.md` เขียนว่า "ทีมต้องเลือกก่อนว่าจะทำทางนี้ไหม" ยังไม่เคยมีคำตอบ งานทั้งหมดของรอบนี้ใช้บริการจริงที่คิดเงิน (Bedrock, AWS) และเปิดรับข้อความของคน (LINE)

**ก. ทำทั้งหมดตามตาราง: AWS, Bedrock, LLM สรุปสถานการณ์, LLM ตีความคำตอบอิสระ, ย้าย Webhook**
- ข้อดี: ครบตามแผนตั้งแต่รอบ 1 และจบ Walking Skeleton ถึงระบบที่ลองใช้จริงได้
- ข้อเสีย: งานมาก ค่าใช้จ่ายและความเสี่ยงสูงสุด (ข้อความอิสระเข้า LLM) และสองงานสุดท้ายรอ AWS กับ Bedrock

**ข. ทำเฉพาะ AWS, Bedrock กับประโยคอธิบายอันดับที่มีอยู่ และย้าย Webhook ส่วน LLM สรุปสถานการณ์กับ LLM ตีความคำตอบอิสระเลื่อนไปรอบ 7 (แนะนำ)**
- ข้อดี: ได้ของจริงที่ทดสอบได้ก่อน (เครื่อง, Bedrock, Webhook) และรู้ราคาจริงต่อ Plan ก่อนเพิ่ม LLM อีกสองจุด งานตีความข้อความอิสระที่เสี่ยงสุดไปทำเมื่อมีเพดานและเครื่องพร้อม
- ข้อเสีย: งานของคน 1 (สรุปสถานการณ์) เหลือแค่ AWS และคน 3 เหลือแค่ย้าย Webhook ซึ่งเบากว่าตาราง

**ค. ทำ AWS, Bedrock, ย้าย Webhook และ LLM สรุปสถานการณ์ แต่เลื่อนเฉพาะ LLM ตีความคำตอบอิสระ**
- ข้อดี: คน 1 มีงาน LLM ที่อ่านอย่างเดียว ความเสี่ยงต่ำ (ไม่มีข้อความจากคนเข้า Prompt) ส่วนทางที่เสี่ยงสุดเลื่อนไปทีหลัง
- ข้อเสีย: คน 3 เหลือแค่ย้าย Webhook

**ง. เลื่อนทุกอย่างของ LLM และ AWS ไปทำเป็นรอบสุดท้ายหลังเลือกงานอื่นก่อน**
- ข้อดี: ไม่ใช้เงินและเวลากับบริการภายนอกจนกว่าจะแน่ใจว่าต้องใช้
- ข้อเสีย: ระบบยังไม่เคยทำงานบนเครื่องจริงและ Bedrock จริงเลย ความเสี่ยงที่ซ่อนอยู่ย้ายไปท้ายโครงการ

### R6-Q3 เกณฑ์ปิดรอบ 6 คืออะไร

**ที่มา:** รอบ 3 ปิดโดยไม่มีบริการจริงและเขียนตาราง "fake กับของจริง" ไว้ รอบ 4 ปิดโดยงานค้างสามเรื่องหลุด รอบ 6 คือรอบที่ต้องผ่านบริการจริง

**ก. ปิดรอบได้เมื่อ (1) เครื่อง AWS ผ่าน `check-gate.sh` (2) LINE ส่ง Offer และรับคำตอบผ่านเครื่อง AWS จริงอย่างน้อยหนึ่งเส้นทาง (3) Bedrock สร้างประโยคอธิบายอันดับจริงอย่างน้อยหนึ่งเคสพร้อมบันทึกค่าใช้จ่าย และ (4) ตาราง "fake กับของจริง" ทุกแถวมีวันที่หรือเหตุผลที่ยังใช้ fake (แนะนำ)**
- ข้อดี: ปิดรอบแล้วรู้ว่าอะไรผ่านของจริง ไม่ต้องย้อนไปตามอีก
- ข้อเสีย: รอบปิดไม่ได้ถ้าบัญชีหรือสิทธิ์ AWS ไม่พร้อม

**ข. ปิดรอบได้เมื่อ PR เข้า `staging` ครบ การลองของจริงเป็นงานแยก**
- ข้อดี: ไม่ผูกรอบกับสิ่งที่นอกการควบคุม
- ข้อเสีย: ซ้ำรอยรอบ 4 ที่งานค้างสามเรื่องหลุด และทั้งรอบนี้เป็นเรื่องของจริงอยู่แล้ว

* **เพดาน 100 ครั้งต่อวันรวมทั้งทีม** นับทุก Attempt ที่เรียก Bedrock จริงรวม Retry วันนับตามเวลา Asia/Bangkok เก็บตัวนับในฐานข้อมูลเพื่อไม่ให้การรีสตาร์ตล้างยอด และต้องกัน Worker ที่ทำงานพร้อมกันไม่ให้เรียกเกินเพดาน

* **ที่มาของ 100 ครั้ง (สมมติฐานวางแผน ไม่ใช่ปริมาณที่วัดได้):** ทีมสามคนทดสอบคนละ 15 เคสต่อวัน เคสละเฉลี่ยสองครั้งรวม Retry เป็น 90 ครั้ง ปัดเป็น 100
* **ที่มาของ 20 USD (ราคาตามที่ทีมให้มา ผมยังไม่ได้ตรวจกับราคาของ AWS):** Amazon Nova 2 Lite แบบ Standard ใน Singapore: Input 0.41 USD และ Output 3.39 USD ต่อล้านโทเคน ถ้าหนึ่งครั้งใช้ Input 5,000 โทเคนและ Output ที่คิดเงินรวม 1,000 โทเคน จะเป็น 0.00544 USD ต่อครั้ง เต็มเพดานทุกวัน 30 วันได้ 16.32 USD (ตรวจด้วยโค้ดแล้วตรงกัน) จึงเผื่อเป็น 20 USD ถ้าใช้ reasoning ต้องนับโทเคนที่คิดเงินส่วนนั้นด้วย
* **ต้องกำหนดขนาด Input และเพดาน Output ต่อคำขอด้วย** เพราะจำนวนคำขออย่างเดียวจำกัดค่าใช้จ่ายไม่ได้
* **ถึงเพดานรายวัน:** หยุดเรียก LLM และใช้ข้อความสำรองตามกติกาของระบบ การจัดเวรทำงานต่อได้ตามปกติ Budget Alert เป็นการเตือน ไม่ตัดการเรียกทันทีเมื่อถึง 20 USD

**2. ล้มเหลวหรือถึงเพดาน กดขอใหม่ได้เมื่อเงื่อนไขพร้อม** คำอธิบาย Plan ใช้แถวเดิมตาม Unique ที่มี แต่ต้องเก็บประวัติ Attempt และห้ามล้างยอดโควตาที่ใช้ไปแล้ว
